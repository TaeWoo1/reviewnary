# 공급자 서버 범위와 API 계약 v1 (초안)

**상태:** 2026-10-17 초안. §0의 D1–D6은 오너가 확정했다. D5는 같은 날 실제 내보내기 파일의 구조를 확인해
"제공되는 첨부 1개 활용"으로 정해졌다(§3.1).
**정본 관계:** 범위는 scope lock v1.14(`docs/product-scope-v1.md`) ①·⑦·⑧, 구역 분할과 보유 기준은
`docs/reviewnary_product_architecture_proposal_v1.md` §17.9가 정한다. 이 문서는 그 결정을 엔드포인트 · 저장
필드 · 상태 전이 · 삭제 시점으로 옮긴 것이며 새 제품 결정을 하지 않는다. 결정이 필요한 곳은 [PO] · [EXT] ·
[REPO]로 표시한다.

## 0. 오너 결정 (2026-10-17)

| D7 | (2026-10-25 개정 — 오너 결정 「기기만 다르고」, 이전: 2026-10-21 「판매자가 보낸 초안만」) **초안은 하나, 기기만 다르다** — 서버에서 받아 온 리뷰에 대한 PC 초안은 저장될 때마다 서버에 자동으로 올라가 휴대폰 「할 일」에도 같이 보인다. 휴대폰에서 고친 문장은 PC 초안이 되고, 두 기기가 동시에 고쳤으면 휴대폰 문장이 앞서고 PC 문장은 판매자가 고를 때까지 따로 둔다. 「휴대폰으로 승인 요청」 버튼은 없앴다. **승인은 자동으로 하지 않는다** | 휴대폰에서 기다리기만 하는 초안(`AWAITING_APPROVAL` · `RECHECK_NEEDED`)은 PC의 길을 막지 않는다 — PC에서 복사 길로 승인하면 휴대폰의 초안을 먼저 거둔다(취소). 승인된 작업이 열려 있는 동안 PC의 승인 · 가이드 등록 길은 닫힌다(답글 두 번 방지). 판매자가 「요청 취소」한 리뷰는 저절로 다시 올리지 않는다. 담당자 없는 스토어는 서버에 리뷰가 없으므로 올라갈 초안도 없다 |
| D9 | (2026-10-21, 2026-10-25 이름 「답글 등록 요청」) **PC에서 바로 「답글 등록 요청」** — PC 앞의 판매자는 화면에 보이는 그 버전(`baseVersion`) 그대로 승인한다. 그사이 PC나 휴대폰에서 문장이 바뀌었으면 승인하지 않고 바뀐 문장을 보여 준다 | 판매자가 누른 것만 승인된다. 이 길이 서는 리뷰에서는 PC의 「승인」(복사 길)이 보조 버튼으로 내려간다 |
| D10 | (2026-10-21) **PC에서도 「요청 취소」** | 서버 규칙 그대로: 착수 전이면 즉시 끝, 착수 후면 담당자에게 멈춤 요청 |
| D11 | (2026-10-21) **담당자 화면은 PC 브라우저 기준** — 판매자센터 옆에 띄워 놓고 복사 · 붙여넣기 | 휴대폰 승인 화면은 휴대폰 기준. 두 화면 모두 시안 확인 후 구현(§10 끝 문장) |
| D8 | (2026-10-21) **'답글 필요 없음'은 판매자가 정한 것만 서버에 알린다** — PC에서 사람이 분류를 `NO_ACTION`으로 둔 리뷰. AI 판정은 보내지 않는다 | §6의 90일 시작 조건이 이 표시와 PC 저장 확인이다 |

## 1. 서버가 하는 일과 하지 않는 일

| 한다 | 하지 않는다 |
|---|---|
| 계정 · 설치 등록 · 라이선스 상태 | 채널 API 호출(Cafe24 토큰 엔드포인트만 예외, §5) |
| 담당자의 리뷰 파일 반입 · 열 제거 · 보관 | 문의 · 상품 · 지식 · 응대 기준 보관 |
| 리뷰 대행 작업의 상태 정본(승인 · 철회 · 착수 · 결과) | 초안 생성 · AI 호출(§17.9: 초안은 PC가 만든다) |
| Cafe24 토큰 중계와 응답 유실 복구 | 임의 명령 · URL · 파일 읽기 전달(§17.6) |
| 요청자 공인 IPv4 응답 | 판매자 PC로의 원격 접속 · 푸시 실행 |

**서버 → PC 방향의 요청은 없다.** PC가 항상 먼저 묻고(pull), 서버는 상태와 자료만 돌려준다. 서버가 PC에게 무엇을
"하라"고 지시하는 필드를 응답에 두지 않는다.

## 2. 행위자와 인증

| 행위자 | 인증 | 볼 수 있는 범위 |
|---|---|---|
| 판매자(휴대폰 · 브라우저) | 이메일 · 비밀번호 → 세션 JWT (기존 `JwtTokenProvider` 형태) | 자기 스토어의 리뷰 · 작업 |
| 설치(판매자 PC) | 장치 승인 흐름 → 불투명 설치 토큰(`rvi_` 접두사, 서버는 SHA-256만 저장) + 설치 공개키 | 자기 계정 스토어의 리뷰 · 작업 동기화, Cafe24 중계 |
| 담당자(공급자 직원) | 이메일 · 비밀번호 + TOTP(D3) | 배정된 스토어의 리뷰 업로드 · 승인된 작업 |
| 관리자 | 담당자와 같음 + 역할 | 배정 · 계정 관리. 원문 열람은 배정 범위로만 |

**권한과 회수는 행위자마다 따로 둔다(D2).** 판매자 계정 정지는 그 계정의 세션과 설치 토큰을 함께 끊는다. 설치
하나만 회수(분실 PC)해도 계정은 유지된다. 담당자 회수는 그 사람의 세션과 스토어 배정을 끊되, 이미 착수(`CLAIMED`)한
작업은 다른 담당자에게 넘기지 않고 `UNKNOWN`으로 두어 확인을 거친다. 담당자는 TOTP와 일회용 복구 코드를 쓰고(D3),
복구 코드는 해시만 저장한다.

설치 등록은 기존 helper 장치 인증(`auth/device/HelperDeviceService`, RFC 8628 장치 승인)과 같은 모양을 쓴다:
PC가 코드를 받아 보여 주고 → 판매자가 웹에서 그 코드를 승인 → PC가 토큰을 받는다. 차이는 **설치 공개키(X25519)를
함께 등록**한다는 점이다 — §5의 토큰 봉인에 쓴다. 공개키는 코드를 요청할 때 보내므로, 판매자가 승인하는 대상이 그 키를
가진 설치이고 나중에 발급되는 토큰도 그 키에 묶인다. 개인키는 PC 밖으로 나가지 않는다.

**구현 (2026-10-17, §11).**

| 경로 | 호출자 | 내용 |
|---|---|---|
| `POST /v1/auth/invites/redeem` {inviteCode, password} | 없음 | 초대 1회 소진 → 계정 생성 → 세션. 비밀번호 10–128자. 이미 있는 주소면 409 |
| `POST /v1/auth/login` {email, password} | 없음 | 세션 JWT(HS256, 12시간). 실패는 이유를 구분하지 않는 `invalid_login`. 주소당 15분에 10회 실패면 429 |
| `POST /v1/auth/logout` · `POST /v1/delegate/auth/logout` | 판매자 세션 · 담당자 세션 | 보낸 그 세션 하나를 서버에서 끝낸다(204). 같은 사람의 다른 세션(휴대폰 · 작업 화면)은 그대로 |
| `POST /v1/installs/code` {deviceName, appVersion?, publicKey} | 없음 | 32바이트 공개키(base64), 10분짜리 장치 코드 · 8자 사용자 코드. 대기 상한은 주소마다 5개(여섯 번째가 그 주소의 가장 오래된 것을 밀어낸다 — 다시 누른 판매자가 거절되지 않는다) · 주소마다 10분에 20번 발급(넘으면 429 `too_many`) · 전체 1,000개(넘으면 503 `busy`). IPv6는 /64 하나를 한 주소로 센다 |
| `POST /v1/installs/token` {deviceCode} | 없음 | `authorization_pending` · `expired_token`(400) 또는 토큰 1회(`rvi_…`, 180일) |
| `POST /v1/installs/pending` {userCode} | 판매자 세션 | 승인 전 조회: `{deviceName, sameNetwork}`. 승인도 소진도 하지 않는다 |
| `POST /v1/installs/step-up` {userCode} | 판매자 세션 | 그 PC 연결 요청용 6자리 코드를 계정 이메일로 보낸다 → `{sentTo(가림), expiresAt}`. 429 `too_many` · `locked`, 503 `mail_off` · `mail_failed` |
| `POST /v1/installs/step-up/verify` {userCode, code} | 판매자 세션 | 같은 세션 · 같은 요청의 코드 확인(204). 400 `wrong_code`+`left`, 410 `expired`, 429 `locked` |
| `POST /v1/installs/approve` {userCode} | 판매자 세션 | 확인된 코드를 한 번 써서 승인하고 장치 이름을 돌려준다. 코드 없이는 403 `step_up_required`. 승인 뒤 새 PC 알림 메일 |
| `GET /link?code=…` | 없음 | 승인 화면(정적 페이지, 아래) |
| `GET /v1/installs` · `DELETE /v1/installs/{id}` | 판매자 세션 | 자기 계정의 PC 목록 · 분실 PC 회수. 다른 계정의 PC는 없는 것과 같은 404 |
| `GET /v1/installs/me` · `DELETE /v1/installs/me` | 설치 토큰 | 자기 행 조회 · 스스로 연결 해제 |
| `GET /v1/ip` | 설치 토큰 | §7 |

- 저장: 초대 코드 · 설치 토큰은 SHA-256, 비밀번호는 BCrypt(12)만 저장한다. 대기 중인 장치 승인은 메모리에만 둔다(서버
  1개 프로세스, 재시작하면 판매자가 한 번 더 누른다).
- 세션 JWT는 그것만으로 회수할 수 없으므로 **매 요청에서 계정 상태를 다시 읽는다** — 정지는 다음 요청부터 세션과 설치
  토큰을 함께 끊고, 정지를 풀면 같은 설치들이 되살아난다(행을 지우지 않는다).
- **세션 회수 (2026-10-22, V6).** 세션마다 고유 ID(`jti`)와 밀리초 발급 시각(`iat_ms`)을 싣고, 둘 중 하나라도 없는
  토큰은 세션이 아니다. 매 요청에서 둘을 본다: 로그아웃한 그 세션(`revoked_sessions`, 원래 만료 시각이 지나면 지운다)과,
  운영 명령 `end-sessions <email>`이 적는 사람별 `sessions_not_before` — 그 시각까지 발급된 그 사람의 세션 전부(판매자이자
  담당자인 주소면 둘 다)가 다음 요청부터 401이다. 유출된 토큰 · 잃어버린 휴대폰용이고, 정지와 달리 계정과 PC 설치는
  그대로라 다시 로그인하면 된다. 같은 밀리초에 발급된 세션은 끝내는 쪽으로 판단한다. 두 화면의 「로그아웃」은 이
  경로를 부른 뒤 응답과 상관없이 페이지에서도 지운다.
- 잘못된 bearer는 어느 경로에서든 401로 끝난다. 다른 규칙이 받아 주는지 시험하지 않는다.
- 초대 · 정지 · 복구 · 세션 끝내기는 관리자 화면이 생기기 전까지 서버 호스트의 운영 명령이다:
  `java -jar vendor-server.jar invite|suspend|reinstate|end-sessions <email>`. 초대 코드는 그 터미널에 한 번만 출력된다(7일 유효).
  판매자 초대도 담당자처럼 **가입 화면 링크**로 출력한다(`/join#코드`, 2026-10-22 — 코드는 주소의 `#` 뒤라 서버 로그에
  남지 않는다).
- **판매자 가입 화면 `GET /join`** (2026-10-22 시안 확인 · 보완 조건). 비밀번호를 정하기 **전에** 그 초대가 만들 계정의
  주소를 보여 준다(`POST /v1/auth/invites/peek {inviteCode}` → `{email}`, 쓴 · 지난 · 모르는 코드는 400 `invalid_invite`
  하나). 내 계정이 아니면 가입하지 말라고 적는다. 가입(`redeem`) 응답은 세션과 함께 휴대폰 승인 화면 주소와 그 QR
  (`phoneUrl` · `phoneQr`, `vendor.public-url`이 있으면 그 주소)을 준다 — 화면은 다음에 할 일 두 가지(PC 연결 · 휴대폰에 승인
  화면 열어 두기)를 보이고, 「이 브라우저에서 승인 화면 열기」는 이 탭의 세션으로 `/replies`를 연다.
  보유 기한 정리(§6)를 손으로 한 번 돌리는 것도 운영 명령이다: `java -jar vendor-server.jar purge`(지운 개수만 출력).
- 세션 서명 키 `VENDOR_SESSION_SECRET`(32자 이상)이 없으면 서버가 시작하지 않는다. 기본값은 없다.
- **PC 쪽 보관.** 설치 토큰과 개인키(PKCS#8)는 PC의 DB(`vendor_install_link`)에 기존 vault 키(`VaultKeyRing`)로 봉인한
  봉투로만 둔다 — 채널 자격 증명과 같은 보호다. vault 키 자체를 OS 비밀 저장소(Keychain · DPAPI)에서 읽는 것은 패키징
  항목이다(proposal §18.7 2). vault 키가 없는 설치에서는 연결 기능이 꺼진다.
- **승인 화면 `/link` (⑧-4 (a)).** 로컬 화면이 `/link?code=XXXXXXXX`를 판매자의 기본 브라우저로 연다. 페이지는 코드를 읽은
  즉시 주소창에서 지우고, 로그인 → 계정 · PC 종류 · 코드 확인 → 「연결 허용」. **코드가 링크로 왔는데 승인하는 브라우저와
  코드를 요청한 PC의 공인 IPv4가 다르면**(다른 네트워크 · IPv6 · 알 수 없음) 페이지는 코드를 보여 주지 않고, PC 화면의
  코드를 직접 입력해야 허용 버튼이 켜진다 — 남의 코드가 담긴 링크를 눌러 공격자의 PC를 자기 계정에 붙이는 피싱(RFC 8628
  §5.4)을 막기 위해서다. 요청 IP는 승인 대기 10분 동안 메모리에만 있다. 페이지는 프레임 안에서 열리지 않고(CSP
  `frame-ancestors 'none'` · `X-Frame-Options DENY`), 스크립트는 같은 출처 파일만, `Referrer-Policy: no-referrer`, 세션은
  페이지 메모리에만 둔다. 거절은 서버에 알리지 않고 코드가 10분 뒤 사라진다.
- 장치 이름은 PC가 정하는 닫힌 값(`macOS (aarch64)` 같은 OS · 아키텍처)이다. 호스트 이름은 소유자 이름을 담는 일이 많아
  보내지 않는다.

**담당자 · 스토어 · 배정 구현 (2026-10-20).** 첫 담당자는 오너 본인이다(2026-10-20 오너 확인: 판매자가 부매니저로
초대하는 사람이 오너이고, 승인된 답글을 판매자센터에 직접 붙여넣는다). 담당자가 판매자센터에 들어가는 네이버 계정은
오너가 따로 만들며 이 서버는 그 계정을 모른다 — 아이디 · 비밀번호 · 스토어 식별자 어느 것도 저장하지 않는다.

| 경로 | 호출자 | 내용 |
|---|---|---|
| `POST /v1/delegate/auth/invites/stage` {inviteCode, password} | 없음 | 초대를 **소진하지 않고** 비밀번호와 새 TOTP 비밀을 초대에 올려 둔다 → `{secret(base32), otpauthUri, qr}`. `qr`은 같은 URI를 QR 모듈 행(`"0101…"`)으로 담은 것 — 화면이 CSP `'self'` 안에서 그리기만 하도록 서버가 인코딩한다(ZXing core, `OtpQr`). 다시 부르면 셋 다 바뀐다(QR 화면을 놓친 경우) |
| `POST /v1/delegate/auth/invites/confirm` {inviteCode, otp} | 없음 | 인증 앱의 첫 코드가 맞을 때만 초대 소진 → 담당자 생성 → 세션 + 복구 코드 10개(한 번만 표시). 틀리면 아무것도 바뀌지 않음 |
| `POST /v1/delegate/auth/login` {email, password, otp 또는 recoveryCode} | 없음 | 둘째 요소는 정확히 하나. 실패는 이유를 구분하지 않는 `invalid_login`, 판매자와 같은 15분 10회 제한(키는 따로) |
| `GET /v1/delegate/me` | 담당자 세션 | 이메일 · 역할 · 남은 복구 코드 수 · 지금 배정된 스토어 |
| `GET /v1/stores` | 판매자 세션 · 설치 토큰 | 자기 계정의 스토어 |

- TOTP: RFC 6238(SHA-1 · 30초 · 6자리, 앞뒤 한 칸 허용). **같은 30초 칸의 코드는 한 번만** 받는다(`totp_last_step`).
  TOTP 비밀은 확인하려면 읽어야 하므로 해시가 아니라 `VENDOR_TOTP_KEY`(base64 32바이트, 세션 키와 별개, 없으면 서버가
  시작하지 않음)로 AES-256-GCM 봉인해 둔다. 복구 코드는 SHA-256만 저장한다.
- 세션 JWT의 `typ`이 `seller` · `delegate`를 가른다. 담당자 세션은 판매자 · 설치 경로를, 판매자 세션 · 설치 토큰은
  담당자 경로를 열지 못한다. 담당자 상태도 매 요청 다시 읽는다.
- 스토어 행은 판매자 계정 · 채널(`NAVER`) · 운영자가 붙인 라벨만 가진다. 배정은 끝낼 때 지우지 않고 `ended_at`을 남긴다.
  담당자 정지는 세션과 **모든 배정**을 끊고, 복구는 계정만 되살린다(배정은 다시 준다). 착수한 작업은 `UNKNOWN`이 되고,
  운영자가 확인해 종결한다(§4.3 운영자 확인 종결).
- 관리 화면 전까지 운영 명령: `invite-delegate <email> [admin]` · `suspend-delegate` · `reinstate-delegate <email>` ·
  `add-store <판매자 email> <라벨>` · `assign` · `unassign <담당자 email> <store-id>` · `checklist` · `check-owner` ·
  `check-assignment` · `recover-seller <email> [새 email]` · `installs <판매자 email>` · `revoke-install <판매자 email> <id>`.
- **스토어 확인 절차(2026-10-22 외부 검토 — 외부 판매자의 자료를 받기 전 필수, V9).** 운영자가 스토어를 만들고 담당자를
  배정해도 그 배정은 **확인 전에는 아무 일도 하지 않는다** — 담당자의 스토어 목록 · 업로드 · 작업 어디에도 나오지 않고,
  업로드는 배정 없음과 같은 404다. 관리자(ADMIN, 활동 중) 담당자가 두 가지를 확인해 남겨야 열린다.
  1. **판매자 소유** — `check-owner <store-id> seller-center-screen|submanager-invite <admin-email>`. 이 스토어가 그 판매자
     계정 주인의 것인지. 근거는 닫힌 말 둘: 판매자가 판매자센터에 로그인한 화면에서 이 스토어를 직접 보여 줌
     (`seller-center-screen`), 판매자 계정 주소로 판매자에게 이 스토어의 부매니저 초대를 보낸 사람임을 확인함
     (`submanager-invite`). 근거 목록은 처음 것이며 오너가 바꿀 수 있다.
  2. **담당자 배정** — `check-assignment <담당자 email> <store-id> <admin-email>`. 배정된 그 담당자 **본인의** 네이버
     계정이 판매자센터에서 이 스토어의 부매니저로 들어가 있는지. 배정마다 따로이고, 배정을 끝냈다가 다시 하면 새 행이라
     다시 확인한다(담당자 정지 · 복구도 같다).
  누가(`owner_checked_by` · `checked_by`) · 언제 · 무엇을 보고(`owner_check_basis`) 확인했는지 남고, 한 번 남긴 확인은
  덮어쓰지 않는다. `checklist`는 스토어마다 두 질문과 남은 것, 확인한 사람 · 시각을 출력한다(리뷰는 출력하지 않음).
  확인하는 관리자와 배정된 담당자가 같은 사람이어도 된다 — 파일럿에서 오너가 첫 담당자이기 때문이다.
- **판매자 추가 인증 — 이메일 일회용 코드 (2026-10-22 외부 검토 권고 · 오너 동의, 구현 V10).**
  - **막으려는 것.** 판매자 비밀번호만 가진 사람이 자기 PC를 그 계정에 붙여, 구매자 리뷰 전체(나중에는 Cafe24 토큰까지)를
    180일 동안 받아 가는 것. `/link`의 같은 네트워크 판별은 링크로 건네진 남의 코드(피싱)만 막는다.
  - **원칙.** 가입과 로그인은 비밀번호 하나. 추가 인증은 **계정 밖으로 나가는 새 통로를 여는 동작**에만 묻는다.

    | 동작 | 추가 인증 | 이유 |
    |---|---|---|
    | 새 PC 연결 허용(`POST /v1/installs/approve`) | **필요(구현)** | 180일 토큰이 그 계정의 모든 리뷰를 받는다 |
    | 앞으로 생길 비밀번호 · 이메일 변경, 결제 정보, Cafe24 중계 등록 | 필요(그 기능을 만들 때) | 계정 탈취이거나 새 통로 |
    | 로그인, 답글 승인 · 문장 수정 · 취소 | 아니오 | 답글마다 반복 요구하지 않는다. 답글은 담당자가 손으로 올리고 결과가 남는다 |
    | PC 연결 끊기 · 로그아웃 | 아니오 | 끊는 동작에는 마찰을 두지 않는다 |

  - **흐름.** `/link`에서 「연결 허용」 → `POST /v1/installs/step-up {userCode}`가 계정 이메일로 6자리 코드를 보낸다(응답은
    가린 주소 `se***@example.com`과 만료 시각) → 같은 화면에 코드를 넣으면 `POST /v1/installs/step-up/verify {userCode, code}`
    (204) → 이어서 승인. 코드 없이 승인하면 403 `step_up_required`. 메일에는 코드와 PC 종류만 싣고 링크는 없다.
  - **묶임 · 한 번만(검토 조건).** 코드는 **그 계정 · 그 세션(`jti`) · 그 PC 연결 요청(사용자 코드의 해시)** 하나에 묶인다.
    맞힌 코드는 그 요청의 승인 **한 번**에 쓰이고 끝난다(`spent_at`). 다른 세션, 다른 PC의 승인에는 쓰이지 않는다 — "10분 동안
    어떤 PC든"은 없다. 맞힌 뒤 10분 안에 승인해야 한다.
  - **횟수(검토 조건).** 다시 받아도 틀린 횟수는 줄지 않는다 — 같은 요청의 모든 코드를 더해 5번이면 그 요청은 막히고(429
    `locked`, PC에서 새로 시작), 계정 전체로 한 시간에 10번 틀리면 모든 요청이 막힌다. 발급은 요청당 3번 · 계정당 한 시간에
    10번(429 `too_many`). 새로 받으면 이전 코드는 끝난다. 코드는 해시만 두고, 하루 지난 행은 정리 작업(§6)이 지운다.
  - **이메일 소유의 기록(검토 조건).** 초대 링크를 받았다는 것은 주소 소유의 증거가 아니다 — 운영자가 링크를 출력해 직접
    전한다. 그 주소로 보낸 코드를 **처음 맞힌 시각**이 `seller_accounts.email_verified_at`에 남는다.
  - **한계(명시).** 이메일 코드는 파일럿용 추가 확인이지 강한 인증이 아니다. 메일함까지 가진 사람, 코드를 중계하는 피싱
    화면은 막지 못한다(OWASP Multifactor Authentication Cheat Sheet, "Email"). 외부 파일럿을 넓힐 때 패스키를 다시 본다.
  - **메일 설정.** `VENDOR_MAIL_MODE` = `smtp`(`SPRING_MAIL_HOST` 등 없으면 서버가 시작하지 않음) · `dev-outbox`(로컬 실행
    전용 — 코드까지 로그에 씀) · `off`(기본 — 아무것도 보내지 않으므로 **새 PC를 연결할 수 없다**, 503 `mail_off`).
    `VENDOR_MAIL_FROM` · `VENDOR_MAIL_REPLY_TO`(새 PC 알림에 답장하면 운영자에게). 백엔드 메일러와 같은 모양.
  - **새 PC 알림(오너 결정 2: 보냄).** 승인되면 계정 이메일로 시각(한국 시간) · PC 종류 · "직접 연결하지 않았다면 운영자에게
    알려 주세요"를 보낸다. **누르기만 하면 끊기는 링크는 넣지 않는다**(검토 조건 — 메일은 전달 · 미리보기 검사기가 열 수
    있다). 판매자가 휴대폰에서 직접 PC를 끊는 화면은 아직 없다(시안 필요) — 지금은 운영자가 `installs <판매자 email>`로
    보고 `revoke-install <판매자 email> <install-id>`로 끊는다.
  - **이미 연결된 PC(오너 결정 3).** 확인된 내부 장치만 유지한다. 실제 목록은 `installs`로 보고, 소유자가 불명확한 PC는
    `revoke-install` 후 다시 연결(이제 이메일 코드를 거친다). 운영 서버는 아직 배포 전이라 지금 조회할 목록이 없다.
- **계정 복구 (2026-10-22 검토 — "재초대"안 정정).** 초대는 이미 계정이 있는 주소로는 가입되지 않는다(409
  `already_registered`). 그래서 이메일 · 비밀번호를 잃은 판매자는 다시 초대하지 않는다. 운영자가 서버 밖에서 본인을 확인한
  뒤 `recover-seller <판매자 email> [새 email]` → **기존 계정에 묶인 복구 초대**(`seller_invites.account_id`)를 링크로 출력하고,
  그 계정의 PC 목록을 함께 보인다. 판매자가 `/join` 링크를 열면 화면이 「계정 복구」로 바뀌고(`peek`의 `recovery: true`), 새
  비밀번호를 정하면 **같은 계정**의 비밀번호(와 새 주소)가 바뀌고 그 순간 전에 발급된 세션이 모두 끝난다. 스토어 · 작업 ·
  기록 · PC 연결은 그대로다(운영자가 PC를 따로 검토). 주소가 바뀌면 `email_verified_at`을 비워, 새 주소가 코드로 스스로를
  증명할 때까지 확인되지 않은 것으로 둔다. 다른 계정이 쓰는 주소로는 옮기지 않는다.
- **담당자 초대는 링크로 출력한다(2026-10-21 오너 확인).** 초대 코드는 43자라 손으로 칠 수 없다. `invite-delegate`는
  `<VENDOR_PUBLIC_URL>/delegate/join#<코드>`를 그 터미널에 한 번 출력하고, 오너가 그 링크를 담당자에게 직접 전한다. 코드는
  fragment(`#` 뒤)에 있어 브라우저가 어느 서버에도 보내지 않고, 화면이 읽자마자 주소창에서 지운다. `VENDOR_PUBLIC_URL`이
  없으면 경로만 출력한다. 담당자 초대는 결제 같은 외부 사건으로 자동 발급하지 않는다 — 배정된 스토어의 리뷰를 모두 보는
  계정이기 때문이다. 판매자 초대도 링크로 출력한다(위, `/join#코드`). 결제(§8)를 붙일 때 판매자 가입 링크의 자동 발송을 함께 정한다.

## 3. 리뷰 교환

### 3.1 반입 — 담당자 업로드

`POST /v1/delegate/stores/{storeId}/review-uploads` (multipart, xlsx, 최대 10MB — 기존 업로드 한도와 같음)

1. 파일을 격리 경로에 쓰고 xlsx 형식을 확인한다(collector `sniffXlsxReadable`와 같은 검사).
2. 머리글을 `contracts/review-export/naver/v1`의 25개 열과 대조한다. 계약에 없는 열이 있으면 반입하지 않고
   담당자에게 알린다(조용히 무시하지 않는다 — 화면 변경을 놓치지 않기 위해).
3. **허용 열만 읽는다.** 아래 표의 열만 행 객체로 만든다. 나머지 열은 메모리에도 행 객체로 올리지 않는다.
4. `(storeId, 리뷰글번호)`로 중복을 거른다. 같은 번호에 본문 · 수정일이 바뀌었으면 새 리뷰가 아니라 **변경 사건**이다(§4.2 무효화).
5. 성공하면 원본 파일을 즉시 지운다. 실패하면 격리에 두고 `quarantine_until = 업로드 + 24h`에 정리 작업이 지운다.

| 저장(허용) | 원본 열 | 저장 안 함 | 원본 열 |
|---|---|---|---|
| 리뷰 번호 | 리뷰글번호 | 구매자 | 등록자 |

**실제 파일의 구조 확인 (2026-10-17).** 오너가 판매자센터에서 평소처럼 내려받은 실제 파일 하나를 보고 구조만
알려 주었다. 내용은 저장소에 넣지 않았다.

| 항목 | 확인 결과 |
|---|---|
| 열 | 합성 계약 `contracts/review-export/naver/v1`의 25열과 **이름 · 순서가 같다**. 첨부 · 답글 본문 · 옵션 열은 따로 없다 |
| 리뷰 첨부 | `포토/영상` 열에 **이미지 주소 1개가 텍스트로** 들어 있다(삽입 이미지 아님). 주소 모양: `https://phinf.pstatic.net/checkout.phinf/{날짜_번호}/{식별자}_JPEG/{원본 파일명}` |
| 여러 장인 리뷰 | 2장짜리 리뷰도 주소는 **1개**만 나오고, 판매자센터 화면의 **첫 번째 첨부**다 — 네이버 FAQ("엑셀은 첨부 1개만 조회")의 뜻이 이것이다 |
| 접근 | 로그인 없이 열린다. 6개월 전 리뷰의 사진도 열렸다 |
| 기존 답글 본문 · 상품 옵션 | 파일에 없다 |
| 동영상 첨부 | 동영상 자체가 아니라 **jpg 정지 이미지 주소**로 실린다. 같은 호스트의 다른 경로: `https://phinf.pstatic.net/image.nmv/{업로드 묶음}/{식별자}.jpg` (사진은 `checkout.phinf/…`) |

설계에 미치는 것:

1. **서버는 사진 파일이 아니라 주소 문자열만 저장한다.** 로그인 없이 계속 열리므로 담당자가 그림을 따로 올릴 필요가
   없다. 판매자 PC · 휴대폰은 그 주소로 바로 보여 준다. 주소 호스트는 반입 때 `phinf.pstatic.net`인지 확인하고, 다른
   호스트면 저장하지 않고 담당자에게 알린다. 경로가 `image.nmv/`면 "동영상의 정지 이미지"로 표시한다 — 관측한 모양이며
   네이버가 보장한 규칙은 아니므로, 모르는 경로는 그냥 "첨부 이미지"로 표시한다.
2. **"로그인 없이 열림"은 "공개 자료"가 아니다.** 주소를 아는 사람은 누구나 볼 수 있으므로 주소 자체가 열쇠다. 리뷰
   원문과 같은 보유 기준(§6)을 따르고, 로그 · 오류 추적에 남기지 않는다. 우리 사본을 지워도 네이버의 원본은 남는다 —
   우리가 지울 수 있는 것은 우리 사본뿐이다.
3. **나머지 첨부와 동영상 내용은 엑셀로 확보할 수 없다.** 첨부가 몇 장인지도 파일로는 알 수 없으므로, 화면에는 "엑셀에는
   첫 번째 첨부 1개만 실립니다 — 다른 사진과 동영상은 판매자센터에서 확인"이라고 밝힌다. 전부 봤다고 표시하지 않는다.
   AI도 동영상은 정지 이미지 한 장만 본다는 전제로 판단한다.
4. **AI로 보낼 때.** 사진에는 얼굴 · 송장 · 주소가 찍힐 수 있다. 사진을 AI에 넣으려면 §17.9의 사진 검사 경계(정제 ·
   불확실하면 보류)를 먼저 거친다. 판매자 PC가 이 주소를 내려받으려면 `OutboundGate`에 리뷰 첨부용 목적지를 새로
   정의한다 — 지금의 `PRODUCT_IMAGE`(상품 이미지)에 끼워 넣지 않는다 [REPO]. 방향(2026-10-17, proposal §18.7 "리뷰
   사진"): 리뷰 사진 분석은 살리되 **담당자가 반입 때 확인한 전송용 사본**만 AI로 보내고, 지금의 일괄 보류는 그 경로가
   생길 때까지의 임시 조치다. 담당자 확인은 이 반입 단계(§3.1)에서 한다.
5. **기존 답글 본문은 파일에 없으므로** 담당자는 등록 직전에 판매자센터 화면에서 기존 답글을 확인한다(§4.3).

판매자가 자기 판매자센터에서 직접 파일을 내려받는 것은 평소 판매자 업무다. 라이브 승인 정본
(`docs/standing/sellerops_live_approval_contract.md`)은 SellerOps · Claude가 실계정에 접근하는 실행에 적용된다.

본문 지문은 `contracts/review-fingerprint/v1`(Java `ReviewBodyFingerprint`)을, 리뷰 식별 지문은
`contracts/review-id-fingerprint/v1`을 그대로 쓴다 — PC와 서버가 같은 값을 계산한다.

### 3.2 PC로 전달

- `GET /v1/stores/{storeId}/reviews?cursor=` (설치 토큰) → 새 리뷰와 변경 사건. 원문 그대로다(§17.9: 판매자에게는 원문).
- `POST /v1/stores/{storeId}/reviews/ack {cursor}` → PC가 로컬 DB에 저장했음을 확인한다.
- `POST /v1/stores/{storeId}/reviews/{reviewId}/disposition {noReplyNeeded: true, commandId}` → PC(또는 판매자)가 이 리뷰에
  답글이 필요 없다고 판정했음을 알린다. 저장 확인과 이 판정이 둘 다 있어야 D4의 90일이 시작된다. 판정 없이 저장만 된
  리뷰는 진행 중 자료로 남아 정리 안내 대상이 된다.

PC는 받은 리뷰를 기존 리뷰 레인(`reviews` 테이블, `external_id` = 리뷰글번호)으로 반입한다. AI로 보낼 때는 §17.9의
로컬 정제를 거친다 — 서버는 정제본을 만들지 않는다.

**구현 (2026-10-20, 서버 쪽).** 위 절차와 다른 점과 정한 점:

- **파일을 디스크에 쓰지 않는다.** 메모리에서 읽고 버린다 — 1 · 5단계의 격리 경로와 24시간 보관을 두지 않았다.
  컨테이너도 쓰지 않는다: multipart의 디스크 전환 기준(`file-size-threshold`)을 요청 상한(12MB)보다 큰 13MB로 둔다.
  기본값 0바이트면 Tomcat이 모든 파일 부분을 임시 폴더에 먼저 쓴다(2026-10-22 외부 점검 지적 · 재현).
  `UploadStaysInMemoryTest`가 실제 Tomcat에서 가장 큰 허용 파일을 받는 도중 그 임시 폴더를 들여다본다 — 0바이트로
  되돌리면 실패한다. 실패한
  파일은 담당자 PC에 그대로 있으므로 서버가 보관할 이유가 없고, 보관하지 않으면 지울 것도 없다. 실패 응답이 고칠 것을
  말한다: `not_xlsx`(400) · `header_mismatch {missing, unexpected}`(422, 25열과 이름이 다르거나 중복 · 순서는 무관) ·
  `invalid_rows {rows(시트 행 번호, 최대 20개), rowCount}`(422, 리뷰글번호 · 평점 1–5 · 등록일 · Y/N 답글 여부 · 시각
  형식 · 같은 번호 반복). 한 줄이라도 틀리면 아무것도 반입하지 않는다.
- **사건은 셋**: `NEW` · `CHANGED`(본문 · 평점 · 시각 · 전시 상태 · 첨부 · 상품 · 관련 리뷰가 달라짐, 답글 Y→N 포함) ·
  `REPLIED`(답글 여부 N→Y — §4.2 무효화의 근거). 같은 내용은 사건이 없다. **다음 업로드에 없다고 삭제로 보지 않는다** —
  내보내기 기간은 담당자가 고르므로 빠졌다는 것은 아무것도 증명하지 않는다. 삭제 · 숨김은 `전시상태`로만 안다.
- 첨부: `https://phinf.pstatic.net/…`만 저장하고 나머지는 저장하지 않고 업로드 응답의 `attachmentsDropped`로 센다.
  경로로 `PHOTO`(`/checkout.phinf/`) · `VIDEO_STILL`(`/image.nmv/`) · `IMAGE`(그 밖).
- 본문 지문은 backend `ReviewBodyFingerprint`를 이 빌드로 옮긴 것이고 계약의 golden vector 전부로 묶었다.
- 응답 시각은 판매자센터 시각(한국 시간)을 UTC로 바꾼 것이다.
- `GET …/reviews?cursor=&limit=`(최대 200) → `{events: [{seq, kind, review}], cursor, more}`. `ack {cursor}`는 그 매장의
  실제 사건 번호여야 하고 PC별 확인 위치를 뒤로 돌리지 않는다. D4의 90일은 PC 저장과 '대응 불필요'가 둘 다 있을 때 늦은
  쪽부터 한 번만 정해진다(`purge_after`). 이 값으로 실제로 지우는 정리 작업은 §6(2026-10-22 구현)이다.

**PC 쪽 반입 구현 (2026-10-21, backend `vendorlink/VendorReviewPullService`).**

- **어느 조직으로 들어가나.** 서버 스토어 하나를 이 PC의 조직 하나에 묶는다(`vendor_store_binding`, V136). 묶음은 판매자가
  「리뷰 받기 시작」(`POST /api/local/vendor-link/reviews/start {storeIds}`)을 누를 때만, **그 화면에 보인 스토어만**, 그
  판매자의 조직으로 생긴다(2026-10-22 보완 조건 — 처음에는 「지금 받기」가 아직 묶이지 않은 스토어를 모두 묶었다). 「지금
  받기」(`…/reviews/pull`)와 5분마다 도는 자동 받기(`sellerops.vendor-link.review-pull.enabled`, `local-seller` 프로필에서
  켜짐)는 묶인 스토어만 따르고 아무것도 묶지 않는다. 운영자가 나중에 만든 스토어는 「아직 받지 않음」으로 보이고 같은 방법으로
  시작해야 받는다. 다른 조직에 묶인 스토어는 그 조직의 판매자만 받는다.
- **스토어별 멈춤 · 실패 · 두 시각** (V139). 스토어마다 「받기 멈추기」 · 「다시 받기」(`…/reviews/stores/{id}/pause|resume`)
  — 멈춘 스토어는 **새 리뷰를 묻지 않는다**. 이미 맡긴 답글의 상태(휴대폰 승인 · 담당자 등록)와 판매자의 「답글 불필요」
  보고는 멈춘 동안에도 계속 따른다(2026-10-22 외부 검토 — 처음에는 멈춤이 이것까지 막아 PC에 이전 상태가 남았다). 마지막 받기가 그 스토어에서 실패하면 이유(서버에 닿지 않음 · 요청 거절 ·
  일부 저장 못 함)와 시각을 그 스토어에 남기고, 다음에 성공하면 지운다. 화면은 **PC가 서버에 마지막으로 물어본 때**와
  **담당자가 마지막으로 엑셀을 올린 때**(서버 `GET /v1/stores`의 `lastUploadAt`)를 따로 보인다 — 방금 물어봤어도 담당자가
  오래된 파일만 올렸다면 최신 리뷰가 아니다. `GET …/reviews/overview`는 서버의 판매자 계정 주소(`GET /v1/installs/me`의
  `accountEmail`)와 이 PC의 작업 계정 이름, 스토어 목록을 준다. 서버에 닿지 않거나 거절되면 이 조직이 묶어 둔 스토어를
  마지막으로 본 대로 보인다. 열린 화면은 1분마다(서버에 닿지 않는 동안은 15초마다), 그리고 탭으로 돌아올 때 다시 읽는다.
  읽기가 실패하면 구역을 숨기지 않고 「다시 확인」과 함께 알린다.
- **사건마다 리뷰를 지금 상태로 맞춘다.** 이 PC에 없는 리뷰는 기존 수집 경로(`IngestionService`, 리뷰글번호 = `external_id`)로
  들어간다. 이미 있는 리뷰는 본문 · 평점을 서버 값으로 고치고, 답글 여부는 앞으로만 움직인다(레인 규칙: 답글 있음을 없음으로
  되돌리지 않는다). 서버의 리뷰 ID · 본문 지문 · 전시 상태 · 첨부 주소 1개는 레인에 칸이 없어 `vendor_review_ref`에 둔다 —
  답글 작업을 낼 때(§4.3) 앞의 둘이 필요하다. 같은 서버 리뷰가 다른 리뷰글번호로 오면 저장하지 않는다.
- **커서는 저장한 데까지만.** 사건 하나가 실패하면 그 앞에서 멈추고 다음 받기가 거기서 다시 시작한다. 같은 사건을 다시 적용해도
  같은 상태가 될 뿐이다. 커서를 저장한 뒤 서버에 `ack`(최선 노력 — 놓치면 다음 받기가 다시 보낸다). 서버가 받았다고
  답한 위치는 커서와 따로 둔다(`vendor_store_binding.acked_cursor`, V138). 그래서 놓친 `ack`는 새 리뷰가 없는 다음
  받기에서도 다시 간다 — 이 알림이 서버 보관 기한(§6)의 시작이라 새 리뷰가 올 때까지 미뤄지면 안 된다.
- **수집 기록.** 받기마다 `sync_jobs` 한 행(`method=VENDOR_RELAY`, `dataType` 없음)과 새 리뷰의 `acquisition_sync_job_id`.
  `VENDOR_RELAY`는 최신성으로 세지 않고(파일의 나이는 담당자의 것이다) 실행 가능한 신원도 아니다(답글은 이 PC가 아니라
  담당자가 올린다).

```text
AWAITING_APPROVAL ──승인──▶ APPROVED ──착수──▶ CLAIMED ──보고──▶ POSTED · FAILED · UNKNOWN
   │   ▲                      │                  │
   │   └─휴대폰 수정(새 버전)   │취소               │취소 요청
   │                          ▼                  ▼
   ├─정책 지문 다름─▶ RECHECK_NEEDED            CANCEL_REQUESTED ──담당자 확인──▶ CANCELLED · POSTED
   ├─취소─▶ CANCELLED      CANCELLED
   └─리뷰 변경 · 삭제 · 이미 답글─▶ INVALIDATED   (APPROVED · HELD에서도 같은 사건이면 INVALIDATED)

APPROVED ──PC: 승인된 문장이 지금 근거와 실질적으로 충돌──▶ HELD ──새 버전(휴대폰 · PC)──▶ RECHECK_NEEDED · AWAITING_APPROVAL
CLAIMED  ──같은 판정──▶ HOLD_REQUESTED ──담당자 「등록 안 했음」 · 반납──▶ HELD   (등록했음 → POSTED, 모름 → UNKNOWN)

APPROVED(PC가 아직 검사하지 않은 휴대폰 버전) ──PC 검사 통과──▶ 담당자 목록에 나타남 · ──PC 검사에서 걸림──▶ HELD
```

- **휴대폰 버전은 PC 검사 전에 담당자에게 가지 않는다(2026-10-23 외부 점검).** 판매자는 PC 검사 전에도 휴대폰에서 승인할 수
  있고 그 승인은 남는다. 다만 그 버전에 대한 PC의 검사(`pc-recheck`)가 기록되기 전까지는 담당자 목록에 나오지 않고, 착수는
  `pc_check_pending`(409)으로 거절되며, 등록 직전 확인도 「등록해도 됨」이 되지 않는다(`ReplyTasks#awaitingPcCheck`). 검사가
  통과하면 판매자가 다시 누를 것 없이 담당자 목록에 나타난다. 검사에서 걸리면(근거에 없는 약속 · 금지 표현) 같은 갱신에서
  `HELD`가 된다 — 판매자가 그 지적을 보기 전에 승인했기 때문이다. 이 규칙 전에 착수된 옛 행은 `HOLD_REQUESTED`가 된다. PC가
  쓴 버전은 보내기 전에 PC가 이미 검사했으므로 기다리지 않는다. PC가 꺼져 있으면 켜질 때까지 기다린다(닫힌 쪽). 휴대폰은
  「승인됨 · PC 검사 기다리는 중」으로 보인다.
- **서버에 반영되지 않은 검사는 검사가 아니다(같은 점검).** PC는 서버가 검사 결과나 보류를 받아들였을 때만 그 버전을
  확인했다고 적는다. 거절(`stale` 등)되면 적지 않고 다음 받기에서 다시 묻는다 — 휴대폰 수정본 · 되돌아온 초안 · 승인된 답글
  모두. 근거가 바뀐 뒤에야 PC가 보게 된 미검사 휴대폰 버전은 승인된 답글 검사에서 그 버전의 첫 검사로 기록한다.

- **취소:** `APPROVED`까지는 즉시 `CANCELLED`. `CLAIMED`에서는 `CANCEL_REQUESTED`가 되고 담당자가 저장 직전에 확인한다.
- **고정 기한 없음(2026-10-17 오너 결정).** 무효화는 사건으로만: 리뷰 변경 · 삭제(다음 반입에서 관측), 이미 답글
  있음(`답글여부=Y`), 판매자 취소, 미승인 건의 정책 지문 변경.
- **승인 보류(2026-10-23 오너 확정, 시안 확인 같은 날).** 근거가 바뀐 뒤 PC가 승인된 문장을 다시 검사해 **실질적 충돌**이
  있으면 `approved-check`로 보류한다 — `APPROVED`는 `HELD`(다시 승인 필요), 담당자가 착수한 `CLAIMED`는 `HOLD_REQUESTED`가
  되어 담당자의 등록 직전 확인이 「등록하지 마세요」와 사유를 보이고, 담당자가 「등록 안 했음 · 보류 확인」을 누르면 착수가
  풀린 채 `HELD`로 판매자에게 돌아간다(결과 기록 없음 — 멈춘 것이지 실패가 아니다). 판매자 화면에만 알리고 실제 등록은 계속되는
  틈은 없다. `HELD`는 새 버전으로만 다시 승인된다(휴대폰 수정은 `RECHECK_NEEDED`를 거쳐 PC 검사를 받는다). 취소는 `HELD` →
  `CANCELLED`, `HOLD_REQUESTED` → `CANCEL_REQUESTED`. 의미 기반 검사(2단계)가 생기기 전까지 「실질적 충돌」은 PC가 증명할 수 있는
  것으로 한정한다: **승인된 문장의 약속(교환 · 환불 …)을 지금 근거가 뒷받침하지 않음**. 인용한 문서가 고쳐지기만 했으면 승인은
  그대로 두고 사유만 남긴다(「이 답글과 부딪히는 곳이 없어 승인을 그대로 둡니다」).
- **보류 사유(`basis_note`, vendor V11).** PC가 남기는 사유는 닫힌 코드 · 바뀐 문서(종류 · 제목 · 고친 때 · 사용 중지) · 근거를 잃은
  약속 낱말 · 그 낱말이 든 답글의 문장이다. 서버는 판정하지 않고 형식 · 길이와 **인용한 문장이 그 작업의 문장 안에 실제로 있는지**만
  확인한다. 새 버전이 생기면 지운다. 판매자 PC · 휴대폰 · 담당자 화면이 같은 사유를 보인다.
- **정책 재확인:** PC가 켜지면 `POST /v1/stores/{storeId}/tasks/policy-check {policy_fp, knowledge_fp, voice_fp}`.
  서버는 `AWAITING_APPROVAL` 중 지문이 다른 건을 `RECHECK_NEEDED`로 돌리고 목록을 돌려준다. `APPROVED`는 판매자의
  결정이라 상태를 바꾸지 않고 응답에 "철회 제안" 목록으로만 담는다. `CLAIMED` 이후는 건드리지 않는다.
- **`UNKNOWN`:** 담당자가 확인할 때까지 재등록하지 않는다. 다음 반입에서 `답글여부=Y`가 보이면 담당자가 확인해
  `POSTED`로 고친다.
- **증거 등급:** PC에 반영할 때 `POSTED`는 기존 쌍 `OPERATOR_REPORTED_SUBMITTED` + `UNVERIFIED`로만 기록한다(v1.14 ⑨,
  `attention/reply/OperatorOutcome`). `COMPLETED`는 쓰지 않는다. 다음 반입의 `답글여부=Y`를 별도 증거 등급으로
  올릴지는 [PO] — 이 계약에서 새 등급을 만들지 않는다.

담당자 화면은 승인된 문장을 복사하는 것까지만 돕는다. 판매자센터에 대신 입력하거나 저장하지 않는다(§17.6).

**구현 (2026-10-20, 서버 쪽).** 위 표대로이고, 정한 점:

- **한 리뷰에 열린 작업은 하나**(`open_review_id` 유일). 두 PC가 동시에 초안을 내면 하나만 열리고 다른 쪽은
  `409 task_in_progress`. 같은 초안을 다시 내면 버전이 오르지 않는다. 승인 · 착수 이후에는 새 초안을 받지 않는다
  (`task_in_progress`) — 바꾸려면 판매자가 먼저 취소한다. 이미 `POSTED`인 리뷰(`already_posted`)와 채널이 답글 있음이라
  말하는 리뷰(`already_replied`)에는 작업을 열지 않는다. 초안의 `reviewBodyFingerprint`가 서버의 현재 본문 지문과
  다르면 `review_changed`.
- **승인은 버전 + 지문에 묶인다.** 담당자의 `POSTED` 보고도 승인된 지문과 같아야 한다(`fingerprint_mismatch`) —
  담당자가 문장을 고쳐 올리는 경로는 없다. 보고 결과는 `POSTED` · `FAILED` · `UNKNOWN`, 방법은
  `SELLER_CENTER_SCREEN`(판매자센터 화면에서 직접 확인) 하나. `CANCEL_REQUESTED`에서 `FAILED`(올리지 않음)는
  `CANCELLED`로 끝난다. `UNKNOWN`은 같은 담당자가 나중에 `POSTED` · `FAILED`로 확정할 수 있고, 그 전에는 같은 리뷰에
  새 작업이 열리지 않는다.
- **무효화**: 업로드에서 본문 · 전시 상태가 바뀌거나 답글 여부가 N→Y가 되면 `AWAITING_APPROVAL` · `RECHECK_NEEDED` ·
  `APPROVED` 작업은 `INVALIDATED`. 착수한 작업은 건드리지 않고, 담당자 `preflight`가 `reviewChanged` ·
  `displayChanged` · `alreadyReplied`로 알리며 `clearToPost=false`가 된다. 전시 상태는 작업이 열릴 때의 값을
  작업에 적어 두고(`review_display_state`) 그 값과 비교한다 — 숨김 · 삭제는 `전시상태`로만 보이기 때문이다.
- **담당자 정지** 시 그 사람이 착수한 작업(`CLAIMED` · `CANCEL_REQUESTED`)은 `UNKNOWN`.
- **운영자 확인 종결** (2026-10-22 결정 — 정지된 계정은 그대로 막고 운영자가 확인 후 종결). 정지된 담당자의 `UNKNOWN`은 그
  담당자가 다시 들어오지 않는 한 아무도 확정할 수 없었다. 이제 관리자(ADMIN) 담당자가 판매자센터에서 실제 등록 여부와
  문장을 본 뒤 운영 명령으로 종결한다: `in-doubt`(정지된 담당자의 `UNKNOWN` 목록 — 스토어 · 리뷰번호 · 승인된 문장, 리뷰
  원문은 출력하지 않음) → `settle <task-id> posted|not-posted <admin-email>`. `posted`는 승인된 문장이 **글자 그대로** 있을
  때만이고 `POSTED`(지문 = 승인 지문)로, `not-posted`는 우리 답글이 없을 때 `FAILED`로 끝나 리뷰가 다시 열린다. 다른 문장이
  있거나 확신할 수 없으면 종결하지 않는다 — `UNKNOWN`으로 남고 그 리뷰에 새 답글이 나가지 않는다. 누가(`settled_by`, V8) ·
  언제(`reported_at`) · 무엇을 보고(`report_method=OPERATOR_SELLER_CENTER_SCREEN`) 종결했는지 작업에 남는다. 담당자가 아직
  활동 중인 `UNKNOWN`은 그 담당자의 몫이라 운영자가 종결할 수 없다. 판매자는 PC · 휴대폰에서 「담당자가 확인 중」을 본다.
  판매자가 휴대폰에서 직접 확인을 요청하는 단추는 화면 시안이 필요해 아직 없다.
- 착수하지 않은 담당자에게 남의 스토어 작업은 없는 것과 같은 404, 다른 담당자가 착수한 작업은 403.
- `RECHECK_NEEDED`는 바로 승인할 수 없다 — PC가 지금의 지문으로 초안을 다시 내야(`AWAITING_APPROVAL`, 새 버전) 승인된다.
  **문장 수정은 재검증이 아니다:** 휴대폰 · PC의 `PUT …/draft`는 새 버전을 만들어도 `RECHECK_NEEDED`를 그대로 둔다.
  서버는 스토어마다 마지막 `policy-check` 지문을 적어 두고(`store_draft_policies`), 그와 다른 지문의 초안은 새로 내든
  고쳐 쓰든 `RECHECK_NEEDED`로 들어가며, 승인 시점에도 다시 비교한다(`409 policy_changed`).
- 서버 검사(`serverChecks`)는 연락처 · 이메일 · 링크 표시뿐이고 승인을 막지 않는다. 답글 지문 · 정규화는 backend
  `ReviewReplyFingerprint` · `ReviewReplyValidation`을 옮긴 것이고, backend 클래스로 계산한 값으로 테스트를 묶었다.
  본문 상한 4,000바이트는 backend와 같은 저장 상한이고 네이버의 한도가 아니다.
- 모든 상태 변경은 `reply_task_changes`에 순서대로 남고 PC가 `tasks/changes?cursor=`로 받는다.
- 판매자 · PC가 받는 작업 응답에는 `review`(상품명 · 평점 · 본문 · 첨부 · 작성 시각 · 전시 상태 · 답글 여부, 최신 업로드
  기준)가 같이 실린다. 휴대폰은 리뷰 피드(설치 토큰 전용) 없이 이 응답만으로 원문을 보고 승인한다.

**PC 쪽 구현 (2026-10-21, backend `vendorlink/VendorReplyTaskService`).**

- **초안은 하나, 기기만 다르다(D7, 2026-10-25 개정).** 「휴대폰으로 승인 요청」(`…/approval-request`)은 없앴다. 대신 PC가 맞춘다
  (`VendorReplyTaskService#mirror`): 받기마다(작업 변경을 받은 뒤 마지막 단계), 초안을 저장한 직후(저장 요청과 다른 스레드), 판매자가
  리뷰를 열었을 때(20초에 한 번) 그 리뷰의 PC 초안과 서버 작업을 비교한다.
  - 대상: 서버에서 받아 온 리뷰 · `대응 필요` · 초안 있음 · 채널 답글 없음 · 이 PC에서 승인하지 않음 · 리뷰 본문이 서버 지문과 같음.
    작업이 없거나, 열린 작업이 고칠 수 있는 상태(`AWAITING_APPROVAL` · `RECHECK_NEEDED` · `HELD`)일 때만. 승인됐거나 끝난
    작업(판매자가 취소한 것 포함)은 건드리지 않는다.
  - 마지막으로 맞춘 서버 버전 · PC 초안 버전(V146 `mirrored_*`)과 비교해 바뀐 쪽을 가른다. PC만 바뀌었으면 올린다. 휴대폰만
    바뀌었으면 그 문장을 PC 초안의 새 버전으로 들인다(작성자 `SELLER_PHONE`, 출처는 판매자). 둘 다 바뀌었으면 휴대폰 문장을
    들이고 PC 버전 번호를 `set_aside_local_version`에 둔다 — 화면이 「이 PC에서 쓰던 문장」으로 보여 주고, 판매자가 「휴대폰 문장
    쓰기」(`POST …/reviews/{id}/set-aside/drop`) 또는 「이 PC 문장 쓰기」(그 문장을 새로 저장)로 고른다.
  - PC가 올릴 때는 마지막으로 본 서버 버전을 `baseVersion`으로 같이 보낸다(서버 `POST /v1/stores/{id}/tasks`의 선택 필드, 열린
    작업이 없으면 `0`). 그사이 휴대폰이 고쳤으면 서버가 `stale`로 거절하고, 휴대폰 문장을 덮어쓰지 않는다.
  - 올린 버전은 PC가 바로 검사하고, 걸린 것(근거 없는 약속 · 금지 표현)이 있으면 그 판정을 `pc-recheck`로 서버에 남긴다 — 휴대폰이
    고칠 곳을 보여 주고, 금지 표현이면 서버가 휴대폰 승인을 거절한다. 그래서 금지 표현이 든 초안도 올라간다(휴대폰에 더 오래된
    문장이 남아 승인되는 것보다 낫다). 걸린 것이 없으면 아무것도 남기지 않는다(표시 없는 PC 버전 = 통과).
  - 거절(리뷰 바뀜 · 보관 끝 등)은 그 리뷰만 건너뛰고 다음 받기에서 다시 묻는다. `GET …/reviews/{reviewId}/task`는 PC가 아는
    마지막 작업 상태.
- **초안 메타의 지문 (2026-10-22 개정, 외부 검토 · 인터뷰 질문 34 「재검증 방식」).** 이전에는 세 지문을 모두 `unversioned`로
  보내고 `policy-check`를 부르지 않았다 — 서버의 재검증 규칙에 입력이 없었다. 이제 PC가 리뷰 초안을 만드는 판매자 자료로 세
  지문을 계산한다(`review/draft/ReviewDraftBasis`, 형식 `v1:` + 16진 32자).
  - `knowledgeFp` — 상품 지식(상품 · 옵션 · 종류 · 제목 · 본문 · 사용 중지 여부). `policyFp` — 회사 운영 정책(org 지식, 같은 항목)과
    약속 검사(`ReviewClaimGuard`)의 약속 낱말 목록. `voiceFp` — 리뷰 답글 문구(분류별 판매자 문구, 없으면 기본 문구)와,
    금지 표현이 하나라도 있으면 리뷰에 적용되는 금지 표현 목록(2026-10-23 — 없으면 예전 지문 그대로).
  - **과거 답글(답변 기억)은 넣지 않는다.** 승인할 때마다 기억이 하나씩 늘어 대기 중인 초안이 모두 되돌아가게 되고, 과거 답글은
    말투 참고일 뿐 사실 · 약속의 근거가 아니라 새 기억이 기존 초안을 틀리게 만들지 않는다. 답변 스타일의 말투 · 길이 · 인사 등은
    리뷰 초안이 읽지 않으므로 넣지 않는다.
  - **리뷰에도 금지 표현을 적용한다(2026-10-23 오너 결정, FINDINGS B24).** 답변 스타일의 「사용하지 않을 표현」은 리뷰에서도 절대
    금지다. 검사는 **실제로 보낼 답글 문장에만** 한다 — 고객 리뷰나 근거 문서에 그 표현이 있어도 일을 막지 않는다.
    - 생성: 금지 표현을 판매자가 입력한 값으로 따옴표에 담아 요청에 싣는다(지시가 아닌 피할 문구). 그래도 들어가면 한 번 다시
      쓴다. 그래도 남으면 초안을 버리지 않고 그대로 두고, 그 표현을 이름으로 알린다(`ReviewDraftComposer#forbiddenLeft`).
    - 승인 · 보내기: PC 승인(`ReviewReplyService`), 담당자 · 휴대폰으로 보내기(`VendorReplyTaskService#send`), 휴대폰 승인(서버가
      그 버전에 대한 PC의 `FORBIDDEN_PHRASE` 판정을 따라 `forbidden_phrase`로 거절)이 모두 같은 검사를 받는다 — 판매자나
      휴대폰이 고친 문장도 마찬가지다. 승인 전 PC 검사보다 먼저 휴대폰에서 승인된 문장은 담당자에게 가지 않고, PC 검사가
      걸리면 그 자리에서 보류된다. 금지 표현은
      약속과 달리 「보고도 승인한 것」으로 남지 않는다.
    - 재검사 코드 `FORBIDDEN_PHRASE`: 되돌아온 초안 · 휴대폰 수정본 · 승인된 답글(새로 금지한 표현이면 보류). 사유에는 그 표현과
      문장이 실린다.
    - 주제어: 「환불」「교환」처럼 약속 낱말 하나만 적은 줄은 리뷰에서는 막지 않는다 — 약속 여부는 근거로 판단하는 약속 검사의
      몫이다(`ReviewStyleGuard`). 문의 쪽 동작은 바뀌지 않는다.
    - **나눔과 화면(2026-10-23 오너 시안 승인 · 같은 날 구현).** 답변 스타일에 「절대 쓰지 않을 표현」(기존 목록 그대로, 위의 절대
      금지)과 「되도록 피할 표현 → 대신 쓸 표현」(`organization_answer_style.avoid_phrases`, V145)을 따로 둔다. 같은 표현을 두 목록에
      넣을 수 없다. 되도록 피할 표현은 말투 선호다 — 문의 답변의 생성 요청에는 「되도록 피하세요, 대신 …」 한 줄로 실리고, 리뷰
      답글에는 검사 없이 표시만 한다(`ReviewStyleGuard#findings`; 울타리 K는 두 목록만 건너게 한다). PC 리뷰 패널은 저장된 초안에서
      절대 금지를 빨간 밑줄, 피할 표현을 주황 점선으로 표시하고(`ReviewReplyPrepView.phraseFindings`), 절대 금지에는 「이 문장 빼기」
      · 「직접 고치기」, 피할 표현에는 「제안대로 바꾸기」 · 「그대로 두기」를 보인다. 바꾸기 · 빼기는 판매자가 누를 때만 판매자의 새 버전으로
      저장된다. 절대 금지가 남아 있는 동안 승인 · 담당자에게 맡기기 · 휴대폰 승인 요청은 꺼지고, 무엇을 고치면 되는지 한 줄로 말한다.
      설정 화면은 낱말 하나짜리 주제어(「환불」 등)를 입력하는 즉시 「안내까지 막힐 수 있다 · 리뷰에는 적용하지 않는다」고 알린다 —
      화면의 주제어 목록은 약속 검사 목록과 같음을 `ReviewTopicWordsParityTest`가 지킨다. **남은 것:** 휴대폰 화면에는 피할 표현을
      표시하지 않는다(절대 금지만 막는다). 문의 패널에는 표시가 없다(문의 초안은 절대 금지가 있으면 쓰지 않는다).
  - **보고.** 받기마다 리뷰 · 작업 동기화 전에, 지문이 이 PC가 그 스토어에 마지막으로 보고한 값(`vendor_store_binding.reported_draft_basis`,
    V141)과 다르면 `policy-check`를 부른다. PC가 초안을 올릴 때 · 판매자가 「답글 등록 요청」을 누를 때도 먼저 같은 확인을 하고
    지금 지문으로 보낸다 — 판매자가 화면의 초안을 보고 누르는 것이므로 그때의 지문이 맞다. 거절은 기록만 하고 받기를 멈추지 않는다.
  - **되돌아온 초안의 재검사(`review/draft/ReviewDraftRecheck`).** 모델이 글을 쓰거나 판정하지 않는다. 근거 검색은 리뷰 초안의 그
    검색 하나(`ReviewDraftComposer#currentLicense`)를 다시 묻는다 — 의미 검색이 켜져 있으면 초안처럼 임베딩을 쓴다. 동기화 뒤 그
    스토어의 `RECHECK_NEEDED` 작업을 서버에서 읽어 검사한다. ① 이 PC에서 쓴 버전이면 그 버전이 인용한 상품 지식 · 운영 정책이 모두 남아 있고, 사용 중이며, 초안 뒤에 고쳐지지
    않았어야 한다(`SOURCE_CHANGED`). 과거 답글 인용은 사실이 아니므로 보지 않는다. ② 지금 찾아지는 근거와 그 리뷰 분류의 판매자 문구에
    없는 약속(교환 · 환불 등)이 없어야 한다(`UNSUPPORTED_PROMISE`). 휴대폰에서 고친 문장은 인용이 없어 ②만 받는다.
    통과하면 **같은 문장을 지금 지문으로 다시 내** 승인 대기로 돌리고, 휴대폰에서 고친 문장이면 `pc-recheck` 통과를 새 버전에 기록한다.
    못 통과하면 `pc-recheck`에 코드를 남기고 `RECHECK_NEEDED`로 둔다 — 판매자가 PC에서 초안을 다시 보고 보낸다. **문장은 바꾸지
    않는다**(판매자의 수정은 보존, 질문 24). 같은 버전을 같은 지문으로 두 번 검사하지 않는다(`vendor_reply_task.rechecked_version` ·
    `rechecked_basis`, V141).
  - **승인된 답글은 실질적 충돌일 때만 보류한다(2026-10-23 오너 확정).** 같은 받기에서 되돌아온 초안 다음에, 지금과 다른 지문으로
    쓴 `APPROVED` · `CLAIMED` 문장을 버전 · 지문마다 한 번 검사한다(`VendorReplyTaskService#recheckApproved`). 근거 없는 약속이면
    `approved-check` hold, 인용한 문서만 고쳐졌으면 사유만 남기고 승인을 둔다. 사유는 PC 사본(`vendor_reply_task.basis_note`,
    V142)에 받아 리뷰 패널이 「왜 멈췄나요」로 보인다 — 바뀐 근거 · 부딪히는 곳(문장 표시) · 할 일.
  - **휴대폰 수정본은 승인 전에 검사한다(2026-10-23).** 받기마다 휴대폰에서 고친 버전(`AWAITING_APPROVAL` · `APPROVED` ·
    `CLAIMED`)을 그 문장이 쓰인 근거 그대로일 때 한 번 검사해 `pc-recheck`로 남긴다(`checkPhoneEdits`, 사본
    `pc_checked_version` V143). 승인이 선 휴대폰 버전의 첫 검사는 위 「PC 검사 전에 담당자에게 가지 않는다」대로 통과면 담당자에게
    넘기고 걸리면 보류한다. 이미 검사한 버전을 다시 기록할 때는 상태를 옮기지 않는다. 휴대폰 · PC는 승인 전이면
    「확인할 점」, 승인 뒤면 「근거에 없는 약속을 확인하고 승인한 답글」 한 줄로 보인다. 근거가 바뀐 뒤 승인된 문장을 검사할 때
    **판매자가 이렇게 보고 승인한 약속은 빼고**, 그 뒤 새로 근거를 잃은 약속만 보류 사유가 된다. **남은 경우:** 휴대폰 수정 직후
    PC가 받기 전에 근거까지 바뀌면 기준선이 없어, 그 약속도 보류된다(닫힌 쪽).
  - **화면 확인.** 휴대폰 · 담당자 화면은 `tools/vendor-pages-check/check.mjs`가 실제 브라우저에서 확인한다(보류 사유 · 문장 표시
    · 등록 직전 멈춤 · 서버 문자열이 HTML로 그려지지 않음).
  - **서버 쪽 정한 점.** PC가 같은 문장을 새 지문으로 다시 내면 `edited_on_mobile`을 유지한다(휴대폰의 문장이라는 표시가 재검사로
    지워지지 않게). 다른 문장이면 PC의 문장이라 해제된다.
  - **한계.** 재검사는 근거 문서가 "고쳐졌는가"를 시각으로 본다 — 초안 시점의 문서 내용 해시를 저장하지 않아서다. 따라서 내용이
    같은 재저장은 없지만(지문은 내용 기준), 판매자가 인용 문서의 다른 부분만 고쳐도 그 문서를 인용한 초안은 판매자 확인으로 넘어간다.
    판매자 판단 기록(SellerDecision) · 판매자 지침(SellerGuidance)처럼 근거를 걸러 내기만 하는 자료는 지문에 없다. 같은 스토어를 받는
    PC가 둘이고 두 PC의 자료가 다르면, 한쪽의 보고가 다른 쪽 초안을 되돌린다 — 재검사가 다시 내도 서버의 마지막 보고와 달라 되돌아간
    채로 남고, 그 버전은 다시 검사하지 않는다.
  - **단계(2026-10-23).** 위 재검사는 **1단계 — 변경 감지와 규칙 재검사**다: 근거가 고쳐졌는지와 근거 없는 약속이 생겼는지를 본다.
    "바뀐 정책이 이 답글의 문장과 실제로 충돌하는가"는 아직 보지 않는다. **2단계** 는 바뀐 근거와 초안 문장의 관련을 좁혀
    검사해, 관련 없는 변경이면 승인 대기를 유지하고 실제로 영향받는 초안만 판매자 확인으로 보내는 것이다 — 판매자가 다시 판단할
    일을 줄이는 것이 목적이다. **2단계 중 구절 단위는 됐다(2026-10-23):** 초안을 쓸 때 본 구절의 지문을 인용에 남기고
    (`review_draft_evidence.passage_fingerprint`, V144 — 구절 자체는 복사하지 않는다), 문서가 고쳐진 뒤에도 같은 지문의 구절이
    지금 문서에 그대로 있으면 그 초안이 쓴 부분은 바뀌지 않은 것으로 본다 — 같은 문서의 다른 부분만 고친 편집은 초안을 되돌리지
    않는다. 지문 없는 옛 인용은 예전처럼 고친 시각으로 본다. **남은 것:** 인용한 구절이 바뀌었을 때 "바뀐 내용이 답글 문장과
    실제로 부딪히는가"(의미 판단)는 아직 하지 않는다 — 구절이 바뀌면 판매자 확인으로 보낸다(닫힌 쪽). 구절 경계는 문서
    나누기(약 420자, 빈 줄 우선)를 따르므로, 앞부분 편집으로 경계가 밀리면 내용이 같아도 바뀐 것으로 볼 수 있다.
    **약속의 조건도 본다(2026-10-23 외부 점검).** 약속 검사는 낱말(교환 · 환불 …)만이 아니라 그 약속 문장이 적은 조건 —
    기간(7일 · 즉시), 금액(무료 · 전액 · 왕복 배송비), 대상(단순 변심 · 개봉 후) — 도 근거에 있어야 통과한다
    (`ReviewClaimGuard#unsupportedConditions`). 그래서 정책이 「교환」은 그대로 둔 채 7일을 14일로, 무료를 고객 부담으로 바꾸면
    「7일 이내 무료 교환」을 승인한 답글은 보류되고 사유에 「7일」 · 「무료」가 실린다. AI 초안도 같은 검사로 걸러진다. 짧은 목록이라
    목록 밖 말로 쓴 조건(예: 「색상만」)이나, 근거 안에서 그 약속과 상관없는 곳에 있는 같은 숫자는 구별하지 못한다.
- **동기화.** 리뷰 받기마다 `tasks/changes`를 받아 `vendor_reply_task`(V137)에 사본을 둔다. 아직 받아 오지 않은 리뷰의 변경을 만나면
  거기서 멈추고 다음 받기에 이어 간다. 상태 버전이 뒤로 가는 사본 갱신은 하지 않는다.
- **답글 두 번 방지.** 작업이 열려 있거나(`UNKNOWN` 포함) **담당자가 등록했다고 보고한(`POSTED`)** 리뷰는 PC의 `canApprove` ·
  `canStartSubmissionRun`이 거짓이고 승인 · 가이드 등록 요청을 409로 거절한다(`DelegatedReplyLane.holds`). `POSTED`는 서버 작업의
  끝이지만 채널의 `답글여부=Y`가 반입되기 전까지 PC의 다른 어떤 것도 답글이 나간 줄 모르기 때문이다. `FAILED` · `CANCELLED` ·
  `INVALIDATED`만 PC의 길을 다시 연다.
- **PC에서 맡기기 · 취소(D9 · D10).** `POST …/reviews/{reviewId}/hand-over`는 승인 요청과 같은 검사(여기에 '대응 필요' 분류 확인이
  더해졌다) 뒤 초안을 내고 서버가 돌려준 버전 · 지문으로 곧바로 `approve`한다(명령 ID `pc-approve:{taskId}:{version}`). 승인이 거절되면
  작업은 휴대폰 승인 대기로 남고 그렇게 알린다. `POST …/reviews/{reviewId}/cancel`은 마지막 작업이 `AWAITING_APPROVAL` ·
  `RECHECK_NEEDED` · `APPROVED` · `CLAIMED`일 때만 서버의 `cancel`을 부른다. 승인 · 착수가 끝난 작업이 있으면 새로 보내기를 PC가 먼저
  거절한다. 리뷰 화면은 답변 준비 응답의 `delegation`(`taskState` · `editedOnMobile` · `canSend` · `canCancel`)만 보고 버튼을 그린다 —
  서버에서 받은 리뷰가 아니거나 연결되지 않은 PC면 `null`이고 화면에 아무것도 서지 않는다.
- **결과 기록.** `POSTED`는 기존 답글 레인에 `OPERATOR_REPORTED_SUBMITTED` + `UNVERIFIED`로 한 번만 남긴다(명령 ID
  `vendor-posted:{taskId}`).
- **승인은 답변 기억이 된다 (2026-10-22 외부 검토 P2, V140).** PC가 작업이 승인된 것을 처음 볼 때(휴대폰 승인 · 휴대폰에서
  고친 뒤 승인 · 이 PC의 「승인하고 맡기기」) 승인된 문장을 판매자 작성 초안 버전으로 저장하고(이미 같은 문장이면 그 버전),
  그 버전을 `vendor_reply_task.approved_draft_version`에 적고, 이 PC에서 승인한 답글과 같은 `USER_APPROVED`로 답변 기억에
  남긴다(`ReviewAnswerMemoryHook`, 행위 ID `review-approved:{review}:{version}`). 과거 답변 검색(`ReviewReplyAdapter`)은 승인이
  서 있는 작업(승인 · 착수 · 등록 · 실패 · 확인 중)의 그 버전을 「판매자가 승인한 답글」로, 등록 보고 뒤에는 「채널에 등록된
  것으로 기록된 답글」로 읽고, 취소 · 리뷰 변경으로 끝난 작업은 읽지 않는다. 담당자의 등록은 보고일 뿐 읽어 확인한 것이
  아니라 더 강한 기억(`EXECUTOR_SENT_VERIFIED`)은 만들지 않는다. 그래서 판매자가 휴대폰에서 고친 답글이 다음 비슷한 리뷰의
  초안 근거(과거 답변 칸)로 돌아온다. 한계: 테스트의 근거 찾기는 낱말 일치뿐이라, 조사가 다른 긴 문장(배송이 · 배송과)은
  같은 리뷰 문장으로도 찾지 못했다 — 실제 사례 확인에서 잰다(`docs/FINDINGS.md` B22).
- **'답글 필요 없음'(D8).** 리뷰 받기마다, 현재 분류가 `NO_ACTION`이고 `SELLER:`가 정한 리뷰를 `disposition`으로 한 번 알린다.
  나중에 판매자가 생각을 바꿔도 서버의 90일 시작점은 움직이지 않는다(§6) — 그 사이 서버의 리뷰가 지워지면 그 리뷰의 대행 작업은
  더 열 수 없고, PC의 리뷰와 PC의 답글 길은 그대로다.

## 5. Cafe24 토큰 중계

§17.7의 설계를 엔드포인트로 옮긴다. 서버가 쥐는 비밀은 **공급자 앱의 client secret 하나**다.

| 단계 | 요청 | 서버가 하는 일 |
|---|---|---|
| 연결 시작 | PC `POST /v1/cafe24/authorize` {mallId, localPort} | 기존 `Cafe24OnboardingService.start`와 같은 state(32바이트, 해시만 저장, TTL 600초, 설치 · 몰당 하나). 인가 URL 반환. `localPort`는 1024–65535만 |
| 콜백 | 브라우저 `GET /v1/cafe24/callback` (Cafe24에 등록하는 유일한 redirect URI) | state 검증 · 소진, `mall_id` 일치 확인, 코드 교환, **결과를 설치 공개키로 봉인**해 보관. 브라우저는 `http://127.0.0.1:{localPort}/connect/cafe24/result?status=…&ticket=…`로 보낸다(코드 · 토큰은 URL에 없음) |
| 수령 | PC `POST /v1/cafe24/pickup` {ticket} | 봉인된 결과 반환 |
| 갱신 | PC `POST /v1/cafe24/refresh` {mallId, refreshToken} | 멱등 키 = SHA-256(refreshToken). 그 키의 봉인 결과가 있으면 Cafe24를 다시 부르지 않고 돌려준다. 없으면 설치 · 몰당 하나만 진행(행 잠금), Cafe24 호출, 봉인 보관, 반환 |
| 저장 확인 | PC `POST /v1/cafe24/ack` {ticket 또는 키} | 봉인 결과 즉시 삭제 |

- 봉인 결과는 확인이 없으면 **최대 72시간** 뒤 정리 작업이 지운다(§17.9 표). 그 뒤 PC가 소진된 refresh token만
  가졌다면 재연결(OAuth)로 복구한다.
- 서버는 `(install_id, mall_id)` 묶음을 저장한다 — 연결한 설치만 그 몰을 갱신할 수 있게 하기 위한 최소 식별자다.
- 요청 본문의 refresh token은 처리 중 메모리에만 있고 로그 · 오류 추적에 남지 않는다. 봉인 전 평문을 DB에 쓰지 않는다.
- **PC 쪽 변경 [REPO].** 지금 `Cafe24Authorizer.authorize`는 부를 때마다 refresh하고, 유효한 access token을 재사용하는
  캐시가 없다(`Cafe24TokenClient` javadoc). 실제 HTTP 요청마다 부르는지는 호출부마다 다르다. 중계를 거치면 그만큼
  서버 왕복과 Cafe24 갱신이 생긴다. 판매자 PC 모드에서는 다음 순서로 바꾼다.
  1. 유효한 access token을 재사용한다. 기준은 고정 "2시간"이 아니라 **응답의 `expires_at`**이다(Cafe24가 만료 시각을
     돌려준다, `Cafe24TokenResult`).
  2. 만료 직전 여유 구간에 들어오면 갱신한다. 여유 폭은 구현 때 정하고 테스트로 고정한다.
  3. 같은 연결의 동시 갱신은 한 번만 한다. 지금의 프로세스 안 잠금(`Cafe24AccountRefreshLocks`)을 그대로 쓰고, 기다린
     호출은 갱신된 토큰을 받는다. 서버 쪽 단일 진행과 멱등 키가 프로세스 재시작 같은 나머지 경우를 맡는다.
- refresh token 수명은 2주라 PC가 2주 넘게 꺼져 있으면 재연결이 필요하다 — 연결 화면에 안내한다.
- Cafe24 개발자센터에 등록할 redirect URI는 이 서버의 콜백 하나다. 기존 pilot의 `/api/connect/cafe24/callback`과
  경로가 다르므로, 기존 앱을 재사용할지 새 앱을 등록할지는 [PO] (기존 pilot 연결을 끊지 않으려면 둘 다 등록).

## 6. 보유와 삭제 — §17.9 표의 실행 규칙

| 대상 | 삭제 시점 | 실행 |
|---|---|---|
| 업로드 원본 엑셀 | 반입 성공 즉시 / 실패는 24시간 | **구현: 디스크에 쓰지 않는다**(§3.2 구현 — 메모리에서 읽고 버림, 컨테이너 임시 폴더도 안 씀). 지울 파일이 생기지 않으므로 정리 작업 대상이 아니다 |
| 진행 중 리뷰 · 초안 · 승인 | 업무가 끝날 때까지 | 30일 넘게 움직임이 없으면 판매자에게 정리 안내만(자동 삭제 아님) |
| 완료된 작업과 그 리뷰 | `POSTED` · `FAILED` 확정 또는 `CANCELLED` · `INVALIDATED` 후 90일 | `ended_at` 기준 정리 작업 |
| 답글이 필요 없는 리뷰 | PC 저장 확인과 '대응 불필요' 판정이 **둘 다** 끝난 시점부터 90일 상한(D4) | 같은 정리 작업. 시작점은 한 번 정해지면 같은 리뷰의 재업로드로 늦춰지지 않는다 — 재업로드는 변경 사건(§3.1 4)만 만든다 |
| Cafe24 봉인 결과 | 저장 확인 즉시 / 최대 72시간 | ack 시 삭제 + 정리 작업 |
| Cafe24 OAuth state | 만료 후 | 정리 작업. 기존 backend는 이 표를 지우지 않는다 — 서버에서는 지운다 |
| 공인 IP 응답 | 저장하지 않음 | §7 |

**정리 작업 구현 (2026-10-22, `retention/Retention` · `PurgeSchedule`).**

- **언제 도나.** 15분마다, 그리고 서버가 요청을 받기 시작하기 **전에** 한 번. 운영 명령 `purge`로 직접 돌릴 수도 있다(지운
  개수만 출력). 운영 명령 프로세스는 시작할 때 돌지 않는다.
- **리뷰 한 건을 지우는 조건.** 그 리뷰의 작업 중 아직 진행 중이거나 끝난 지 90일이 안 된 것이 없고, 다음 둘 중 하나일 때:
  '대응 불필요' 90일(`purge_after`)이 지났거나, `purge_after`가 없고 작업이 있었다. **둘 다 해당하면 늦은 쪽**을 따른다.
  아무도 정하지 않은 리뷰(작업도 '대응 불필요'도 없음)는 진행 중 자료라 지우지 않는다. `UNKNOWN` · 승인 대기처럼
  진행 중인 작업이 있으면 다른 기한이 지났어도 남는다.
- **함께 지우는 것.** 그 리뷰의 작업 전부와 각 작업의 명령 기록 · 상태 변경 기록, 그 리뷰의 피드 사건. 작업은 리뷰와 함께만
  지운다 — 리뷰가 남은 채 '등록됨' 작업만 지우면 같은 리뷰에 두 번째 답글을 막는 근거가 사라진다.
- **남기는 것은 식별자뿐.** `purged_reviews`에 서버 리뷰 ID와 리뷰글번호의 **해시**만 둔다(내용 없음).
  - 같은 리뷰가 다음 업로드에 다시 실려도 되살리지 않는다. 업로드 결과에서 「그대로」에 세고 응답의 `purged`로 따로 센다
    (D4 "재업로드로 늦춰지지 않는다"). 되살리면 PC 쪽 묶음(리뷰 한 건 = 서버 리뷰 한 건)이 새 ID를 받지 못해 그 매장의
    받기가 그 자리에서 멈춘다.
  - 지운 리뷰에 PC가 늦게 보낸 '답글 필요 없음'은 이미 끝난 일로 받는다(204). 404로 거절하면 PC가 받기 전체를 "권한
    없음"으로 멈추고 매번 다시 보낸다.
  - 지운 리뷰에 새 답글 작업을 내면 `409 review_purged`. PC는 "서버 보관 기간이 끝나 정리된 리뷰라 담당자에게 맡길 수
    없습니다. 판매자센터에서 직접 답글을 다세요"라고 보인다.
- **그 밖에 지우는 것.** 만료된 판매자 · 담당자 초대(주소와, 담당자는 등록 중인 비밀번호 해시 · TOTP 비밀까지 들고 있다)와
  만료가 지난 로그아웃 세션 기록. 초대가 없어진 뒤의 안내는 만료와 같다(둘 다 "유효하지 않은 초대").
- **아직 없는 것.** 30일 넘게 움직임 없는 진행 중 자료의 정리 안내는 판매자 화면이 필요해 시안 확인 뒤로 미뤘다.
  Cafe24 봉인 결과 · OAuth state는 §5가 생길 때 같은 작업에 붙인다.
- **알려진 한계.** PC의 확인 위치(`ack`)가 가리키는 사건이 그 사이 지워졌으면 그 `ack`는 거절된다. 다음 업로드로 새 사건이
  생기면 PC가 그 위치로 다시 확인해 풀린다.

**백업은 별도로 설계한다 — "최대 14일 더 남는다"고 말할 수 없다.** 기존 `deploy/pilot/backup.sh`는 호스트 안의
덤프만 `PILOT_BACKUP_KEEP_DAYS`(기본 14일)로 지운다. 외부(S3) 사본은 **버킷 수명주기 정책이 지우고, 스크립트는 원격
객체를 지우지 않는다**(업로더 자격증명이 PutObject 전용이라서 — 스크립트 주석 34–37행). 그 정책의 실제 설정은 아직
확인하지 않았다 [EXT]. 처리방침에 추가 보관 기간을 적는 것만으로 해결되지도 않는다 — 불필요해진 개인정보의 파기
의무를 기준으로 백업의 필요성과 삭제 방법을 함께 정한다.

1. 운영 데이터의 보관(§6 표)과 재해복구 백업의 보관 기간을 따로 정의한다. 백업 기간은 [PO].
2. 백업은 일반 조회에 쓰지 않고 접근을 복구 담당으로 제한한다.
3. 복원하면 서비스를 열기 전에 삭제 대상 목록을 다시 적용한다. 그러려면 삭제 기록(무엇을 언제 지웠는지 — 내용 없이
   식별자만)이 백업과 별도로 남아 있어야 한다.
   **구현 (2026-10-22): 별도 기록 대신 규칙으로 다시 지운다.** 삭제 조건은 모두 행 자신이 들고 있는, 한 번 정해지면 늦춰지지
   않는 날짜(`purge_after` · `ended_at` · 만료 시각)로만 정해진다. 백업 뒤에 지워진 행은 그 기한이 백업 시점보다 앞서
   정해졌으므로(지워진 시각 − 90일 < 백업 시각), **백업 보관이 90일보다 짧은 한** 복원본 안에 다시 지울 근거가 다 들어
   있다. 서버는 시작할 때 요청을 받기 전에 한 번 정리하므로 복원 → 시작만으로 적용된다. 백업을 90일 이상 두기로 하면
   그때 백업 밖의 삭제 기록이 필요하다 — 백업 기간은 아직 [PO].
4. Cafe24 봉인 결과는 일반 백업에서 뺀다(별도 테이블 · 덤프 제외). 72시간 뒤 쓸모가 없고 복원해서도 안 된다.
5. 호스트 덤프 · S3 사본 · 볼륨 스냅샷까지 실제 모든 사본의 삭제 시점을 검증한다.

EC2 볼륨 · 백업 대상의 저장 암호화도 AWS 콘솔에서 확인한다 [EXT].

## 7. 공인 IP 확인

`GET /v1/ip` (설치 토큰 필요 — 공개 IP 조회 서비스로 쓰이지 않게) → `{"ipv4": "x.x.x.x"}`

- **IPv4 전용 호스트명**(A 레코드만, AAAA 없음)으로 제공한다. NAVER 호출 IP 등록은 IPv4이고(`NaverAdvertisedEgress`가
  IPv4만 받음), PC가 IPv6로 서버에 닿으면 엉뚱한 주소를 안내하게 된다.
- 요청자 주소는 Caddy가 붙인 `X-Forwarded-For`의 마지막 값만 믿는다. Spring은 Caddy 컨테이너만 신뢰하는 프록시로 둔다.
- 저장 · 로그 없음. 현재 Caddyfile에는 `log` 지시어가 없어 접근 로그가 꺼져 있다 — 그 상태를 유지하고 fence로 고정한다.
- 연결 화면은 이 값을 "이 PC의 공인 IP"로 보여 주고, 서버에 닿지 않으면 지금의 수동 안내로 돌아간다(§17.9).
- **PC 쪽 (2026-10-17).** backend `GET /api/local/vendor-link/public-ip` → `{ipv4}` 또는 `{reason}`
  (`NOT_LINKED` · `IPV6_ONLY` · `NOT_AUTHORIZED` · `UNREACHABLE`). 같은 답을 60초 재사용한다. 판매자 PC의
  `OutboundGate`는 새 목적지 `VENDOR`로 이 요청을 검사한다. 통과하는 것은 loopback과 `OutboundGate.VENDOR_HOSTS`의
  이름 하나 — `https://vendor.reviewnary-pilot.duckdns.org`(⑧-4 (c), 2026-10-17)뿐이고, http · 원래 pilot 이름 · 닮은
  이름은 전송 전에 막힌다. 설정한 주소가 다른 곳을 가리켜도 나가지 않는다. DNS는 A `3.39.210.89` 하나, AAAA 없음 —
  PC가 IPv4로 닿으므로 IP 응답이 네이버에 등록할 주소다.

## 8. 라이선스

`POST /v1/installs/me/heartbeat` {appVersion, osFamily} → `{licenseStatus, validUntil, latestVersion}`

보내는 필드는 이 두 개뿐이다(§17.3: 스토어 ID · 원문 · 작업 목록을 몰래 붙이지 않는다). 서버에 닿지 않아도 로컬
업무와 이력 열람은 유지한다. 유예 기간은 [PO] 미정이며, 결제 문제로 데이터를 막거나 미확인 발송을 재시도하지 않는다.

## 9. 배치 — 기존 AWS 자산 재사용

`deploy/pilot`의 형태(Caddy가 TLS를 끝내는 단일 공개 출입구 + compose + Postgres + `backup.sh` · `restore.sh` ·
`preflight.sh`)를 그대로 쓰고, backend 대신 `vendor-server`를 넣는다. 기존 pilot compose는 보류 상태로 보존한다(v1.14 ⑧-2).

- 서버도 Sentry · 분석 도구 · 요청 본문 로그를 끈다(§17.9 경계 5). 오류는 본문 없는 코드와 요청 ID만 남긴다.
- 외부로 나가는 곳은 `*.cafe24api.com`의 토큰 엔드포인트 하나다. 기존 `OutboundGate`와 같은 허용 목록을 서버에도 둔다.

## 10. 구현 전에 고정할 테스트

1. **서버에 채널 클라이언트가 없다:** `vendor-server/` 소스에 NAVER · Coupang 호스트와 `com.sellerops.connector` 류

2. **열 제거:** 계약 fixture의 `MUST-NOT-PERSIST` 표식이 DB · 응답 · 로그 어디에도 없음. 계약에 없는 열이 있는 파일은 거부.
3. **상태 경합:** 취소와 착수, 담당자 두 명의 착수, 휴대폰 수정과 승인이 동시에 와도 한 전이만 성립.
4. **중계 응답 유실:** Cafe24 성공 후 응답을 버리고 같은 refresh token으로 다시 요청 → Cafe24 호출 1회, 같은 결과.
5. **보유:** 시계를 옮겨 24시간 · 72시간 · 90일 경계에서 정확히 지워지고, 하루 전에는 남아 있음. 같은 리뷰를
   다시 올려도 90일 시작점이 바뀌지 않음. 백업을 복원한 뒤 삭제 기록을 다시 적용하면 지운 행이 남지 않음.
   (2026-10-22 구현: `RetentionTest` — 90일 경계 1초 전 · 당일, 진행 중 작업 · 미결 리뷰는 10년 뒤에도 남음, 둘 다면
   늦은 쪽, 지운 리뷰 재업로드 · 늦은 판정 · 새 작업, 만료 초대 · 세션, 복원본 재정리. 24시간 · 72시간은 해당 자료가 없다 —
   엑셀은 디스크에 쓰지 않고 §5는 미구현.)
6. **봉인:** 서버 DB · 로그에 토큰 평문이 없음(합성 표식으로 확인), 다른 설치의 키로는 열리지 않음.

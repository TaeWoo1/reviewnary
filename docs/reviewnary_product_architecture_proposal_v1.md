# Reviewnary 제품 구조 v1

작성: 2026-10-14, 제품 오너와의 구조 검토.

**상태: 판매자 자체 운영형 로컬 제품 + 네이버 리뷰 사람 대행(교환 서비스)을 초기 구조로 채택 — `docs/product-scope-v1.md` v1.14 / 외부 허가·구현 검증은 별도.** 2026-10-15 확정한 §12 업무 모델, 2026-10-16의 §16 개인사업자 결정과 §17 로컬 운영 경계가 최신 제품 방향이다. **Claude 개발 인계는 §18부터 읽는다.** 브라우저 자동 수집·입력·게시는 v1.14 ⑦에 따라 제품 범위 밖이다. §1~§16의 중앙 SaaS·연동사·전체 로컬 후보는 조사 이력이며, 충돌 시 해당 범위의 최신 결정을 우선한다. 상세 인터뷰는 일시 중단 상태를 유지한다. 이 결정은 채널 추가·외부 문의 전송·계약·라이브 수집·발송 승인이 아니며 전체 구현 감사도 아니다. 기존 canonical scope와의 차이는 §18에서 명시적으로 대조하며 안전 계약은 유지한다. 오너는 Cafe24 API 관련 검증을 이미 수행했다고 설명했다. 이를 출발점으로 사용하되, 특정 발송 기능·상시 운영·상용 계약까지 검증됐다고 확대하지 않는다.

## 1. 제품 정의와 고정할 중심

Reviewnary는 상품과 판매자의 운영 기준을 이해하고, 여러 채널의 리뷰·문의에서 처리할 업무를 찾아, 근거 있는 대응을 준비하고, 허용된 실행을 이어가며 결과를 기록·재사용하는 판매 운영 AI다.

- 초기 진입점은 리뷰 대응과 상품 관련 문제 해결이다. 문의는 같은 맥락을 사용하는 인접 업무이며, 리뷰 접근 제약 때문에 문의 전용 서비스로 전환하지 않는다.
- 단기는 개별 승인 후 실행을 목표로 한다. 장기는 판매자가 유형별로 위임하고 채널도 허용하는 업무에 한해 자율 실행을 검토한다.
- 자동 수집·자동 게시 여부 하나만으로 제품 전체의 가치를 정의하지 않는다. 동시에 반복 업로드·복사·등록의 부담도 실제 비용으로 측정한다.
- Aside와 범용 agent의 발전을 활용하되, 제품의 필수 인터페이스나 권한 판단의 주체로 고정하지 않는다.

## 2. 하나의 제품, 분리된 계층

```text
공식 API / 허가된 연동사 / 판매자 제공 파일 / 허용된 사람 수행
                         |
             수집 어댑터 + 출처·범위·최신성
                         |
          판매자별 상품 지식·정책·응대 기억
                         |
    운영 AI: 조사 -> 판단 -> 우선순위 -> 대응 준비
                         |
             업무 큐 + 채팅 + 개별 승인
                         |
       별도 실행 계층: 권한·정책·버전·중복 검사
                         |
          공식 실행 / 허가된 대행 / 사람 수행
                         |
             게시 결과·후속 관측·학습 기록
```

| 계층 | 책임 | 맡기지 않을 책임 |
|---|---|---|
| 수집 어댑터 | 허용된 방법으로 확보, 중복 제거, 상품 연결, 획득 범위 보고 | 서비스 입점만으로 모든 데이터 접근이 허용됐다고 가정 |
| 지식·운영 기억 | 출처·상품·적용 범위·버전·유효 기간·수정 이력 | 과거 일회성 약속을 현재 정책으로 일반화 |
| 운영 AI | 목표 해석, 필요한 조사, 대응 필요 판단, 근거 기반 초안·조치 준비 | 자격 증명 보유, 권한 생성, 금지된 경로로 우회 |
| 업무 화면 | 오늘의 중요 업무, 누락·대기 사유, 채팅 수정, 개별 승인 | 승인과 발송 성공을 동일 상태로 표시 |
| 실행 계층 | 승인된 정확한 대상·내용을 허용된 경로로 실행, 결과 검증 | LLM 출력만으로 외부 작업 실행 |
| 결과·학습 | 게시 확인, 판매자 수정, 관측 가능한 후속 결과, 재사용 효과 | 무응답을 고객 문제 해결로 단정 |

기존 Spring 사실·거래 책임, backend-only LLM egress, credential 없는 LangGraph orchestration을 존중한다. 현재 Operator의 READ-only catalogue에 WRITE 도구를 넣지 않는다. 실행은 별도 권한 계층의 변경 제안이며, 실제 구현 전 현행 scope·승인·안전 계약을 명시적으로 대조하고 필요한 변경을 합의해야 한다. 외부 도구나 agent도 같은 경계를 적용받는다.

## 3. 채널이 아니라 작업별로 권한 관리

채널 전체에 supported=true를 붙이는 대신, `(채널, 자료 유형, 작업, 연결 방식)`별로 다음을 따로 관리한다.

1. **허용 근거:** 공식 문서·정책·계약·플랫폼의 구체적 답변과 적용 범위. 불명확하면 불명확한 상태를 유지한다.
2. **판매자 권한:** 실제 부여된 scope, 계정/스토어 범위, 위임, 철회·만료.
3. **데이터 사용 조건:** 보관, AI 처리, 제3자 처리, 국외 처리, 다른 채널과의 결합, 삭제·재학습 금지 조건.
4. **실제 동작 증거:** 조회·준비·게시 각각의 구현과 성공 증거. 허용됐다고 동작 성공까지 추론하지 않는다.
5. **관측 범위:** 마지막 확보, 포함 기간, 빠진 구간·미지원 자료, 최신성.

허용 여부와 기술적 동작 여부는 별개다. 플랫폼이 허용한 범위 안에서 판매자가 권한을 부여해야 하고, 실제 성공 증거까지 있어야 운영 기능으로 제공한다. 판매자의 승인만으로 플랫폼 제한이 사라지지 않는다.

업무 상태는 최소한 자료 대기, 판단/준비 중, 판매자 정보 필요, 승인 대기, 외부 등록 대기, 실행 중, 게시 확인, 실패, 결과 미확인, 대응 불필요를 구분한다. 복사하거나 승인한 건을 게시 확인으로 표시하지 않는다. 사람의 완료 신고와 공식 조회에 의한 확인도 구분한다.

## 4. 네이버 제품 구조

> 이 절의 입점 우선·중앙 SaaS 전제는 초기 조사안이다. 초기 제품의 최신 운영·배포 방향은 §17, 구현 전 계약 조정은 §18을 따른다. 기존 조사 내용을 현재 결정으로 다시 채택하지 않는다.

### 4.1 서비스와 상용 연결

- Reviewnary 하나를 CS·고객관리 솔루션으로 입점하는 경로를 우선 추진 대상으로 제안한다.
- 판매자가 솔루션을 구독·인증하는 공식 흐름으로 연결한다. 내스토어 애플리케이션의 키를 받아 외부 SaaS를 운영하는 형태를 상용 연결의 기본으로 삼지 않는다.
- 외부결제는 검토·협의를 완료한 경우 가능하다. 마켓 유입 사용자의 결제 내역 전송과 별도 과금 안내를 포함한다. 협의 전부터 외부결제가 확보됐다고 취급하지 않는다.
- API대행사는 입점 외 공식 연결의 대안이다. 리뷰 접근 권한이 따라온다고 가정하지 않으며, 솔루션과 병행할 실익·권한·의무는 따로 확인한다.
- 멀티채널 운영 자체와 네이버 자료의 목적 외 이용을 구분한다. 네이버 자료를 다른 채널의 응대 근거로 재사용할 수 있는지는 데이터 유형·승인 목적별로 확인하고, 미확인 자료는 출처 범위 안에서만 사용한다.

### 4.2 리뷰 수집 경로를 병렬로 확보

| 경로 | 제안 | 운영 가능한 경로로 만들 조건 |
|---|---|---|
| 판매자 직접 공식 내보내기 + 웹 업로드 | 초기 대체 경로 | 파일 사용·처리 목적 검토, 실제 필드·기존 답글·기간 확인, 중복·누락 검사, 짧은 업로드 UX |
| Reviewnary 매니저 계정으로 사람 수행 | 조건부 대행 후보 | 매니저 접근 범위, 서비스 제공·자료 처리 조건, 최소 권한·해지 회수 확인. 사람이 처리하더라도 보관·AI 처리는 별도 검토 |
| Reviewnary 매니저 기반 자동 연동 | 핵심 확인 과제 | 정확한 수집 수단·주기·필드·보관·AI 처리·게시를 설명한 플랫폼 허용 범위 확보. 초대만으로 자동 수집을 허용하지 않음 |
| 기존 리뷰 서비스와 계약 연동 | 핵심 확인 과제 | 우리 서비스에 대한 재제공·AI 처리 권리, 원채널 조건, 식별자·원출처·기존 답글·갱신·삭제 제공, SLA·비용 확인 |
| 네이버 직접 데이터 제휴 | 장기 전략 경로 | 제한된 유스케이스와 최소 데이터, 평가 방식, 보안·책임을 제시하고 실제 계약·허용 범위 확보 |

기존 연동사의 API 존재와 매니저 초대 운영 사례는 협의 가능성을 보여주는 근거다. 우리 사용 목적의 허가·계약은 아직 확보된 것이 아니다. 제휴사의 자사몰 댓글 등록 기능이 네이버 원본 리뷰 게시까지 지원한다고 가정하지 않는다.

직접 제휴는 새 공개 API를 요구하는 방식 하나로 제한하지 않는다. 승인된 데이터 파일 전달·한정 연동·플랫폼이 지정하는 방식 등도 후보로 제시할 수 있다. 단, 해당 방식을 플랫폼이 실제 제공한다는 주장은 하지 않는다.

### 4.3 리뷰 답글의 실행

- 지금 확보되지 않은 리뷰 게시 API를 추측하거나 비공식 endpoint로 대체하지 않는다.
- 최초 후보는 판매자 직접 복사·등록이었으나, §12 결정으로 기본 경험은 개별 승인 후 운영 담당자의 직접 등록으로 바뀌었다. 판매자 직접 등록은 대체 경로로 남긴다. 공식적으로 가능한 링크·검색 안내로 찾는 부담을 줄이되, 안정적인 리뷰별 링크가 있다고 가정하지 않는다.
- 브라우저 입력 보조와 자동 게시도 각각 별개의 허가 과제로 관리한다. 판매자가 우리 서비스에서 승인했다는 사실만으로 허용되는 것이 아니다.
- 사람 대행과 허가된 자동 게시 경로가 확보되면 같은 업무의 실행 어댑터를 교체한다. 업무·지식·승인 이력을 다시 구축할 필요가 없게 한다.
- 게시 확인 방법이 없으면 외부 등록 대기 또는 결과 미확인으로 남긴다. 공식 다음 파일이나 허가된 조회로 확인 가능한지 검토한다.

### 4.4 자동화 약속의 범위

파일 입력 전의 미관측 리뷰를 실시간으로 확인했다고 말하지 않는다. 자료 확보 지연과 확보 후 처리 시간을 각각 기록한다. 기존 15분 목표를 파일 경로에서는 발생부터 충족한다고 약속하지 않으며, 처리 목표 변경은 추가 합의 대상이다.

네이버 입점 기능은 별도 앱·확장 프로그램·Aside 설치에 의존하지 않는 웹 경로를 목표로 한다 (§12). 로컬 폴더 지속 동기화나 외부 도구는 선택 기능 후보이며, 별도 기능으로 분리했다는 사실만으로 입점·자동화 제한을 피했다고 취급하지 않는다.

## 5. 가능성을 실제 운영으로 바꾸는 작업 패키지

검색을 반복하기보다 다음을 같은 검토 자료로 준비한다.

- 판매자 여정과 제품 화면: 자료 확보, 근거 기반 초안, 개별 승인, 등록, 결과 보고.
- 데이터 흐름: 누구의 어떤 자료가 어디로 이동하고, 어떤 모델·처리자가 쓰며, 언제 삭제되는가.
- 작업별 권한표: 수집·저장·AI 처리·초안·입력 보조·게시·결과 조회를 분리.
- 안전 설계: 계정 최소 권한, 개인 정보 최소화, 감사 이력, 철회·삭제, 오발송·중복·알 수 없는 결과 처리.
- 제한 파일럿 제안: 허용된 판매자·자료·기간·주기·작업만 포함. 제품 오너의 기대가 아니라 실제 기록으로 효과를 보고.
- 사업 조건: 데이터 제공 비용, 수집 지연, 사람 작업 비용, 계약 종료 시 전환·삭제, 실패 시 대체 경로.

일반적인 'AI 자동화가 되나요?' 대신 실제 범위별로 허용·조건·신청 절차를 묻는다. 공식 안내상 솔루션 전체의 사전 검토를 제공하지 않는다는 점을 존중하며, 개별 정책 질의·제휴 상담과 실제 입점 심사를 구분한다. 답변 또는 계약이 불명확하면 허용된 것으로 승격하지 않는다. 이번 문서는 문의 전송이나 외부 접촉을 승인하지 않는다.

네이버 대상 확인 묶음:

1. 같은 Reviewnary 서비스의 멀티채널 CS와 네이버 자료 사용 목적·범위.
2. 매니저 초대 후 사람 수행과 지정 자동 수집 각각의 허용 조건·필드·보관·AI 처리.
3. 리뷰 답글 복사, 입력 보조, 개별 승인 후 게시, 유형별 장기 위임 각각의 조건.
4. 자체결제 적용 범위·결제 보고·환불·구독 해지·기존 외부 고객 연결 조건.
5. 문의 공식 API를 통한 승인 후 발송과 미래 자율 발송의 심사 범위.

제휴사 대상 확인 묶음:

1. 스마트스토어 원출처 리뷰를 Reviewnary에 제공하고 AI 응대 준비에 사용할 권리.
2. 원 리뷰 식별자·상품 매칭·기존 답글·수정/삭제 동기화·업데이트 시각 제공 여부.
3. 답글 API가 자사몰 댓글인지 원채널 답글인지, 게시·결과 조회 권한.
4. 판매자 연결·동의·해지·보관·삭제와 서비스 종료 시 대체 경로.
5. 호출 제한·갱신 주기·SLA·비용·판매자별 최소 비용.

외부 허가를 100% 보장할 수는 없다. 대신 모든 후보에 필요한 근거·담당자·다음 행동·성공 기준을 붙이고, 거절된 수단이 있어도 업무 자체는 다른 허용 경로로 이어가게 설계한다. 데이터 접근이 끝내 확보되지 않는 채널은 출시 필수 의존성으로 두지 않는다.

## 6. 해자와 외부 도구의 역할

- 핵심 자산은 판매자별 상품·모델 지식, 유효한 정책, 응대 기준·말투, 실제 수정 사유, 해결 절차, 후속 관측의 연결이다.
- 동일 상품의 채널 간 연결은 정확히 확인한다. 네이버에서 얻은 지식의 재사용은 출처별 목적·계약 범위에 제한되며, 기술적으로 결합할 수 있다는 이유만으로 허용하지 않는다.
- 판매자 간 공유·모델 학습은 별도 권한 검토 영역이다. 판매자 동의만으로 원플랫폼·고객 자료의 모든 권리가 해결된다고 가정하지 않는다.
- 범용 agent와 Aside는 허용된 조사·자료 처리·작업 준비의 도구 후보다. 성능이 좋아지면 교체하고, 같은 평가 사례로 품질·비용·재현성을 비교한다.
- 해자는 원문 보유량이나 프롬프트가 아니라 같은 문제가 다시 생겼을 때 더 적은 판매자 개입으로 정확히 처리하는 능력이다.
- 지표 후보: 건당 판매자 개입 시간, 의미 있는 수정 비율, 사실·정책 오류, 놓친 대응 업무, 중복 게시, 관측 가능한 후속 문의. 게시 완료와 문제 해결은 구분한다.

## 7. 지금 고정할 구조와 유보할 것

> 이 절의 "하나의 SaaS"·중앙 서버 전제는 2026-10-16 이전 서술이다. 실행 위치는 §17과 `docs/product-scope-v1.md` v1.14 ①을 따른다. 업무 모델(지식·판단·개별 승인·결과 상태)은 유지된다.

**확정한 중심 구조 (§12):** 하나의 SaaS·공통 업무 모델·판매자별 지식과 기억·교체 가능한 수집/실행 어댑터·작업별 권한·개별 승인·정확한 결과 상태. 외부 허가와 구현 완료를 뜻하지 않는다.

**유보:** 네이버 리뷰의 최종 연동사, 수동 파일 처리의 상용 조건·주기, 외부결제 승인, 네이버 무인 게시·포괄 위임 허용 여부, 신규 채널 출시, 세부 화면과 threshold. Aside 필수 설치는 §12에서 초기 기본 의존성에서 제외한다. 수집 경로의 불확실성을 이유로 상품 지식·판단·대응 준비 개발 전체를 정지하지 않는다.

Cafe24는 오너가 검증한 API 경로를 활용하는 기준 채널로 둔다. 필요 없이 같은 API 존재 여부 조사부터 반복하지 않는다. 아임웹은 신규 후보이며 현재 제품 채널 집합에 바로 추가하지 않는다. 쿠팡 리뷰를 답글 가능한 채널로 바꾸거나 허가되지 않은 수집을 상용 기본 경로로 삼지 않는다.

이 구조를 기준으로 다음 구현 대조에서는 '구현됨'과 '동작 증거', '허용 근거', '상시 운영'을 분리한다. 인터뷰 재개 전에는 큰 구조의 검토를 먼저 마친다.

## 9. NAVER / Coupang / Cafe24 실행 구조 상세

> 이 절의 입점·중앙 SaaS 연결 전제(특히 §9.1 "내스토어 앱 인증정보를 상용 연결에 쓰지 않는다")는 초기 조사안이다. 판매자가 자기 PC에서 자기 앱 인증정보로 직접 호출하는 현재 구조는 §17.5, 브라우저 자동화의 제품 범위는 v1.14 ⑦을 따른다.

2026-10-14 추가 검토. 아래는 출시 구조 제안이며 동작 완료 선언·정책 허가·실행 지시가 아니다. Cafe24 API 존재 여부의 검증을 다시 요구하지 않는다.

### 9.1 네이버

**연결:** CS 솔루션 입점·판매자 구독/인증을 우선, API대행사는 별도 공식 대안. 판매자센터 로그인 비밀번호를 받거나 내스토어 앱 인증정보를 상용 서비스의 연결 방식으로 사용하지 않는다.

**문의:** 공식 상품 문의·고객 문의의 정확한 지원 범위를 선언한다. 조회 -> 상품·정책·과거 응대 조회 -> 대응 준비 -> 개별 승인 -> 허용된 답변 API -> 결과 확인을 목표로 한다. TalkTalk 등 별도 표면까지 같은 API로 지원한다고 표시하지 않는다. 모델 confidence와 API 제공만으로 무인 답변의 심사·운영 조건까지 충족했다고 취급하지 않는다.

**리뷰:** 판매자 직접 공식 파일 제공과 허가된 연동을 같은 자료 모델로 받는다. 식별자·기간·상품·답글 포함 여부를 실제 파일/제공 명세로 검증한다. 미답변 상태나 기존 답글이 없는 자료는 추측하지 않는다. 최근 자료를 다시 받으면 새 리뷰·변경·실제 확인된 답글 상태만 반영하고 단순히 파일에서 빠진 행을 삭제로 판정하지 않는다.

**리뷰 게시:** §12 결정에 따라 개별 승인 후 운영 담당자가 직접 등록하는 경로를 기본으로 한다. 판매자 직접 등록은 대체 경로다. Reviewnary 내 승인, 클립보드 복사, 담당자/판매자 완료 신고, 채널에서 실제 확인된 게시를 서로 다른 기록으로 관리한다. 직접 연동사 댓글 API는 원본 네이버 답글 지원 여부를 확인하기 전 호출 경로로 승격하지 않는다.

**Aside 조건:** 설치가 없으면 사용할 수 없는 입점 기능과 사전 허락 없는 자동 화면 수집/입력/게시를 상용 기본으로 두기 어렵다. 사람이 로그인하거나 마지막 등록 버튼을 누르는 것만으로 앞선 자동 수집·입력의 허가가 성립하지 않는다. 리뷰 조회, 입력 보조, 제출은 각각 허용 범위를 확보한다. 특정 허가를 확보해도 입점의 필수 설치 제한은 별도로 해결해야 한다.

**확보할 결과:** 매니저 기반 수집·저장·AI 처리의 범위별 허용 조건, 제휴사 데이터 재제공 계약 또는 네이버 지정 경로. 게시 권한은 수집 권한과 별개. 해지·철회 시 자동 접근 중단·자료 처리 조건도 포함한다. 허가된 방식이 서버/제휴사 API라면 Aside를 유지하기 위해 브라우저 경로로 다시 바꾸지 않는다.

### 9.2 쿠팡

**연결:** 공식 WING OpenAPI 연동 설정과 연동업체 절차를 따른다. 최신 가이드는 목록에 없는 업체의 직접 입력 경로도 설명한다. 등록 여부·계약·저장/AI 처리 조건을 별도로 확인하며, 네이버의 내스토어 앱 제한을 쿠팡에 그대로 일반화하지 않는다. API 키는 backend의 보호된 연결 계층만 다루고 LangGraph나 LLM에 전달하지 않는다.

**문의:** 상품별 고객문의 공식 조회/답변 API로 처리한다. 콜센터 문의는 별도 범위이며, 현재 제품 계약에 없는 개인정보 노출 경로를 이번 제안으로 추가하지 않는다. 승인 대상과 실제 보낼 문장의 버전을 일치시키고, 불명확한 응답은 조회로 확인하기 전 자동 재발송하지 않는다. 키 유효기간 180일·14일 전 재발급 가능 안내에 맞춰 유효기간을 알고 있는 연결의 갱신을 안내한다. 브라우저로 재발급 버튼을 자동 클릭하는 구조를 기본으로 삼지 않는다.

**리뷰:** 2026-10-14 공개 API 카탈로그에 리뷰 조회/답글 endpoint가 없다. 저장소의 이전 판매자 화면 확인은 공식 export·판매자 답글 미지원으로 기록돼 있지만 오늘 화면의 재확인은 하지 않았다. 따라서 쿠팡 리뷰를 답글 승인 큐로 구성하거나 '엑셀을 받으면 된다'고 약속하지 않는다.

자료 확보 후 가능한 업무는 상품 사용 문제·반복 불만·안전 우려·안내 누락의 대응 준비다. 상품/옵션 단위 근거와 확인된 판매자 귀속을 보존하며, 결합된 카탈로그 리뷰를 해당 판매자의 거래 결과로 단정하지 않는다. 리뷰만으로 고객/주문을 특정하거나 연락처를 찾아 개별 연락하지 않는다. FAQ·상세페이지 개선은 향후 승인 과제로 준비하고, 이번 제안으로 상품 수정 기능을 실행하지 않는다.

**Aside 조건:** 일반 이용약관의 자동 접근 제한과 WING 판매자 계약의 구체적 적용을 구분한다. 기존 repo policy gate는 WING 리뷰를 `POLICY_UNCLEAR`로 두고, 개발 posture `PILOT_ALLOWED` · GA `POLICY_GATED`로 기록한다. 외부 LLM 사용은 D6 개정에 따라 AI triage pilot에 한정된다. 기술 proof·내부 파일럿 허용은 플랫폼 허가가 아니다. 상용 기본으로 채택하려면 현재 판매자 계약 및 쿠팡의 구체적 허용 범위를 확인해야 한다.

**확보할 결과:** 판매자 본인 WING의 제한된 읽기·저장·AI 분석에 대한 명시적 조건, 공식 자료 전달 방법 또는 해당 용도의 제공 권한이 있는 연동사. 공식 리뷰 export는 아직 확보되지 않았으므로 대체 경로로 존재한다고 가정하지 않는다. 확보 전에는 허용된 API 업무를 운영하고 리뷰 coverage 부족을 표시한다. 특정 리뷰만 판매자가 직접 제공하는 경로도 자료 사용 조건 검토 뒤 제한적으로 사용할 후보이지, 상시 리뷰 모니터링의 대체 증명이 아니다.

### 9.3 Cafe24

**연결:** 오너가 검증한 OAuth/API 경로를 사용한다. API 재조사부터 반복하지 않고 실제 상품·게시판·답변 표현과 지원 범위를 제품 업무에 연결한다.

**리뷰·문의:** 게시판형 자료의 조회 -> 지식 결합 -> 판단·초안 -> 개별 승인 -> 정확한 원문에 댓글/답변 -> 결과 확인을 목표로 한다. 게시판 설정과 댓글·답변글 의미, 비밀글, 원출처를 보존한다. 게시글 등록과 댓글 등록은 같은 작업이 아니며, 댓글 API 존재만으로 모든 문의 응답 방식이 같다고 가정하지 않는다. 토큰 갱신은 공식 OAuth 흐름으로 구현하고, 권한 추가가 필요하면 판매자 재동의를 요청한다.

크리마 등 외부 리뷰 앱이 원본 저장소인 경우 해당 앱의 정식 연결을 별도로 사용한다. Cafe24 API로 모든 외부 앱 자료가 내려온다고 가정하지 않는다. 네이버에서 가져온 리뷰가 자사몰에 보인다고 네이버 원본 답글을 Cafe24 API로 게시할 수 있는 것도 아니다.

**Aside 조건:** 기본 수집·답글 실행은 API이므로 Aside가 필수가 아니다. 선택적인 외부 도구가 운영 보조를 하더라도 자료 처리·권한 범위와 backend-only LLM egress 계약을 따라야 한다. API에 없는 표면을 브라우저로 처리하려면 그 표면의 허용 조건을 따로 확인한다.

**상용화:** 앱 심사·결제·데이터 처리 조건은 API 기술 검증과 별개로 마무리한다. 같은 SaaS라도 Cafe24 결제 계약을 외부 결제로 우회하지 않는다. 필요하면 제품 계정·구독 권리는 통합하고 채널별 계약을 따르는 결제 어댑터를 둔다.

### 9.4 Aside와 기존 collector의 위치

§12 결정은 'Aside 전면 삭제'가 아니라 **'필수 수집 엔진에서 허가된 도구 후보로 변경'**이다. 기존 필수 설치 합의는 초기 기본 경험에 대해서 이 결정으로 대체한다. 특정 Aside 기능의 허가·구현은 별개다.

- 플랫폼에 의해 허가된 브라우저 업무: 구체적인 표면·행동·빈도·자료 범위 안에서만 연결. 별도 제품 배포 조건도 만족해야 함.
- Reviewnary 자체 화면 또는 판매자가 처리 권한을 가진 작업 공간: 역할별 접근과 자료 처리 조건을 충족한 경우 보조 도구 후보. 권한이 넓은 범용 agent를 무조건 연결하지 않음.
- 플랫폼 밖의 자료 처리: 모델/외부 도구의 데이터 취급 조건과 실제 기능을 확인한 뒤 검토. Aside가 로컬 문서 처리나 플랫폼에 허용된 특정 기능을 제공한다고 이번 문서가 보증하지 않음.
- 플랫폼의 무허가 자동 수집·입력·게시: 사람의 마지막 클릭, 로컬 실행, 별도 앱, 이름 변경만으로 허용되지 않음.

기존 collector 코드는 삭제하지 않는다. 정규화·중복 제거·상품 연결·자료 범위 검증·작업 상태를 입력 수단과 분리하고, 브라우저 adapter는 별도 정책 상태로 관리하는 것을 향후 구현 과제로 제안한다. 자동 브라우저 수집을 쓰지 않으면 세션/도우미 상태가 전체 서비스의 필수 조건일 이유도 없다.

공식 API 운영은 실제 always-on backend가 있는 경우 PC 꺼짐과 독립될 수 있다. 로컬 브라우저 작업은 PC·도우미·브라우저 세션이 준비돼야 한다. '24시간 작동'이나 '전 채널 실시간 리뷰 관측'을 통합 배지로 표시하지 않는다.

## 10. 채널 연결 자격·리뷰 쓰기 UX·기존 툴 추가 조사

2026-10-14 추가 검토. §9에 덧붙이는 제안과 공개 근거이며 확정된 구현 계약이 아니다. 인터뷰는 재개하지 않는다. 실제 판매자센터 접속·새 권한 발급·외부 문의·게시 실행은 하지 않았다.

### 10.1 먼저 구분할 네 가지

- 판매자 자기 계정의 API 발급 가능 여부.
- 제3자 SaaS의 상용 연결·데이터 처리 자격.
- 특정 작업의 실제 API 존재와 scope.
- 브라우저 자동 수집·입력·게시의 허용과 설치형 제품 배포 조건.

하나가 충족돼도 다른 셋을 대신하지 않는다. '세 채널 모두 법인을 설립하고 앱마켓에 입점해야 API 시험이 가능하다'고 일반화하지 않는다. 사업자 등록과 법인 설립도 서로 다른 개념이다.

### 10.2 상용 연결과 법인 요건

| 채널 | 추천 상용 연결 | 공개 문서에서 확인한 자격 | 개발·시험과 구분 |
|---|---|---|---|
| NAVER | 솔루션 입점·구독/인증 또는 API대행사 | 현재 공개 입점 동의 가이드는 국내 법인 계정 대상이라고 안내하며 본문 기준 표시는 24.10. 대행사 공식 답변에도 국내 법인 요건 설명 | 판매자의 직접 내스토어 앱 개발과 외부 SaaS 운영은 다름. 외부 서비스에 내스토어 앱 정보를 위탁하는 방식으로 우회하지 않음 |

네이버 출시를 직접 추진하는 경우 국내 법인 요건은 실제 준비 과제다. Cafe24와 쿠팡까지 같은 법인 요건이라고 단정하지 않는다. 네이버 가이드의 대상 확대 여부·쿠팡 사업자 유형·Cafe24 필요한 개인정보 scope 자격은 신청 시점에 확인한다. 법인이 있어도 리뷰 자동 수집·게시 권한이 생기는 것은 아니다.

### 10.3 상품 정보 확보

| 채널 | 기술 경로 | 설계할 범위 |
|---|---|---|
| NAVER | 상품 목록 + v2 원상품/채널상품 상세 | 상품 식별·모델/옵션·설명·이미지 참조·배송 조건을 해당 API의 실제 응답과 신청 권한 안에서 확보 |
| Coupang | 판매자 상품 목록 + 상품 상세 + 필요한 재고/가격/상태 read | 상세 응답의 이미지·고시·옵션 속성·contents 및 배송/반품 조건. 노출 카탈로그와 판매자 리스팅의 차이를 보존 |
| Cafe24 | 상품 목록/단건 + 옵션·품목·재고 관련 read | 실제 상품 설명·이미지·옵션 및 채널별 운영 조건을 확보. 각 read의 scope와 실제 반환 필드 확인 |

목록 API만으로 지식을 완료했다고 표시하지 않는다. 상세 HTML/이미지 참조 확보와 이미지에서 검증된 사실 추출은 다른 단계다. 참조 이미지의 취득·AI 처리 조건도 확인한다. 확보한 설명·정책은 원출처와 버전·적용 상품을 유지하며, 암묵지는 채팅·판매자 자료로 보완한다. API 자료 사용 권한과 다른 채널에 재사용할 권한은 분리한다.

### 10.4 네이버 리뷰 쓰기 UX의 네 단계

**A. 웹만으로 가능한 후보: 검토·복사·찾기·등록을 연속 작업으로 설계.**

1. 리뷰 원문·상품·날짜·현재 초안을 업무 한 건으로 묶는다. 식별 정보가 부족하면 같은 리뷰라고 단정하지 않는다.
2. 근거가 준비된 초안을 판매자가 개별 확인한다. '답변 확정·복사' 동작으로 우리 초안 버전을 고정하고 복사할 수 있게 한다.
3. 판매자센터를 한 번 열고 Reviewnary 작업창을 옆에 유지한다. 검증된 개별 링크가 있으면 사용하고, 없으면 상품·기간·원문 일부 등의 검색 단서를 보여준다. 링크가 존재한다고 추정하지 않는다.
4. 판매자가 대상과 초안을 대조한 뒤 직접 붙여넣고 네이버에서 등록한다.
5. Reviewnary에서 '등록했다고 표시'하면 판매자 신고로 기록하고 다음 업무로 이동한다. 공식/허가된 재조회로 확인하기 전에는 채널 확인 완료로 승격하지 않는다.

불필요한 탭 왕복·재검색·중복 검토를 줄이는 것이 목적이다. 중요도 큐와 별개로 확정된 업무의 처리 세션을 상품·기간 등으로 묶을 수 있지만, 일괄 승인으로 바꾸지 않는다. 순서만 보고 동일 리뷰를 자동 매칭하지 않는다. 다음 초안 복사는 명시적인 클릭을 통해 수행하고 다른 업무의 클립보드를 백그라운드에서 덮어쓰지 않는다.

작업창은 우리 서비스의 별도 웹 창 또는 사용자가 나란히 배치한 창이다. 네이버 화면을 iframe에 담거나 교차 출처 DOM을 읽는 기능이 아니다. 지원 브라우저에서는 Document Picture-in-Picture로 우리 작업창을 항상 위에 표시하는 후보도 있다. 제한된 브라우저 호환성·사용자 동작·보안 조건을 확인하고 일반 웹 창 대체 경로를 둔다. 해당 UX 자체가 심사 승인됐다고 취급하지 않는다.

**B. 판매자센터 안에서 초안을 제공하는 보조 기능: 별도 허가 후보.**

사용자가 현재 연 리뷰 한 건에 대해 AI 초안을 보고 명시적으로 입력 적용, 네이버 등록은 직접 수행하는 방식이다. 작성 지점에서 작업하므로 복사·대상 찾기 부담을 줄일 수 있다. 그러나 선택 리뷰 읽기·AI 전송·입력 자동화와 확장 프로그램/별도 앱 의존은 각각 정책 검토 대상이다. 마지막 등록 클릭만 사람에게 남긴다고 허가된 경로가 되지 않는다. Aside 또는 확장 프로그램을 사용하려면 실제 플랫폼 허용과 배포 조건을 먼저 확보한다.

**C. 허가된 연동사 실행 API: 제휴 후보.**

Reviewnary에서 개별 승인 -> 원채널 식별자와 확정된 초안 버전을 연동사에 전달 -> 네이버 원본에 게시 -> 결과 조회/감사 기록. 계약에서 원채널 게시·외부 SaaS의 API 사용·재위탁·AI 처리·수정/삭제·중복 제어·결과 조회를 확인한다. 연동사의 기능이나 입점 상태만으로 우리에게 권한이 이전되지 않는다.

**D. 사람이 수행하는 관리 대행: 비용을 포함한 서비스 후보.**

판매자가 승인한 정확한 답글을 권한 있는 담당자가 직접 등록하고, 처리 증거와 상태를 돌려준다. 판매자가 옮겨 붙이는 시간을 줄일 수 있지만 사람 수행 비용·SLA·최소 권한·위탁 계약이 필요하다. 플랫폼이 해당 대행·자료 처리를 허용하는지 확인하며 직원 계정을 봇으로 바꾸는 경로로 사용하지 않는다.

추천은 A를 검증 가능한 초기 경험으로 설계하되 B/C의 권한 확보를 병행하는 것이다. A가 최종 목표라고 고정하지 않는다. 운영자가 시간을 충분히 절감하지 못하면 A의 효과가 부족하다고 인정하고 다른 경로를 확보한다. 직접 게시 능력을 보유한 툴에 AI 모듈을 공급하는 방식도 C의 다른 사업 구조 후보이며, 명의·키를 빌리는 것이 아니라 플랫폼이 허용한 제품과 계약 안에서 공급해야 한다.

실행 연동 후보를 확인할 때는 (1) 실제 게시 대상, (2) 인증 흐름, (3) 플랫폼이 허용한 범위, (4) 외부 서비스 사용 가능 계약, (5) 실제 완료 응답·재조회 방식을 요구한다. 플랫폼 계약 전체 공개가 어렵다면 해당 기능·사용 목적에 대한 확인 가능한 증빙/공동 확인을 요청하는 후보로 둔다. 이번에는 연락하지 않았다.

### 10.6 쿠팡 리뷰 경로의 추가 후보

이번 현재 공개 카탈로그에서 리뷰 조회/답글 endpoint를 찾지 못했다. 공식 WING 상품평 엑셀 다운로드는 공개 자료로 확인하지 못했고 로그인 화면도 열지 않았다. '리뷰 엑셀 파일을 주는 확장 프로그램'은 공식 쿠팡 내보내기와 다르다.

새로운 구체적 후보: 크리마의 2026-07-30 공식 안내는 쿠팡을 포함한 외부 플랫폼 리뷰의 과거/정기 연동을 제공한다고 설명한다. 이를 쿠팡 리뷰 입력의 제휴 검토 대상으로 추가한다. 원자료 취득의 허용 근거, Reviewnary에 제공하는 권리, 갱신 주기·상품/옵션 식별·판매자 귀속을 확인해야 한다. 자사몰 재노출 기능을 우리 서비스의 운영 분석 권리로 가정하지 않는다.

쿠팡 리뷰는 현재 답글 게시 업무를 만들지 않는 방향을 유지한다. 읽은 리뷰가 특정 판매자의 거래에 귀속되는지 확인하고 반복 상품 문제·안내 개선·운영 위험을 준비한다. 리뷰 작성자에게 다른 채널로 연락하는 기능은 대체 게시 경로가 아니며 새로 제안하지 않는다. 동일 카탈로그에 여러 판매자의 리뷰가 합쳐질 수 있다는 사실을 운영 판단에 반영한다.

### 10.7 Aside를 유지할 수 있는 정확한 위치

- **네이버 필수 브라우저 수집·게시 엔진:** 지금 확보된 근거로는 상용 기본 채택이 어려움. 작업 자동화 허용과 필수 설치 제한을 모두 풀어야 함.
- **쿠팡 로컬 공식 API 클라이언트:** 공식 안내에 존재하는 경로. 이를 근거로 로컬 도우미 전체를 금지한다고 단정하지 않음. 이는 Aside의 WING 화면 수집 허가가 아니며 서버형 SaaS를 위장하는 방법도 아님.
- **Cafe24 공식 API 작업:** Aside가 없어도 운영 가능. API에 없는 작업을 하려면 따로 허용 범위 확인.
- **공통 AI의 도구:** 허가된 자기 서비스/작업 공간의 보조, 승인된 외부 자료 처리, 플랫폼이 허용한 특정 브라우저 업무의 교체 가능한 어댑터 후보. 범용 agent의 무제한 화면 접근 권한을 부여하지 않음.

제품의 핵심 자산은 Aside가 어떤 버튼을 누르는지가 아니라, 상품·판매자 기준·업무·근거·승인·결과의 연결이다. 해당 도구가 사용할 수 없는 채널에서도 이 자산을 유지한다.

## 11. 판매자 승인 후 운영 담당자의 지연 수동 등록

2026-10-14 조사. 오너는 이번 후보에서 '내가 나중에 입력'의 의미가 **프로그램/Aside의 자동 입력이 아니라 운영 담당자의 직접 등록**이라고 확인했다. 이는 검토할 모델의 범위 확인이며 상용 모델 확정·매니저 초대·자료 다운로드·실제 게시 실행 승인이 아니다.

### 11.1 공개 근거에 따른 판정

**기능과 권한 측면에서 실행 가능한 대행 모델이라는 근거가 있다.** 네이버의 매니저 권한표는 계정 부매니저와 대행사에 문의/리뷰관리 메뉴 접근을 제공하고, 대행사 역할을 일부 운영 업무 대행용으로 설명한다. 공식 리뷰 FAQ는 리뷰 팝업에서 댓글을 작성하고 저장하는 방법, 등록 후 수정·삭제 기능을 안내한다.

다음 모델을 제안할 수 있다: 담당자가 정식으로 초대받은 자기 계정으로 필요한 자료를 직접 확보하고, Reviewnary가 대응을 준비하며, 판매자가 정확한 문장을 개별 승인한 뒤, 담당자가 판매자센터에서 해당 문장을 직접 붙여넣고 저장한다. 승인과 저장 사이의 시간차 자체를 위 안내에서 금지하는 내용은 확인하지 못했다. 이것을 모든 약관에 제한이 없다는 전수 법률 판정으로 확대하지 않는다.

이번 공개 근거는 유료 대행 서비스의 모든 조건, 엑셀의 외부 저장·AI 처리, 상용 솔루션 심사까지 포괄 승인하는 문서가 아니다. 스마트스토어 판매 이용약관 전문은 공식 FAQ의 약관 링크가 판매자센터 SPA로 연결돼 이번 web 도구에서 확보하지 못했다. 해당 조건은 상용 출시 전 전문·적용 계약과 대조하고 필요한 정책 질의를 진행한다. 범위가 좁혀진 사람 수행 대행에 대해 무조건 별도 자동화 허가가 있어야만 한다고 단정하지 않는다.

부매니저는 READ-only 역할이 아니다. 실제 가능한 메뉴와 기능을 기준으로 제한해야 한다. 공식 대행사 역할도 후보로 비교하되, 리뷰 댓글·파일 내보내기의 구체적 작업 권한은 실제 계정에서 별도 확인한다. 판매자 비밀번호·OTP를 공유하지 않는다.

### 11.2 추천 판매자 경험

```text
담당자의 직접 자료 확보 -> AI 대응 준비
                               |
판매자: 초안 확인/수정 -> 개별 등록대행 승인
                               |
등록 대기 + 다음 처리회차/예상 시각 + 취소 경로
                               |
담당자: 현재 리뷰·답글·승인 상태 대조 -> 직접 등록
                               |
실제 결과 기록 -> 판매자에게 묶어서 보고
```

- 승인 버튼은 사람이 나중에 처리한다는 의미를 분명히 한다. 승인과 동시에 등록된 것처럼 표시하지 않는다.
- 승인 이후 불필요한 대기시간을 강제하기보다 운영 가능한 '다음 처리회차'를 안내한다. 처리시간·등록 마감·운영시간·용량은 실제 운영 인력과 작업시간 측정으로 정한다. 판매자가 특정 시각을 지정할 수 있어도 담당자가 즉시 처리할 능력이 있다고 약속하지 않는다.
- 처리 전에는 취소를 제공한다. 담당자가 이미 처리 중이면 취소 요청 상태를 표시하고 중단 확인 전 취소 완료로 표시하지 않는다. 사람의 저장과 취소 사이의 경쟁을 완전히 원격 차단할 수 있다고 주장하지 않는다.
- 일반 업무는 회차별로 묶어서 담당자가 처리하고 결과를 묶어서 보고한다. 판매자 승인은 기존 합의대로 개별이다. 긴급한 업무가 다음 회차까지 기다려야 한다면 실제 가능한 긴급 대응 경로와 한계를 알린다.
- 자료 확보 시점과 등록 처리 시점을 분리한다. 담당자의 주기적 파일 확보로 아직 들어오지 않은 리뷰를 관측했다고 말하지 않는다.

### 11.3 내부 운영 큐의 최소 계약

| 조건 | 운영 원칙 |
|---|---|
| 승인 대상 | 판매자·스토어·리뷰 식별·원문 버전·답변 버전·승인자를 묶어서 기록 |
| 승인 후 내용 변경 | 새 버전을 다시 승인받음. 담당자는 임의로 문장을 수정하지 않음 |
| 담당 배정 | 한 업무는 한 담당자만 맡음. 외부 플랫폼의 다른 직원 게시까지 이 잠금이 막지는 못함 |
| 등록 직전 | 최신 승인·취소 상태, 리뷰 변경·삭제, 기존 답글, 시점 의존 사실을 직접 재확인 |
| 이미 답글 존재 | 중복 등록/덮어쓰기를 하지 않고 상태 확인. 수정·삭제는 별도 승인 범위 |
| 결과 불명확 | 실제 게시 여부를 확인하기 전 다시 등록하지 않음 |
| 완료 기록 | 담당자·처리 시각·실제 대조 결과·답변 버전·확인 방법. 복사나 승인만으로 완료 판정하지 않음 |
| 계정·자료 | 스토어별 격리, 최소 권한, 해지 시 회수, 목적 외 사용 금지, 접근·삭제 기록 |

완료의 근거가 담당자의 직접 화면 확인이면 그 방법으로 명시한다. 시스템 자동 확인으로 가장하지 않으며 원문/개인정보가 포함된 전체 화면 캡처를 기본 감사 증거로 요구하지 않는다. 새 내부 담당자 기능은 기존 데모의 판매자 직원 초대 기능과 다르며, 구현 전 현재 권한·안전 계약과 별도 대조가 필요하다.

### 11.4 개인정보와 상용화 조건

리뷰·파일·문의에 개인정보가 포함돼 처리 위탁에 해당하는 경우, 개인정보 보호법 제26조의 위탁 문서·업무/수탁자 공개·보호조치·감독·목적 제한을 검토한다. AI 제공자나 외부 등록 담당자에게 다시 맡기는 경우 재위탁·국외 처리 등 적용 조건을 별도로 확인한다. 국내 모델이라는 사실만으로 이 조건을 충족하지 않는다.

판매자 승인 UI는 개별 답글의 업무 승인이며 개인정보 처리 위탁 문서 전체를 대신하지 않는다. 또한 상용 서비스의 API 연결·솔루션 입점·결제 조건을 사람 등록 모델이 면제하지 않는다. 법인 설립 여부와 사람 대행의 작업 권한은 별개다.

### 11.5 이 모델의 사업적 의미

**판매자 UX를 먼저 완성하고, 실행 수단은 교체 가능한 구조다.** 허용 조건을 충족한 수동 등록을 초기 운영 경로로 두고 향후 원채널 게시 권한을 가진 정식 연결이 확보되면 같은 승인 업무의 실행 어댑터를 교체할 수 있다. 아직 확보되지 않은 자동 게시까지 서비스가 제공한다고 광고하지 않는다.

판매자의 반복 클릭은 줄지만 서비스 측 사람 작업·인력 확보·지연·오등록 비용이 발생한다. 건당 찾기/검증/등록/재확인 시간을 실제 자료로 측정하고 승인 건수에 따른 처리 용량과 가격을 정한다. 직접 부매니저 초대와 수동 등록은 기술 검증 후보이지 지금 상용 적법성·수익성이 모두 증명된 모델이 아니다.

## 12. 오너 확정: API와 사람 수행을 결합한 운영 AI

> 이 절의 "하나의 SaaS"·중앙 서버 전제는 2026-10-16 이전 서술이다. 실행 위치는 §17과 `docs/product-scope-v1.md` v1.14 ①을 따른다. 업무 모델(지식·판단·개별 승인·결과 상태)은 유지된다.

2026-10-15 오너 결정: '좋아 일단 이렇게 제품을 고정하자.' 이는 직전 하이브리드 구조 권고의 채택이며, 제품의 실행 목표를 소유한다. 앞선 제안 중 아래와 충돌하는 기본 경로는 이 결정으로 대체한다.

1. 하나의 SaaS에서 AI가 상품 지식·판매자 기준·과거 대응을 활용해 업무를 판단하고 대응을 준비한다. 판매자는 단기에는 개별 업무의 정확한 내용을 확인·수정·승인한다.
2. 공식 API로 실행할 수 있고 필요한 자격·계약·권한을 갖춘 업무는 API로 실행한다. 불필요하게 전부 사람에게 넘기지 않는다. API 제공, 상용 자격, 실제 동작 증거는 계속 구분한다.
3. 네이버 리뷰는 초기에는 권한 있는 담당자의 주기적 공식 파일 확보·연동과, 개별 승인 후 담당자의 판매자센터 직접 등록을 기본 목표로 한다. 사람 수행의 접근 권한, 파일 외부 보관·AI 처리·위탁 등 상용 조건과 실제 파일 지원 범위는 출시 전 검증한다. 판매자가 파일을 제공하거나 직접 등록하는 대체 경로도 유지한다.
4. 네이버 문의와 Cafe24의 지원 업무는 허용된 API 경로를 활용한다. 쿠팡은 공식 지원 문의 업무를 처리하며, 리뷰 답글 기능을 만들거나 미확인 리뷰 수집을 지원한다고 약속하지 않는다. 쿠팡 리뷰의 합법적 자료 확보는 별도 미해결 과제다.
5. 판매자 경험은 승인 -> 등록 대기 -> 처리 중 -> 실제 등록 확인으로 연결한다. 예상 처리회차·취소·변경 재승인·중복 방지·불명확한 결과 확인·묶음 보고는 §11의 원칙을 따른다. 주기적 자료 확보를 실시간 모니터링으로 표시하지 않는다.
6. Aside/범용 agent는 초기 필수 설치 조건이 아닌 선택적 도구다. 플랫폼·자료·행동별 허용 범위에서 활용하며, 향후 허용된 실행 경로가 생기면 수집/실행 어댑터를 교체한다. 미래 자동화 허가 획득을 사업 성립의 전제로 두지 않는다.
7. 장기 목표는 판매자가 허용된 유형별 업무를 위임하는 판매 운영 AI다. 해자는 수작업 인력이나 원문 양이 아니라 판단 기준·지식·수정 이유·실행·관측 결과의 연결과 다음 업무에서 확인되는 개선이다.
8. 사람 수행의 건당 시간·처리 용량·오등록·지연·판매자 절약시간을 측정한다. 개발자 본인의 무제한 수작업을 지속 운영 모델로 두지 않는다.

외부결제, 서비스 입점, 구체적 사업자 자격·개별 처리 계약의 승인이 확정된 것은 아니다. 현재 READ-only Operator나 라이브 승인 계약을 바꾸지 않으며, 새 실행 계층의 구현 착수 전 정합성을 대조한다.

## 13. 초보자 온보딩과 개인사업자 단계 검토

2026-10-15 공개 자료 확인. 오너는 초기 API 연결·부매니저 등록을 모르는 사람도 수행할 수 있도록 highlight 등을 활용한 튜토리얼을 요구했다. 실제 외부 페이지 주입 방식까지 확정하거나 구현을 지시한 것은 아니다.

### 13.1 튜토리얼의 표시 위치와 권한

| 방식 | 권고와 한계 |
|---|---|
| Reviewnary 자체 화면의 highlight·단계 안내 | 기본 경로로 권고. 외부 화면 자동 읽기/조작 없이 구현 가능 |
| 우리 안내 창 + 판매자가 직접 여는 공식 화면 | 설치 없는 기본 경로 후보. 예시 화면의 해당 위치 강조, 메뉴 경로, 담당자 초대 정보 복사, 진행 저장·도움 요청 제공 |
| 실제 판매자센터 화면 위에 삽입하는 highlight | 보통 확장 프로그램·스크립트·별도 앱 또는 플랫폼 협력이 필요. 단순 설명과 수집/자동 입력을 분리해서 검토하되, 설치가 필수인 입점 솔루션에 대한 제한과 충돌 가능. 무조건 허용/금지로 단정하지 않음 |
| 사용자 주도 화면공유로 사람이 안내 | 막힌 경우 보조 후보. 로그인·OTP·초대 확정은 판매자가 직접 수행, 민감 화면 제외·최소 공유·기본 녹화 없음. 실제 적용 조건은 별도 검토 |

일반 웹 페이지는 동일 출처 정책상 다른 출처 페이지의 내부 요소를 자유롭게 읽거나 수정할 수 없다. 새 탭/iframe으로 열었다는 것만으로 외부 화면에 highlight하거나 단계 완료를 자동 관찰할 수 있는 것은 아니다. 보안 제한을 해제하거나 외부 페이지를 중계·복제하는 방식으로 우회하지 않는다.

네이버 공식 상용 연결에서는 판매자에게 '내스토어 앱을 만들어 키를 넘기라'고 안내하지 않는다. 솔루션 구독·공식 인증 또는 정식 대행사 지정 절차를 안내한다. 부매니저 초대는 별도 필요 권한으로 설명한다. '초대했어요'라는 자기 신고, 담당자 초대 수락, 실제 접근 확인을 구분한다. API 연결 완료는 허용된 공식 응답으로 확인 가능한 범위만 확인한다.

초기 권고는 우리 웹의 가이드와 예시 화면 강조를 기본으로 하고, 공식 화면에서는 사용자가 직접 조작하는 형태다. 실제 페이지 위 highlight는 플랫폼이 허용하는 배포·동작 범위를 확보한 후 추가 검토한다. 가이드에는 마지막 확인일·화면 변경 시 대체 안내·중단 후 재개를 포함하며 기존 가이드가 현재 유지·동작한다는 판정은 하지 않는다.

### 13.2 부매니저 초대와 API 사업자 자격의 분리

- 공식 매니저 초대는 담당자 이름·휴대폰으로 초대하고, 담당자가 SMS 링크에서 커머스 ID로 로그인/가입하여 권한을 수락하는 절차다. 일반 개인 네이버 ID를 통한 가입도 안내한다. 법인 서류를 제출하는 API대행사 등록과 다른 절차이며, 공개 안내에서 초대받는 부매니저의 법인 보유 요건은 확인되지 않는다. 개인사업자로 사람 수행 기반 니즈 검증을 추진할 수 있다는 판단 근거다. 유료 대행·자료 처리 전체의 적법성이 자동 입증된 것은 아니다.
- 네이버 커머스솔루션마켓 개발사 입점은 현재 공개 문서가 국내 법인 사업자만 가능하다고 안내한다. 본문 기준일은 24.10이며 현재 페이지에서 이 제한을 재확인했지만 개인사업자 확대가 완료됐다는 근거는 확보하지 못했다.
- 네이버 API대행사 역시 공식 답변상 국내 법인이 아닌 경우 반려될 수 있다. 부매니저 초대로 외부 SaaS의 공식 API 연결 자격을 대신하거나 판매자의 내스토어 앱 키를 받는 경로로 우회하지 않는다.
- 따라서 개인사업자 검증 단계에서 네이버 API를 외부 판매자에게 직접 제공할 수 있다고 약속하지 않는다. 우선 허용 조건을 충족한 파일·사람 수행으로 검증하고, 네이버 문의 API까지 외부 고객에게 제공할 시점 전에 직접 자격을 확보하거나 해당 사용과 제공이 명시적으로 허용된 정식 제휴 연결을 확보한다. 제휴사의 자격·인증정보를 빌리는 것은 대안이 아니다.
- 개인사업자 -> 법인 전환 시 서비스 계약 주체·처리위탁·개인정보 처리·결제·매니저 권한·API 연결의 변경 절차를 미리 설계한다. 자동 승계나 기존 권한의 무조건 유지를 가정하지 않는다. 전환 시점은 매출 규모뿐 아니라 필요한 공식 연결 자격에도 달려 있다.

### 13.3 개인사업자 니즈 검증의 권고 범위

개인사업자 단계에서 제품의 판단·승인·결과 경험을 검증하는 것과, 모든 채널의 상용 API 연결을 직접 제공하는 것을 구분한다. 아래는 권고 경로이며 오너가 별도로 채택한 출시 범위는 아니다.

| 채널/작업 | 초기 검증 경로와 남은 조건 |
|---|---|
| 네이버 리뷰 | 정식 초대받은 담당자의 허용된 파일 확보·직접 등록. 자료 외부 저장·AI 처리·위탁·유료 제공 조건은 별도 검토 |

## 14. 네이버 문의 유지와 개인사업자 연결 경로 재검토

2026-10-15 추가 조사. 오너는 네이버 문의가 제품의 큰 부분임을 지적하고, 개인사업자로 API까지 포함할 수 있는 경로와 개인화/운영 주체 변경의 영향을 요청했다. 문의 제외나 셀프호스팅 전환을 결정한 것은 아니다. 아래는 §12 제품 목표를 유지하기 위한 연결 후보이며, 외부 권한 획득·구현·문의 전송 승인이 아니다.

### 14.1 직접 자격과 제품 제공을 구분

Reviewnary가 직접 네이버 상용 연동 자격을 확보하는 경우에는 커머스솔루션마켓 또는 API대행사 경로를 비교한다. 마켓 입점만이 유일한 방법은 아니다. 2026-06-17 공식 답변은 API대행사도 국내 법인에 한정한다고 명시하여, 과거 답변의 '반려될 수 있음'보다 분명한 근거를 제공한다. 법인 설립 후에도 신청·테스트·라이브 전환 등 해당 절차가 남는다.

이는 모든 API 이용자에게 법인이 필요하다는 뜻이 아니다. 판매자 본인의 자기 스토어 직접 이용과 다른 판매자에게 제공하는 서비스는 구분된다. 오너가 실제 판매자/이용 주체인 본인 스토어에서는 해당 계정의 내스토어 앱 조건에 맞는 자체 운영을 검증 출발점으로 삼을 수 있다. 가족·고객의 계정이거나 상품이 같다는 이유만으로 본인 스토어로 간주하지 않는다. 자사 운영 증거는 타 판매자에 대한 상용 제공 권한을 입증하지 않는다.

### 14.2 이전 후보: 정식 연동사의 외부 솔루션 연결

후속 오너 요청으로 사방넷 등 외부 툴 경유가 아닌 운영 주체/제품 구조 변경을 우선 검토한다 (§15). 이 절은 조사 이력으로 보존하며 이번 추천 경로가 아니다.

사방넷 공식 개발자 가이드는 외부 부가 서비스를 다수 고객에게 제공하는 Solution 환경, 별도 신청·초대와 오픈 전 심사를 안내한다. 또한 쇼핑몰 상품 문의 수집과 답변 전송 워크플로우를 공개 설명한다. 2026-10-15 공개 브라우저에서 직접 확인했다. 상세 문의 문서는 로그인으로 이동하여 열람하지 않았다. 네이버 상품 문의와 고객 문의 각각의 지원, Reviewnary의 개인사업자 자격, AI 처리·재제공 권리·가격은 아직 확인되지 않았다.

```text
판매자 <-> 정식 연동사: 공식 채널 연결·인증·작업 권한
정식 연동사 <-> Reviewnary: 허가된 파트너 API·최소 데이터
Reviewnary: 상품 지식 -> 문의 판단 -> 답변 준비 -> 개별 승인
승인된 답변 -> 연동사의 허가된 전송 -> 네이버 -> 결과 확인
```

이 설계는 확인할 제휴 후보이지 기존 연동사의 권한이 자동으로 Reviewnary에 확장된다는 주장이 아니다. 네이버 인증정보는 연동사 경계에 두고 자격·키만 대여하지 않는다. 플랫폼 조건과 연동사의 계약이 해당 외부 솔루션·AI 처리·답변 전송을 허용해야 한다. 필요한 경우 연동사가 실제 서비스 제공·처리 책임을 맡는 정식 공급/재위탁 구조도 협의 후보로 검토한다. 허용 범위가 다르면 네이버 확인이 선행되어야 한다.

제휴 검증 항목: 개인사업자 파트너 수락, 네이버 문의 종류별 R/W·답변 수정·결과 조회, 판매자 연결/기존 대행사와의 충돌, 최소 자료·AI 처리·보관·재위탁, 비용·지연·요청 한도, 종료·직접 연결 전환 시 내보내기·삭제. 외부 계약에 없는 데이터나 권한을 기술적으로 호출 가능하다는 이유로 사용하지 않는다.

| 형태 | 정책 판단에 미치는 영향 |

## 15. 판매자 자체 운영형 Reviewnary 후보

> 후속 결정: §16에서 로컬 개발 목표, §17에서 판매자 자체 운영 경계를 채택했다. 이 절의 공개 근거와 미확인 정책 질문은 유지하되, '후보'라는 당시 상태는 현재 제품 방향을 부정하지 않는다.

2026-10-15 후속 오너 요청: 사방넷 등 외부 툴 경유가 아니라 제품의 중추·운영 주체를 변경하여 개인사업자 단계에서도 네이버 문의 API를 포함할 수 있는지 검토한다. 네이버 문의는 제품 목표에 유지한다. §12의 하이브리드 업무 모델을 폐기하거나 SaaS에서 설치형으로 전환 확정한 것은 아니며, 아래는 정책 질의용 설계 후보다.

### 15.1 확인된 경계와 미확인 경계

- 공식 #2283은 판매자가 자신의 스토어에 직접 API를 연동하는 경우 별도 대행사 등록이 불필요하다고 안내한다.
- 공식 #6과 #3463은 타 판매자의 내스토어 앱 인증정보를 받아/위탁받아 서비스를 운영하는 형태를 제한한다. #961은 직접 API대행사 입점의 국내 법인 요건을 명시한다. 마켓 등록만이 유일한 직접 자격 경로는 아니다.
- 위 공개 답변이 외부 공급자의 유료 반복 판매 소프트웨어·로컬 agent·셀프호스팅을 자체 이용으로 일괄 승인한 것은 아니다. #556은 외주 개발 위수탁 정책을 별도 정책 문의로 확인하라고 안내한다. 커머스API 이용약관 전문은 이번 공개 web 조회로 확보하지 못했으며 검색 부재를 허용 증거로 취급하지 않는다.
- 개인화, 전용 서버, MCP, 범용 agent, 키의 로컬 보관, 판매자의 최종 승인만으로 분류가 달라진다고 단정하지 않는다. 실제 수집·처리·통제·유료 공급 관계를 함께 제시한다. 플랫폼 계약 준수와 법률 준수도 별개다.

### 15.2 가장 명확하게 구분할 후보 설계

```text
판매자 소유·관리 PC / 판매자 소유 서버
  판매자 관리 비밀 저장소 -> 공식 네이버 API
  판매자별 DB·상품 지식·업무 큐·승인 이력
  해당 환경의 Spring backend -> 허용된 AI 처리 경로
  credential 없는 LangGraph -> 대응 준비
  판매자 개별 승인 -> 별도 권한 실행 계층 -> 공식 API -> 결과 확인

공급자(Reviewnary): 프로그램·설명서·업데이트·라이선스 제공
  기본적으로 키/토큰/문의 원문/상품 원문/답변/개별 작업 명령을 수신·통제하지 않음
```

키만 로컬인 중앙 SaaS 프록시보다 실제 자체 운영에 가까운 구조를 정책 질의하는 목적이다. 위 항목은 허가를 보장하는 충분조건이 아니다. 판매자 소유 클라우드라도 공급자가 상시 관리자 권한·원격 스케줄/작업 통제를 가지면 그 실질을 공개해야 한다. 유료 소프트웨어·구축·유지보수 제공 자체가 가능한지도 명시적으로 확인한다.

AI는 완전 로컬 처리와 판매자가 직접 계약한 외부 모델 사용을 구분한다. 후자는 개인정보·국외 처리·플랫폼 데이터 사용 조건이 여전히 남으며 BYOK만으로 해결되지 않는다. Reviewnary 중앙 AI가 원문을 받아 추론하는 절충형은 별도 후보로 질의하고, 키가 없다는 이유로 자체 이용 판정을 내리지 않는다. 학습/모델 개선용 외부 전송도 기본 비활성화한다.

이는 현재 런타임 배포 상태가 아니다. 실제 구현 전 backend-only LLM egress, credential 없는 READ-only Operator, 별도 실행 계층·승인 계약을 대조한다. Spring backend를 판매자 환경에 배포하는 후보이며 agent-runtime에 키나 LLM 직접 호출을 넣는 제안이 아니다.

### 15.3 UX와 사업상 비용

판매자는 설치 후 브라우저에서 기존과 같은 홈·문의·리뷰·채팅·개별 승인을 사용할 수 있다. 설치/권한 연결/업데이트/백업·복구를 간단하게 만들어야 하며, PC 종료·절전 중 상시 수집은 약속하지 않는다. 판매자 소유 상시 서버는 가용성을 보완하지만 비용·설치·운영 부담이 늘어난다. 단순히 법인 비용을 피하려고 설치형 전환 비용이 더 커지는지도 비교한다.

네이버 리뷰 사람 대행은 별도 위임·처리 계약 경로로 유지할 수 있지만, 그 업무를 위한 자료 공유가 문의 API 자체 운영 경계를 자동으로 넓혀주지는 않는다. 두 데이터 흐름과 권한을 분리한다. 장기 해자는 판매자 환경에 있는 기준·지식·수정 이력의 재사용으로도 구현할 수 있으며 원문 중앙 집중이 필수는 아니다. 다판매자 모델 학습은 별도 조건이 필요하다.

### 15.4 확정 전에 답을 받아야 할 정책 질문

1. 개인사업자가 유료로 반복 공급하는 프로그램을 비개발자 판매자가 자기 PC/자기 서버에 설치하고, 자신의 내스토어 앱으로 API를 직접 호출하는 형태가 자체 이용으로 허용되는가? 별도 공급자 등록이 필요한가?
2. 공급자가 인증정보·원문을 받지 않고 API 실행을 원격 통제하지 않으며 프로그램 업데이트·일반 기술지원만 제공할 때 필요한 조건은 무엇인가? 반복 라이선스와 고객별 구축의 구분이 있는가?
3. 상품·문의 조회와 판매자 개별 승인 후 답변 등록 각각이 허용되는가? 판매자 직접 계약 AI 사용 시 허용되는 자료·처리 위치·보관 조건은 무엇인가?
4. 중앙 라이선스 확인·업데이트만 있는 경우와 중앙 AI/원격 작업 통제가 추가되는 경우의 분류는 어떻게 달라지는가?

정책 질의는 #556이 안내한 공식 창구 commerce-api@navercorp.com을 후보로 한다. 이 문서는 전송 승인이 아니며 실제 문의를 발송하지 않았다. 허용 답변이 나오면 조건을 제품 계약·데이터 흐름·온보딩에 반영한다. 반려되면 API를 빼는 대신 기존 서버형에 필요한 직접 자격을 확보하는 경로와 설치형 개발 비용을 다시 비교한다.

## 16. 오너 결정: 개인사업자로 시작하고 로컬 agent 구축을 목표로 함

2026-10-16 오너는 자금 제약을 고려하여 당장은 개인사업자로 시작하고, API 활용을 위한 로컬 agent 구축을 목표로 하겠다고 결정했다. 법인 우선 설립은 초기 전제가 아니며, 사방넷 등 외부 툴 경유도 이번 목표가 아니다. 네이버 문의를 제외한다는 결정은 아니다.

### 16.1 확정 범위

1. 초기 사업 형태는 개인사업자를 목표로 한다. 사업자등록이나 외부 계정 연결을 이번 대화로 대신 수행하지 않는다.
2. 판매자가 직접 운영하는 로컬 agent를 우선 개발 목표로 한다. 키만 로컬에 보관하는 중앙 SaaS와 동일시하지 않으며 실제 운영 통제·자료 처리 경계를 설계한다.
3. 상품 지식·판매자 기준 기반 판단, 자연스러운 대응 준비, 판매자 개별 승인, 허용된 실행과 결과 기록이라는 §12 업무 모델은 유지한다.
4. 로컬 agent를 외부 판매자에게 공급하여 네이버 API를 사용하는 방식의 허용 여부는 §15.4의 미확인 과제로 유지한다. 개인사업자·설치형 선택은 플랫폼의 허용이나 상용 API 자격 확보를 뜻하지 않는다. 실계정 호출·등록은 별도 승인과 조건 확인 전 실행하지 않는다.

### 16.2 다음 설계에서 구분할 사항

- 로컬 배포 범위: 채널 연결 모듈만인지, 업무·지식 저장과 Spring backend·credential 없는 orchestration까지 포함하는지. 판매자 자체 운영 목표에 맞춰 비교하고 확정한다.
- AI 처리: 로컬 agent 실행과 로컬 LLM 실행은 다르다. 모델 실행 위치·계약 주체·원문 전송·비용·자료 처리 허용 조건은 미확정이다.
- 판매자 경험: 설치 후 기존 웹의 홈·채팅·개별 승인 경험을 유지하고, 연결 가이드·가동 상태·오류 복구·업데이트를 단순화하는 것을 권고한다. 구체적 화면 변경은 아직 확정하지 않는다.
- 배포 대상: 기존 Mac 개발·Windows 이식 목표를 존중한다. 패키징 기술·배포 순서·지원 범위·PC 절전/종료 시 동작은 별도 설계한다. Aside 자체는 필수 설치로 다시 확정하지 않는다.
- 리뷰 사람 대행: 기존 선택을 자동 폐기하지 않는다. 로컬 문의 흐름과 담당자의 접근·파일 전달·승인 작업 전달 경계를 별도로 확인한다.

현재 구현을 재사용할 수 있는 범위와 누락 기능을 먼저 대조한 후 개발 단위를 정한다. 이 문서 갱신은 구현 완료나 기존 scope·안전 계약의 암묵적 변경을 의미하지 않는다.

## 17. 판매자 자체 운영형 제품의 상세 구조

2026-10-16 오너는 인증정보를 공급자에게 주지 않고 판매자 PC에서 업무를 처리하는 구조를 채택하고, 네이버의 이의 제기 위험을 줄이는 구체적 설계 및 Claude 개발 인계를 요청했다. 아래에서 **채택한 원칙**과 **구현을 위한 권고안**을 구분한다. 네이버의 승인을 받은 설계이거나 클레임을 보장해 방지하는 설계라는 주장은 하지 않는다.

### 17.1 채택한 원칙과 제품 정체성

- 개인사업자로 시작한다. 판매자가 직접 운영하는 프로그램을 제공하며, NAVER 인증정보를 공급자가 수령해 대신 API를 운영하지 않는다.
- API 조회·토큰 관리·스케줄·업무 저장·승인·API 실행은 실제 판매자 PC의 런타임이 담당한다. '키만 로컬, 개별 작업은 중앙에서 지시'하는 구조가 아니다.
- 판매자는 Reviewnary 화면에서 업무를 보고 승인한다. **서비스 화면과 중앙 서버 저장은 같은 뜻이 아니다.** 초기 화면은 로컬 런타임의 데이터와 승인 기록을 사용하도록 설계한다.
- 외부 LLM 호출과 네이버 리뷰 사람 대행은 로컬 경계 밖의 명시적 자료 처리 흐름이다. 제품 전체를 '아무 자료도 외부에 나가지 않는 100% 로컬'로 홍보하지 않는다.
- 문의·리뷰를 판단하고 대응을 준비하는 운영 AI라는 정체성과 §12의 개별 승인·결과 보고는 유지한다. 로컬 설치 도구 자체나 수동 대행 인력이 해자의 전부가 아니다.

### 17.2 권고 배치: 기존 엔진을 로컬에 옮기고 업무 모델을 유지

```text
판매자 PC: Seller Workspace
  로컬에서 제공하는 Reviewnary UI (기존 React 화면 재사용)
                  |
  로컬 Spring backend: 사실·정책·업무·지식·승인·트랜잭션의 원장
       |              |                 |
  로컬 Postgres   로컬 비밀 저장소   credential 없는 LangGraph
       |              |                 |
       +------ 준비·승인·별도 실행 계층 --+
                      |
          허용된 공식 채널 API 직접 호출
                      |
          결과 재조회 / 미확인 결과 보류

  로컬 Spring -> 허용된 LLM 제공자 (승인된 최소 컨텍스트만)
  로컬 Spring -> 선택한 리뷰 대행 자료 교환 (별도 위임·자료 범위)

공급자 서비스: 프로그램 배포·라이선스·일반 지원
  기본적으로 채널 키·문의 원문·API 작업 큐·원격 실행 권한 없음

별도 Review Service Workspace
  초대받은 담당자의 직접 자료 확보 -> 판매자 로컬로 전달
  판매자가 승인한 리뷰 작업 수신 -> 담당자 직접 등록 -> 결과 전달
  NAVER API 인증정보나 로컬 업무 제어 권한은 없음
```

Spring을 로컬에 배치해도 **backend-only LLM egress**는 유지된다. Node/LangGraph에서 LLM 제공자나 채널 API에 직접 접근하도록 새로 구현하지 않는다. Operator catalogue는 READ-only로 유지하고, 외부 등록은 기존 계약에 맞춘 별도 권한 실행 계층이 담당한다. React 앱이 LLM 키나 채널 Secret을 읽을 수 있는 API도 만들지 않는다.

로컬 DB는 기존 Postgres/Flyway를 재사용하는 권고안이다. SQLite 전환·백엔드 전면 재작성·새 범용 agent 프레임워크 도입을 이 결정에 끼워 넣지 않는다. 최종 설치 패키징은 §18의 기술 검증 뒤 선택한다.

### 17.3 데이터 경계와 외부 통신 계약

| 자료/기능 | 기본 위치·전달 범위 | 금지 또는 별도 변경 대상 |
|---|---|---|
| 채널 Secret·토큰·LLM 키·암호화 키 | 판매자 PC의 보호된 저장소, 필요한 로컬 backend 프로세스만 사용 | 공급자 서버·브라우저 저장소·로그·argv·대행 작업 패키지로 전송 |
| 문의·상품·정책·과거 답변·작업 원장 | 판매자 PC | 중앙 DB 자동 복제, 공급자의 상시 DB 접속 |
| 모델 입력 | 로컬에서 선택·정제한 최소 문맥을 허용된 LLM 제공자로 직접 전송 | 전체 DB·폴더·작성자·연락처를 무조건 전송, 공급자 LLM 프록시를 숨겨 사용 |
| 리뷰 대행 자료 | 별도 위임 범위의 리뷰와 정확히 승인된 답글 및 작업 식별 정보 | 문의 API 데이터 전체·전체 상품 지식·다른 판매자 자료·인증정보를 함께 전달 |
| 라이선스·업데이트 | 설치 식별자·버전·라이선스 상태 등 명시한 최소 필드 | 스토어 ID·원문·작업 목록을 식별/과금 명목으로 몰래 첨부 |
| 진단·지원 | 기본 원문 전송 없음. 판매자가 확인한 최소 진단 패키지만 선택 제공 | DB 덤프·화면 녹화·네트워크 본문·세션 쿠키 자동 수집 |
| 백업·내보내기 | 판매자가 지정한 로컬/자기 관리 위치 | 공급자 보유 복호화 키, 중앙 자동 백업을 기본값으로 설정 |

추가 설계 규칙:

1. 외부 목적지·용도·필드 allow-list와 최종 요청 직전 정책 검사를 둔다. HTTP redirect·파일 첨부·이미지/OCR·임베딩·관측 SDK도 검사 범위다. URL이나 목적지를 LLM 출력·가져온 문서가 정하지 못하게 한다.
2. LLM은 판매자 직접 계약/BYOK를 초기 권고안으로 두되 제공자·모델·처리 위치·보관·학습 이용 조건을 실제 확인한다. BYOK 자체를 정책·개인정보 문제의 면제로 취급하지 않는다. 구매자 개인정보가 검출되거나 전송 허용 범위가 불명확하면 해당 모델 호출을 보류한다.
3. 공급자 프록시·중앙 모델 호출·중앙 지식 검색·cloud sync는 단순 설정 변경으로 켜지지 않는다. 데이터 흐름·계약·테스트를 바꾸는 별도 기능이다.
4. 외부로 나가는 내용을 판매자가 이해할 수 있게 표시하고 중단할 수 있게 한다. 동의 버튼만으로 플랫폼 데이터 사용 조건까지 충족됐다고 판단하지 않는다.
5. 공급자 계정/업데이트 서버가 연결되지 않아도 이미 허용된 로컬 업무와 이력 열람을 유지하는 방향으로 설계한다. 구체적인 라이선스 유예 기간은 [PO] 미정이며, 결제 문제로 데이터를 인질로 삼거나 미확인 발송을 재시도하지 않는다.

### 17.4 실제 자체 운영을 유지하는 보안·운영 경계

- 로컬 UI·API·LangGraph·DB는 필요한 loopback 인터페이스에만 바인딩한다. 인터넷 공개·중앙 reverse proxy·터널을 기본으로 설치하지 않는다. localhost라는 이유만으로 인증을 생략하지 않는다.
- 설치별 인증·세션, 엄격한 Host/Origin 검증, CSRF 방어, CORS 제한을 함께 적용한다. 악성 웹사이트의 localhost 접근과 DNS rebinding, WebSocket 위조를 부정 테스트한다. CORS만으로 로컬 API를 보호했다고 판정하지 않는다.
- API 호출의 대상 스토어는 로컬 연결 과정에서 판매자가 확인한다. 한 PC에 여러 계정이 있어도 org·account 범위를 검증하며, 로컬 단일 사용자 모드가 DB의 모든 org에 동작하는 기존 성질을 설치 격리의 증거로 오해하지 않는다.
- OS 비밀 저장소에 설치별 암호화 키를 보관하는 방식을 검증한다. 복구 수단·재연결 절차를 제공하되 공급자 master key/복구용 뒷문은 두지 않는다. 잠금·키 유실이면 안전하게 멈춘다.
- 중앙 서버가 임의 작업·코드·URL·SQL을 전달하는 RPC, shell 도구, 원격 API 호출 프록시는 만들지 않는다. 공급자 직원의 상시 원격 관리자 계정도 두지 않는다.
- 업데이트는 서명·무결성 확인, 판매자 통제, 변경 내용 안내, 안전한 중단·재개를 갖춘다. 업데이트는 코드 실행 권한이므로 데이터 경계를 바꾸는 업데이트도 통제한다. 롤백은 DB 호환성을 확인하고, 적용된 Flyway migration을 수정·역실행하지 않는다.
- 오류 모니터링·분석·세션 replay·원격 tracing은 로컬 제품에서 기본 비활성화하고 모든 SDK 경로를 감사한다. 실제 원문이 담긴 테스트 출력·지원 패키지도 수집하지 않는다.
- 문의·문서·상세페이지·외부 도구 결과는 신뢰하지 않는 입력이다. '키를 보내라/다른 URL을 열라'는 지시를 데이터로 취급하고 권한·실행 결정에 사용하지 않는다.
- PC 절전·종료 중에는 로컬 수집·초안·API 실행이 멈춘다는 것을 표시한다. 재시작 시 최근 구간과 별도 과거 업무를 구분하고 무제한 catch-up이나 자동 재발송을 하지 않는다.

위 방어는 기술적 사고와 운영 실질의 혼동을 줄이기 위한 것이다. 네이버가 유료 소프트웨어 공급 자체를 어떤 유형으로 분류할지까지 보장하지 않는다.

### 17.5 네이버 문의·상품 API 흐름

1. 판매자가 공식 페이지에서 자신의 앱을 준비하고 로컬 Reviewnary의 보안 입력 화면에 직접 연결한다. 공급자가 키를 받아 설치하거나 API센터에서 키를 추출하지 않는다.
2. 로컬 backend가 공식 API를 직접 호출한다. 실제 앱 유형별 권한·호출 IP 조건을 확인하며, 공인 IP 변경·허용 목록 불일치는 갱신 안내로 처리한다. 공급자 고정 IP 프록시로 우회하지 않는다.
3. 로컬에서 정규화·상품 연결·최신성·대응 필요 여부·중요도·근거를 판단한다. 조회 가능한 목록 정보가 상세설명·이미지·옵션·재고까지 모두 제공한다고 가정하지 않는다.
4. 초안은 현행 지식·판매자 응대 기준·관련 과거 답변을 사용한다. 외부 모델 사용이 허용되지 않으면 허용된 기본 문구/정보 요청 또는 준비 불가 사유를 보여주며 'AI 처리 완료'로 위장하지 않는다. 자연어 Agent planner 실패 시 결정론 planner로 대체하지 않는 기존 계약은 유지한다.
5. 판매자가 정확한 초안을 개별 승인한다. 로컬 원장이 대상 계정·원문 버전·초안 버전/지문·관련 정책 버전·승인자·명령 식별자를 묶는다.
6. 별도 실행 계층이 채널 capability·권한·정책 조건·현재 대상 상태·승인 유효성·중복 여부를 재검증하고 허용된 API로만 등록한다. LLM이 endpoint나 대상 계정을 정하지 않는다.
7. 결과가 불명확하면 상태 조회로 확인한다. 타임아웃을 실패로 간주해 즉시 재발송하지 않는다. 외부에서 이미 답변했거나 대상이 바뀌었으면 멈추고 차이를 보여준다.

판매자 개별 승인과 플랫폼의 API 사용 허용은 별개의 조건이다. 실제 채널별 실행 가능 여부는 기존 capability/코드/증거를 대조하며 이 문서로 일괄 활성화하지 않는다.

### 17.6 네이버 리뷰 사람 대행 흐름

**리뷰 대행은 실제 업무 위임이다.** 로컬 API 부분이 자체 운영이라는 설명을 사람 수행까지 확장하지 않는다. 초대받은 담당자는 자신의 계정으로 직접 작업하며 판매자 비밀번호·OTP를 공유하지 않는다. 부매니저 역할의 광범위한 권한은 메뉴별 최소화 가능 여부·직원 권한·회수 절차로 관리한다.

권고 왕복 흐름:

1. 담당자가 정식 권한 범위에서 자료를 직접 확보한다. 파일 제공 여부·기간·식별자·답변 포함 여부는 실물로 검증하며, 브라우저 자동 수집이나 자동 다운로드를 기본으로 되살리지 않는다.
2. 판매자별 자료 교환 공간으로 전달하고 로컬 프로그램이 범위·형식·중복·상품 귀속을 검증해 반영한다. 초기 개발은 합성 자료의 명시적 import/export로 계약부터 검증할 수 있으나 판매자의 반복 수동 업로드를 최종 UX로 고정하지 않는다.
3. 로컬에서 판단·초안을 준비하고 판매자가 Reviewnary 화면에서 개별 등록대행 승인한다. **정확한 리뷰 대상과 승인된 답글만** 대행 작업 패키지로 전달한다.
4. 패키지는 판매자/스토어 범위, 작업 ID·버전·원문/답글 지문, 승인·만료·철회 상태를 대조할 수 있어야 한다. 전송 인증·무결성 검증은 로컬 backend와 교환 서비스의 책임이며 Graph에 키를 넣지 않는다. 구체적 키·메시지 프로토콜은 [REPO/PO] 설계 검토 후 확정한다.
5. 담당자 한 명이 작업을 맡고, 게시 직전에 현재 리뷰·기존 답글·유효한 승인·취소·시간 의존 사실을 확인한다. 수정이 필요하면 재승인한다. 담당자가 직접 붙여넣고 저장하며 프로그램이 대신 입력·제출하지 않는다.
6. 담당자 보고·확인 시각·확인 방법·게시 내용 지문을 판매자 로컬 원장에 반영한다. 사람 확인은 공식 API 검증과 다른 증거 등급으로 표시한다.

교환 서비스는 범위가 정해진 파일·승인 패키지·작업 상태만 전달한다. 임의 API 요청·스크립트·로컬 파일 읽기 명령을 전달하는 원격 제어 채널이 아니다. 모든 교환은 판매자/스토어로 격리하고, 리뷰 원문도 필요한 기간·용도로만 보유한다. 파일럿 보유 기준은 §17.9(2026-10-17 오너 결정)를 따르고, 위임·개인정보 처리 조건은 [EXT]로 확정한다.

취소는 분산된 사람 작업에서 원자적으로 보장할 수 있다고 약속하지 않는다. 미착수 건은 취소 처리하고, 착수 후에는 '취소 요청 중'으로 두어 담당자 확인 뒤 결과를 알린다. 오프라인 담당자는 최신 승인·철회 상태를 확인할 수 없으면 게시하지 않는다. 이미 게시한 건을 삭제 요청 없이 자동 삭제하지 않는다. 저장 결과가 불명확하면 확인 전 재등록하지 않는다.

### 17.7 채널별 실행 위치와 확장

| 채널/업무 | 초기 목표 경로 | 현재 지원 주장과 구분할 점 |
|---|---|---|
| NAVER 문의·상품 | 판매자 로컬 backend -> 공식 API | 외부 공급 프로그램의 자체 이용 분류·자료 사용 조건 [EXT], 세부 R/W·IP·권한·증거 [REPO/EXT] |
| NAVER 리뷰 | 담당자 직접 확보 -> 로컬 판단·승인 -> 담당자 직접 등록 | 파일 범위·자료 처리 조건·대행 운영 비용 별도 검증. 리뷰 API를 만들어내지 않음 |
| Coupang 문의·상품 | 판매자 로컬 backend -> 지원되는 공식 API | 등록·권한·호출 IP·실제 지원 필드 대조. 로컬화가 채널 조건을 면제하지 않음 |
| Coupang 리뷰 | 공식적으로 허용된 확보 수단을 확인한 범위에서 분석 | Excel 존재·자동 취득을 미리 약속하지 않음. 답글 발송 업무는 없음. 과거 READ proof는 최신 정책 허가가 아님 |
| Cafe24 문의·리뷰·상품 | 오너가 검증한 API를 로컬로 재배치하는 방향 | 검증을 다시 처음부터 요구하지 않되, 설치형 배포에 따른 OAuth callback·scope·발송 의미·토큰 갱신은 영향 점검 |

Cafe24 OAuth는 특히 [EXT/REPO] 선행 검증 대상이다. 2026-10-16 공식 가이드 확인: Admin API는 PKCE를 쓰지 않고, 코드 교환과 refresh 모두 `client_id:client_secret` Basic 인증이며 "backend server"에서 하라고 안내한다(access 2시간, refresh 2주·회전). 저장소의 `Cafe24TokenClient`도 같은 방식이다. 따라서 공급자 앱 하나를 판매자들이 설치하는 구조에서 secret을 판매자 PC에 배포하지 않으려면 **공급자 서버의 토큰 중계**가 필요하다 — callback 수신·코드 교환·refresh에 secret만 덧붙여 전달하고, 토큰·상품·게시물 자료를 저장하거나 기록하지 않는다. 토큰이 공급자 서버를 지나가므로 v1.14 ①의 두 번째 예외다 — **2026-10-16 오너가 채택**(v1.14 ⑧). 공급자는 개인사업자로 등록하고, 현재 scope는 개인정보 취급권한이 필요 없다는 오너 가정으로 진행한다(Cafe24 확인 전 가정). 교환 서비스와 같은 서버에 두더라도 기능·로그·저장소를 분리한다. **응답 유실 문제(2026-10-17 검토):** refresh token은 회전하므로, 중계가 갱신에 성공했는데 PC가 새 토큰을 받기 전에 연결이 끊기면 PC에는 이미 소진된 refresh token만 남는다 — 단일 backend 안에서 저장까지 한 번에 끝나던 기존 구조에는 없던 문제다. 그래서 "완전 무저장"이 아니라 **복구용 단기 보관**으로 설계한다: 갱신 요청은 설치별 멱등 키(소진될 refresh token의 해시)를 가지며, 서버는 그 결과를 설치의 공개키로 암호화해 PC의 수신 확인 또는 짧은 TTL까지 보관한다. 같은 키로 다시 요청하면 Cafe24를 다시 부르지 않고 보관한 결과를 돌려준다. 설치별로 갱신은 한 번에 하나만 진행한다. PC의 영구 저장 확인을 받으면 즉시 지우고, 확인이 없으면 최대 72시간 뒤 지운다(2026-10-17 오너 결정). 그 뒤에는 재연결(OAuth)로 복구한다. 개발자센터 FAQ는 개인·사업체 가입을 허용하나 "개인개발자에게는 개인정보 취급권한을 부여하고 있지 않"고 테스트 설치는 5개 쇼핑몰까지다. 개인사업자의 개인정보 권한 범위와 현재 scope(`mall.read_community`, `mall.read_order`, `mall.read_product`)의 분류는 [EXT] 확인 대상이다. 데스크톱에서 기존 앱에 등록된 callback을 어떻게 만족하는지, 공개 relay가 code를 받는지, 토큰 교환을 누가 하는지 확인한다. loopback callback/PKCE 지원이나 token 없는 relay를 추측해 확정하지 않는다. 현재 `localhost` 기본값·개발 터널 증거만으로 판매자 설치형 연결이 해결됐다고 판정하지 않는다.

장기적으로 공식 SaaS 자격이나 허용된 외부 도구가 확보되면 실행 어댑터를 교체한다. 지식·기준·승인·결과 모델을 다시 만들지 않는다. 다만 클라우드 전환은 판매자 데이터의 무단 이전이 아니며 별도 계약·이동·권한 회수 절차를 거친다. 원문을 중앙 학습시키지 않아도 판매자별 수정·결과를 로컬에서 재사용하는 제품 가치는 유지된다.

### 17.8 네이버 이의 제기 위험에 대한 대응 패키지

**위험을 줄이는 방법은 명칭 변경·탐지 회피가 아니라 실제 제공 범위와 설명을 일치시키는 것이다.**

| 우려 | 설계/증거 | 남는 확인 |
|---|---|---|
| 판매자 키를 받아 대신 API 운영 | 중앙 credential intake/원격 개별 작업 제어 없음, 로컬 호출 네트워크 검증 | 유료 반복 공급 설치형 프로그램의 플랫폼 분류 |
| '로컬'이라지만 원문이 중앙에 복제 | 데이터 흐름·egress 검사·지원/telemetry/backup 감사 | 외부 LLM과 리뷰 대행 자료 처리 조건 |
| 부매니저 초대를 자동화 허가로 사용 | 담당자 직접 확보·입력·저장, 프로그램의 자동 등록 경로 비활성 | 실제 역할·작업별 권한과 사용 조건 |
| 판매자가 무엇을 맡겼는지 불명확 | API 자체 운영·LLM 전송·리뷰 대행을 별도 설명/철회 | 적용 계약·개인정보 처리 의무 검토 |
| 승인하지 않은 내용·다른 계정에 등록 | 대상/내용 바인딩, 직전 재검증, 재승인, 결과 미확인 보류 | 채널별 실증과 담당자 운영 품질 |
| 정책 변경 이후 계속 운영 | 범위별 일시중지, 이유·영향 표시, 자료 내보내기 유지 | 변경된 공식 정책/계약 대조 후 재개 |

준비할 자료는 실제 배치도, 필드별 데이터 흐름, 인증정보 비수령 확인, 원격 제어 부재, 업데이트/지원 방식, LLM 제공자·보관 조건, 별도 리뷰 대행 범위, 합성 데이터 기반 네트워크 검증 결과다. 마케팅·계약서도 구현과 일치시킨다. 서면 확인 없이 '네이버 공식 인증/제휴', '완전 무위험', '키를 안 받으니 등록 불필요 확정'이라고 쓰지 않는다.

외부 판매자에게 NAVER API 기능을 제공하기 전 §15.4 질문을 이 구체적 구조로 좁혀 공식 확인한다. 문의는 `commerce-api@navercorp.com` 후보이며 **이번 작업에서 전송하지 않는다.** 부정적 답변이 오면 범위를 확인하고 해당 경로를 멈춘 뒤 수정안 또는 공식 자격 경로를 비교한다. 공급자 프록시·개인화라는 이름으로 숨겨 계속하지 않는다. 자체 개발·합성 검증은 그 답변을 기다리는 동안 분리해서 진행할 수 있다.

근거 재확인: 2026-10-16. 아래 공개 자료는 정책 판단의 일부 근거이지 설치형 상용 공급에 대한 개별 허가서가 아니다. 적용 약관 전문과 실제 계약도 확보해야 한다.

### 17.9 서버와 판매자 PC의 책임 분할 (2026-10-16 오너 결정)

**API로 처리할 수 있는 문의·상품은 판매자 PC에서, NAVER 리뷰는 공급자(부매니저 권한의 담당자)가 확보·등록한다.**
그래서 PC가 꺼지면 문의 수집은 멈추지만 리뷰 확보는 계속된다. 이 절이 §17.2의 배치도와 v1.14 ①·⑦·⑧을
구역 단위로 묶는다.

| 구역 | 기본 책임 |
|---|---|
| 판매자 PC | 채널 연결, API 호출·스케줄(문의·상품), 문의·상품 데이터와 지식, 리뷰 초안 작성, 문의 승인·실행 원장 |
| 공급자 서버 | 계정·라이선스·배포, 리뷰 자료 교환·담당자 작업 관리, 리뷰 대행의 승인·철회 상태(정본), 공인 IP 확인 |
| 별도 선택 영역 | AI 호출 중계(규정 검토 중), Cafe24 인증 중계(채택, v1.14 ⑧), 모바일 검토용 자료 동기화 |

**PC가 꺼졌을 때.**

| 업무 | PC 켜짐 | PC 꺼짐 |
|---|---|---|
| 문의 | 수집 → 초안 → 개별 승인 → 공식 API 발송 | 멈춤. 아래 「문의 공백 보완」을 따른다 |
| 리뷰 자료 | 담당자가 확보해 서버에 둠 | 계속 확보됨 |
| 리뷰 초안 | PC가 지식 기반으로 작성해 서버에 올림 | 새 초안은 PC가 다시 켜질 때까지 대기 |
| 리뷰 승인·등록 | PC 또는 휴대폰에서 개별 승인 → 담당자 직접 등록 | PC가 미리 준비한 건은 휴대폰 승인·담당자 등록 가능 |

**리뷰 답글 승인 — 모바일을 위해 서버에서 초안을 만들 필요는 없다.** PC가 만든 검토 건만 서버에 올린다.

```text
PC: 지식 기반 초안 작성
        ↓
서버: 해당 리뷰 · 정확한 초안 · 버전 · 유효 상태만 보관
        ↓
휴대폰: 확인 · 수정 · 개별 승인
        ↓
담당자: 승인 상태 확인 후 직접 등록
```

전체 상품 지식과 응대 기준은 동기화하지 않는다. 리뷰 대행의 승인·철회 상태는 서버가 일관되게 관리하고 PC는 그것을
동기화한다. 휴대폰에서 문장을 고치면 새 초안 버전이 되며, 승인은 그 버전에 묶인다.

- PC가 준비해 둔 건: PC가 꺼져도 모바일 승인과 담당자 등록이 가능하다.
- PC가 꺼진 뒤 새로 들어온 건: 자료는 서버에 들어오지만 새 초안 생성은 대기한다.
- PC 없이 새 업무까지 준비하려면 서버 추론과 필요한 지식의 복제가 필요하다(B2). 이번 결정의 범위가 아니다.

**모바일 승인에서 추가로 정할 것.** PC가 꺼져 있으면 서버는 로컬 정책이 지금도 최신인지 알 수 없다. 그래서 서버는
판단하지 않고, 초안이 무엇을 근거로 만들어졌는지를 들고 다닌다.

- **초안 메타:** 리뷰 원문 지문 · 초안 버전 · 생성 시각 · 생성 당시 지식 · 정책 · 응대 기준 버전 지문. 승인은 이 묶음에
  걸린다.
- **고정 기한은 두지 않는다(2026-10-17 오너 결정).** 대신 사건으로 무효화한다: 리뷰 원문이 바뀌거나 삭제됨, 채널에 이미
  답글이 있음, 판매자 취소, (미승인 건에 한해) 정책 지문 변경. 담당자는 저장 직전에 이 사건들을 다시 확인한다(§17.6).
  오래 방치된 건은 무효화하지 않고 정리 대상으로 안내한다.
- **정책이 바뀐 경우:** PC가 다시 켜지면 서버의 미승인 · 미착수 건의 정책 지문을 현재와 비교해, 다르면 「재확인 필요」로
  돌린다. 이미 착수한 건은 멈추지 않고 결과만 표시한다. 판매자가 승인한 정확한 문장은 판매자의 결정이므로 정책 변경으로
  자동 철회하지 않는다 — 대신 판매자에게 알리고 철회를 제안한다.
- **취소와 등록 착수의 경합:** 서버가 상태 전이를 원자적으로 처리한다. `APPROVED → CLAIMED(담당자 착수) →
  POSTED · FAILED · UNKNOWN`. 취소는 `APPROVED`에서만 즉시 성립하고, `CLAIMED`에서는 `CANCEL_REQUESTED`가 되어
  담당자가 저장 직전에 확인한다. 담당자는 저장 직전 서버 상태를 다시 읽고, 읽을 수 없으면 등록하지 않는다(§17.6).
- **휴대폰에서 고친 문장은 허용한다(2026-10-17 오너 결정).** 새 버전이 되며 PC의 지식 기반 검사(근거 · 금지 표현)를
  거치지 않았음을 표시한다. 서버는 지식 없이 가능한 검사(연락처 · URL · 길이)만 하고, PC가 켜지면 다시 검사해 결과를
  알린다.

**리뷰 교환 자료 — 판매자에게는 원문, AI에는 정제본(2026-10-17 오너 결정).**

```text
담당자가 판매자센터에서 확인 · 파일 확보
                  ↓
업로드 단계에서 불필요한 열 제거
                  ↓
서버: 업무에 필요한 리뷰 원문 · 사진 · 상품 · 답글 보관
       ├ 판매자 PC · 휴대폰 → 원문 그대로 열람
       └ AI 처리 → 별도로 정제한 내용만 전달
```

'원문 그대로'와 '엑셀의 모든 열'은 다르다. 제공하는 것은 리뷰 본문 · 사진 · 상품과 옵션 · 평점 · 작성일 · 기존 답글처럼
대응에 필요한 맥락이고, 구매자 ID · 주문번호처럼 그 업무에 불필요한 정보는 기본으로 뺀다. 특정 업무에 정말 필요한
추가 정보는 목적과 권한을 정해 제한적으로 다룬다. 본문에 개인정보가 섞여 있어도, 정당한 업무 범위에서 권한 있는
판매자에게 원문을 보여 주는 것과 외부 AI로 보내는 것은 별개다. 담당자는 우리 쪽 사람이라 리뷰가 판매자 PC보다 먼저
우리에게 오므로 "PC가 정제한 뒤 올린다"는 이 경로에 적용할 수 없고, v1.14 ⑦의 명시적 예외로 남는다.

서버 원문 보관에는 위탁 범위 · 접근 통제 · 암호화 · 보유와 삭제 기준을 갖춘다(제26조). 매니저 권한을 얻었다고 파일의
외부 보관까지 자동으로 허용되는 것은 아니다 — 그 조건은 [EXT] 확인으로 남는다.

**보유 기준(파일럿, 2026-10-17 오너 결정).** 리뷰와 토큰은 따로 정한다.

| 대상 | 보유 |
|---|---|
| 업로드 원본 엑셀 | 정상 반입 · 검증 후 삭제. 실패 파일은 격리하고 최대 24시간 후 삭제. 담당자 PC에 내려받은 사본도 같은 기준으로 삭제 |
| 진행 중 리뷰 · 초안 · 승인 자료 | 업무 수행에 필요한 동안 보관. 장기 방치는 정리 대상으로 안내 |
| 완료된 리뷰 교환 자료 | 등록 확인 후 90일, 이후 서버 사본 삭제. 필요한 이력은 판매자 로컬에 보존 |
| Cafe24 토큰 복구 결과 | PC의 영구 저장 확인 즉시 삭제, 확인이 없으면 최대 72시간 |

모바일 검토 화면은 A7 FE freeze에 대한 새 delta다 — 구현 전 화면 단위로 따로 확인한다.

**문의 공백 보완 — 표시만이 아니라 보완 경로가 필요하다.** 네이버는 문의에 1영업일 이내 답변을 안내한다. 야간
정지가 곧바로 문제는 아니지만 며칠 동안 PC가 꺼지는 상황은 운영상 중요하다. 초기 조합:

- 자동시작 · 재연결 · 제한된 최근 구간 복구. 무제한 catch-up과 자동 재발송은 하지 않는다(§17.4).
- 마지막 정상 수집 시점과 이후 미관측 구간 표시.
- 네이버 자체 문의 알림과 판매자센터 직접 대응을 대체 경로로 안내.
- 연결 끊김을 곧바로 'PC 종료'나 '문의 없음'으로 단정하지 않는다.

자동시작은 꺼진 PC를 켜 주는 기능이 아니다. 상시 실행이 꼭 필요한 판매자에게만 전용 기기나 판매자 관리 서버를
나중에 검토한다.

**네이버 호출 IP 자동 감지.** 공급자 서버가 요청자의 공인 IP만 돌려주는 엔드포인트를 제공하고(저장·기록 없음),
연결 화면은 "이 PC의 공인 IP: x.x.x.x — 이 주소를 등록하세요"와 복사 버튼을 보여 준다. 서버에 닿지 않으면 지금의
수동 안내(네이버 '내 IP' 검색)로 돌아간다. VPN·프록시로 경로가 나뉘면 서버가 본 주소와 네이버가 보는 주소가 다를 수
있으므로, 최종 확인은 기존처럼 연결 테스트가 한다.

**AI 답변 모델 — 기본은 로컬 정제 후 최소 데이터만 외부로, 중계는 UX 선호안이며 미채택.**

문의를 AI에 쓰기 위해 우리 서버를 거칠 필요는 없다. 연결 방식에 따라 달라진다.

| AI 연결 방식 | 문의 내용이 우리 서버를 지나가나 | 메모 |
|---|---|---|
| 판매자 PC → 외부 AI 제공사 직접 | 아니요 | 현재 구현. 판매자가 키를 발급·관리해야 한다 |
| 판매자 PC → 우리 AI 중계 → 제공사 | 예. AI에 보낸 내용만 | 우리 키 보호 · 요금 통합. v1.14 ①의 예외가 된다 |
| 판매자 PC 안의 로컬 모델 | 아니요(제공사에도 안 나감) | 품질 · PC 사양 · 배포 크기를 별도 검증 |

중계를 고민한 이유는 네이버 연동에 필요해서가 아니라, 판매자가 AI 키를 따로 발급하고 비용을 관리하지 않게 하려는 UX
때문이다. 우리 공용 키를 판매자 프로그램에 넣으면 추출·도용되므로 키를 보호하면서 요금을 통합하려면 중계가 필요하다.

**기본 원칙(2026-10-17 오너 합의): 원문과 고객 연결은 로컬, 외부에는 답변에 필요한 최소 맥락만.**

```text
판매자 PC
  원문 · 고객 · 주문 정보 → 로컬 DB 보관 → 판매자에게 그대로 표시
           ↓
  필요한 사실 추출 + 식별정보 제거 + 본문 검사
           ↓
  외부 전송용 데이터만 별도 생성 (원문은 덮어쓰지 않음)
           ↓
  외부 AI 직접 호출 또는 우리 AI 중계
           ↓
  초안 수신 → 로컬에서 필요한 값 결합 · 검증
           ↓
  판매자가 최종 답변 확인 · 승인 → 로컬에서 발송
```

| 로컬에만 남길 내용 | AI에 전달할 내용 |
|---|---|
| 고객 이름 · 주문번호 · 주소 · 전화번호 | 전달하지 않음 |
| 주문 · 배송 조회 결과 전체 | 배송 중, 도착 예정일, 주소 변경 불가 같은 필요한 사실 |
| 개인정보가 포함된 문의 원문 | 개인정보를 제거한 질문과 필요한 맥락 |
| 전체 응대 기록 · 상품 자료 | 이번 답변에 필요한 기준 · 자료 일부 |

구현 경계:

1. **검사는 외부 전송 전에 로컬에서 한다.** 개인정보를 찾으려고 원문을 외부 AI에 먼저 보내지 않는다.
2. **허용된 항목만 조립해 보낸다.** API 응답 전체를 보낸 뒤 지우는 방식이 아니다. 과거 답변 · 첨부 · 검색된 지식에도
   같은 검사를 적용한다.
3. **불확실하면 원문 전송으로 우회하지 않는다.** '탐지되지 않음'을 '안전'으로 취급하지 않고, 위험 유형이나 불확실성이
   있으면 보류해 로컬에서 더 고치거나 판매자 확인으로 돌린다. 판매자의 '전송' 클릭만으로 구매자 정보의 처리 근거가
   생기지 않는다. 같은 기준을 사진(이미지 인식) · 과거 답변 · 지식 자료에도 적용한다.
4. **복원은 로컬 코드가 통제한다.** 필요한 값만 현재 업무에 결합하고, AI가 만든 고객 · 주문 식별자를 믿지 않는다. 공개
   리뷰 답글에는 연락처 · 주소를 복원하지 않는다.
5. 중계 서버의 요청 로그 · 오류 추적 · 분석 도구에 본문이 남지 않게 한다. 판매자 화면에서 **'외부 AI에 전달된 내용'**을
   확인할 수 있게 한다(FE delta).

**현재 코드와의 차이 [REPO].** 필드 단위 최소화는 이미 있다 — `AgentDraftGenerator`의 payload floor는 작성자 · id ·
시각 · 점수를 보내지 않고 바이트 단위 테스트로 고정돼 있다. 그러나 **본문 검사는 LLM 경로에 없다.** `PiiMasker`는
화면 표시에만 쓰이고 전화 · 이메일 모양만 가린다(이름 · 주소는 오탐 때문에 의도적으로 제외). 그래서 「본문 검사 +
불확실 시 보류」 단계를 새로 만들어야 하며, 한국어 자유문 속 이름 · 주소 탐지는 완전할 수 없으므로 탐지기보다 **보류
규칙**이 경계다. → 2026-10-17 판매자 PC 모드에 구현했다(`LlmSendGate`, §18.7 다음 작업 3의 결과).

**최소화가 개인정보 문제를 없애는가.** 노출 범위를 크게 줄이지만 자동으로 익명정보가 되지는 않는다. 법은 다른 정보와
쉽게 결합해 알아볼 수 있는 정보와 가명정보를 개인정보에 포함하고, 합리적으로 다른 정보를 써도 알아볼 수 없는 정보만
적용 제외한다(제2조, 제58조의2). 이름 삭제 · 임시 ID 치환만으로 어느 쪽인지 확정할 수 없다. 따라서 "개인정보가 아니므로
의무가 없다"에 기대지 않고, 최소화 설계와 처리 요건을 함께 갖춘다.

**규정 쟁점 — 계약 · 실제 보호조치 · 플랫폼 조건을 함께 갖춰야 한다.** 2026-10-16 판단을 2026-10-17 오너 검토로 고쳤다.

1. **처리위탁(제26조, 시행령 제28조).** 위탁 목적 · 범위 · 보호조치 등을 담은 문서, 수탁자 공개, 수탁자 감독이 필요하다.
   전자약관을 쓸 수 있더라도 포괄 문구 하나로 끝났다고 보지 않는다.
2. **재위탁 동의(제26조 제6항).** 우리가 제공사에 다시 맡기면 판매자(위탁자)의 동의가 필요하다.
3. **국외 이전(제28조의8).** 처리방침 공개로 이전할 수 있는 예외는 **정보주체와의 계약 체결 · 이행에 필요한** 처리위탁 ·
   보관에 적용된다. 구매자 개인정보에 대해 판매자–우리의 SaaS 계약만으로 그 필요성이 성립한다고 단정할 수 없다. 판매자의
   재위탁 동의와 구매자의 국외 이전 근거는 서로 다른 것이다. 이 쟁점은 판매자 PC가 직접 호출해도 남는다.
4. **플랫폼 조건.** 네이버: 공급자 서버가 API로 받은 문의를 처리하면 자체 이용 설명이 약해진다(§15.4 질문 4) — 네이버
   문의 중계는 그 답 전 출시하지 않는다. **Coupang · Cafe24: 네이버와 같은 제한을 확인하지 못했을 뿐 무제약은 아니다.**
   쿠팡 API 연동 협약은 API로 취득한 정보의 무단 이용 · 제3자 제공을 제한하고(제3조 · 제7조), Cafe24도 개인정보와 앱
   운영 조건을 둔다. 외부 모델 처리가 허용된 업무 범위에 드는지 채널마다 대조한다.

결론: 해결 가능한 과제들이지만 "약관과 고지로 감당되고 남은 위험은 네이버뿐"은 아니다. 중계는 위 조건을 갖출 때까지
채택하지 않으며, 그 전까지는 판매자 PC가 최소 데이터로 제공사를 직접 호출한다. 법률 검토 전 정리이며 법률 의견이 아니다.

**판매자 PC 구조와 네이버 제한의 관계.** 판매자 PC가 인증정보를 보관하고 직접 문의를 조회 · 답변하는 구조는, 공급자가
인증정보를 받아 대신 API를 호출하는 구조와 분명히 다르다. "인증정보를 받아 대신 운영하지 말라"(#6)만으로 이 구조까지
금지라고 결론 낼 수 없다. 남는 불확실성은 네이버가 제3자 스토어 운영 관리 솔루션에 공식 등록 경로를 안내한다는
점(#3463)이며, 그 답변은 외부 SaaS 사례에 대한 것이라 판매자 PC에서 실행되는 유료 공급 소프트웨어의 분류는 직접 답하지
않는다(#556은 별도 정책 문의를 안내). 확인할 범위이지 위반 근거는 아니다. 다만 공급자 서버로 가는 경로(리뷰 교환,
Cafe24 중계, 앞으로의 AI 중계)가 늘수록 질의에서 함께 설명해야 할 내용이 늘어난다.

## 18. Claude 개발 인계: 기능 보존형 로컬 전환

이 절은 오너의 개발 방향을 실행 가능한 순서로 바꾸는 인계안이다. **앱 코드를 이번 문서 작업에서 변경하지 않았으며, 전면 삭제·DB 초기화·기존 migration 수정·실계정 실행을 지시하지 않는다.** 이 문서만으로 기존 safety contract나 READ-only Operator를 완화하지 않는다.

### 18.1 이번 저장소 확인 범위

2026-10-16 다음 **소스/문서의 책임 구조를 확인**했다. 코드 존재는 실판매자 로컬 패키지·권한·반복 운영 완료의 증거가 아니다. 아래는 전체 감사 결과가 아니며 각 경로의 현재 동작과 설정은 구현 시 다시 검증한다.

| 기존 자산 | 확인 지점 | 전환 시 취급 |
|---|---|---|
| Spring/React/collector/LangGraph/contracts 분리 | `docs/architecture.md` | 모듈별 책임을 유지하고 배치 경계를 변경 |
| 암호화 credential 저장·runtime connector 사용 | `backend/src/main/java/com/sellerops/credential/CredentialVault.java` | 판매자 로컬에서 재사용. 키 보관·복구·중앙 경로 차단은 추가 검증 |
| 승인 초안 지문·대상 바인딩·중복 방지·결과 조회 | `backend/src/main/java/com/sellerops/inquiry/publish/InquiryPublishService.java` | 재사용 후보. 채널별 live gate·실제 adapter·현재 canonical 계약과 함께 감사 |
| 리뷰 답글 초안: 근거가 있으면 LLM 작성(`AgentDraftService`), 없으면 org 템플릿 | `backend/src/main/java/com/sellerops/review/draft/ReviewDraftComposer.java` | 재사용. scope v1.14 ④로 '리뷰 LLM 제외' 문구를 대체함 |
| 로컬 self-pilot scope | `backend/src/main/java/com/sellerops/selfpilot/SelfPilotProperties.java` | loopback DB 검사만으로 충분하지 않음. 모든 org 대상 성질·계정 격리·외부 통신 별도 검증 |
| Operator WRITE 등록 거부 | `agent-runtime/src/operator/tools/OperatorToolRegistry.ts` | 보존. 별도 실행을 Graph tool로 우회하지 않음 |
| FE API 주소·오류 계측, runtime backend URL | `frontend/src/lib/apiClient.ts`, `frontend/src/main.tsx`, `agent-runtime/src/http/config.ts` | 로컬 주소 고정·공급자 fallback 제거·telemetry 비활성 범위를 감사 |
| 개발용 compose와 pilot 배포 문서 | `infra/compose/docker-compose.local.yml`, `docs/standing/sellerops_local_to_pilot_connectivity_decision.md` | 개발 compose는 오래된 프로토타입 설명을 포함. 판매자 설치기로 그대로 배포하지 않음 |

### 18.2 구현 전 정합화할 충돌

현재 오너 결정은 제품 방향에서 우선하지만, 실제 구현에서 규칙·테스트를 조용히 지우지 않는다. 다음을 첫 변경 단위에서 대조하여 각 문서의 소유 범위만 좁혀 고친다.

| 기존 문서/계약 | 이번 방향과의 차이 | 처리 원칙 |
|---|---|---|
| `docs/product-scope-v1.md` | 설치형 지원 범위, 리뷰 LLM·상품 API·발송에 관한 과거 제한과 이후 코드/결정의 시점 차이 | 현재 오너 결정·후속 승인·실제 증거를 추적해 delta 명시. 포괄 금지 삭제로 해결하지 않음 |
| `docs/standing/sellerops_local_to_pilot_connectivity_decision.md` §2.3 | 외부 pilot에서 중앙 backend/고정 egress로 이전하던 전제 | 새 초기 로컬 NAVER 경로에는 적용하지 않는 범위를 명시. 기존 배포를 갑자기 종료하지 않음 |
| `docs/standing/sellerops_local_agent_runtime_adr.md` | collector 중심 로컬 경계와 OS 지원/상태의 오래된 서술 | 로컬 Spring 포함 배치 경계 확장. 과거 검증 이력은 보존, 상태는 재도출 |

### 18.3 단계별 변경과 완료 조건

**L0. 기준선·계약 정합화**

- root 규칙과 canonical reading path를 읽고, 기능 기준선 및 현재 dependency/호출/저장/계측 지도를 만든다. 저장소 전체에 닿는 전환은 `CLAUDE.md`의 정량 기준선·보존 게이트를 적용한다.
- 실제 운영 DB·runtime holder·브라우저 프로필·기존 credential은 읽거나 이동하지 않고 소스·합성 설정으로 시작한다. 기존 사용자 변경과 생성 자료는 보존한다.
- 결과물: 재사용/이동/차단/미확인 목록, 문서 충돌 조정, 단계별 테스트 명령과 롤백 범위. L0 완료를 전체 migration 완료로 보고하지 않는다.

**L1. 로컬 실행 구성과 통신 차단**

- 판매자용 명시적 local 배포 모드를 만들고 기존 Spring·React·LangGraph·Postgres를 로컬에서 연결한다. frontend는 배포한 로컬 자산을 사용하고 기존 FE 기능/라우트를 보존한다.
- 주소 검증·세션·비밀 저장·로컬 스코프·telemetry OFF·외부 전송 allow-list·중앙 fallback 차단을 먼저 구현한다. 라이선스/배포 서비스는 최소 기능으로 격리한다.
- 완료: 공급자 업무 서버 없이 합성 문의·리뷰·지식·초안·승인 이력이 재시작 후 유지되고, 승인 없는 외부 요청/중앙 복제가 부정 테스트에서 차단된다. '브라우저에 화면이 뜸'만으로 완료하지 않는다.

**L2. 로컬 공식 API 업무의 한 수직 흐름**

- 기존 NAVER 문의·상품 코드를 먼저 감사하고, 합성 HTTP 서버로 조회 -> 상품/지식 연결 -> 준비 -> 승인 -> gated 등록 -> 검증을 연결한다. LLM도 우선 stub, 이후 별도 승인된 최소 입력 경로만 사용한다.
- 재시작·중복 승인·다른 계정·변경된 초안·외부 답변·만료 credential·429·타임아웃·결과 미확인을 검증한다. 실제 미답변 문의에 테스트 답글을 보내며 개발하지 않는다.
- 완료: 합성 흐름에서 외부 효과 1회와 중복 0을 증명하고 기존 승인/실행 계약이 보존된다. 외부 판매자 제공은 §17.8 정책 gate와 별개다.

**L3. 리뷰 수동 대행의 왕복**

- 합성 파일/리뷰 작업 패키지로 담당자 확보 -> 로컬 반영·판단·개별 승인 -> 대행 작업 -> 결과 반영을 검증한다. 교환 저장소와 전송 프로토콜은 최소한으로 시작하고 전용 원격 제어 시스템을 만들지 않는다.
- 오귀속·패키지 변조·중복 업로드·취소·승인 만료·담당자 중복 착수·등록 결과 불명·권한 회수·오프라인을 테스트한다. 사람 등록의 증거 등급을 UI에 정직하게 표시한다.
- 완료: 판매자는 복사·붙여넣기 없이 승인/취소/결과 확인을 할 수 있고, 담당자는 정확한 대상·문장·현재 허가를 확인할 수 있다. 사람의 실제 채널 작업은 별도 라이브 승인 이후다.

**L4. Mac 설치 품질과 Windows 이식성**

- 기존 OS 경계를 재사용해 기동·종료·자동시작 동의·단일 인스턴스·포트 충돌·키 저장·폴더 선택·알림·백업/복구·안전한 업데이트를 묶는다. runtime 버전/의존성을 고정하고 installer의 다운로드 경로도 공개한다.
- 일반 판매자에게 Docker·Java·Node·DB를 각각 설치·관리하게 하지 않는 것을 목표로 한다. 번들/설치 전략은 먼저 작은 배포 spike로 자원 사용·서명·라이선스·백업 복원을 비교한 뒤 결정한다. Tauri/Electron/DB 교체를 지금 확정하지 않는다.
- Cafe24 OAuth 및 Coupang 호출 IP 조건의 설치형 적합성을 개발 초기에 병행 확인한다. 여기서 막히면 앞 단계의 정책 설명·지원 범위를 수정한다.
- 완료: 깨끗한 Mac 사용자 환경에서 설치 -> 합성 첫 업무 -> 재부팅 -> 이력/키 복구가 가능하고, Windows용 OS 어댑터·검증 미완료 항목이 분리된다. Windows 실기 검증 전 지원 완료라고 표시하지 않는다.

**L5. 조건을 충족한 실계정·외부 파일럿**

- 허용 범위·실계정 승인·자료 처리 조건을 갖춘 뒤 실제 사례로 read/준비/승인/실행을 각각 검증한다. Cafe24의 기존 검증은 재사용하고 배포 변경의 영향만 확인한다.
- 실제 수집 최신성, 누락, 응대 필요 판단, 근거/목소리 품질, 판매자 수정량, 담당자 처리시간·원가, 승인부터 확인까지 시간, 중복/오발송을 측정한다. '설치 성공'과 '판매 후 운영시간 감소'를 별도로 평가한다.
- 라이브 증거는 정본 evidence index에 연결하고 capability의 구현/검증/정책/운영 표기를 일치시킨다. 정책 불명 경로를 supported로 바꾸지 않는다.

### 18.4 Claude가 반드시 증명할 핵심 테스트

1. **공급자 비수령:** 합성 고유 표식을 키/원문에 심고 실제 실행 경로의 HTTP·WebSocket·telemetry·파일 전송 목적지를 관측한다. 공급자 목적지 수신 0을 확인한다. 허용된 LLM·리뷰 교환·Cafe24 토큰 중계는 별도 필드 계약으로 검사한다. 문자열 검색만으로 비수령을 증명하지 않는다. **공급자 목적지가 아직 없는 상태의 "0"은 증거가 아니다** — 외부 목적지를 허용 목록으로 고정하고, 목록 밖 목적지(공급자 주소 포함)를 일부러 넣었을 때 실패하고 되돌리면 통과하는 양방향 증명을 함께 낸다.
2. **악성 로컬 접근:** 잘못된 Host/Origin, CSRF, 위조 WS, 미인증 loopback 요청이 업무/키/등록에 접근하지 못한다. 허용 경로의 정상 성공도 함께 증명한다.
3. **권한의 실제 분리:** Graph가 키나 privileged 실행을 얻지 못하고, 모델 출력/문서에 원격 전송 지시를 넣어도 실행되지 않는다. 대상·내용·명령 replay/변조는 등록 전에 거부된다.
4. **재시작 안전성:** 승인/전송 중 crash·DB 복구·중복 시작 후 이미 실행한 효과를 다시 발송하지 않는다. 네트워크 타임아웃 뒤에는 결과 확인만 수행한다.
5. **기능 보존:** 기존 채널·화면·초안·지식·정책·학습·인증·연결 가이드를 기준선과 대조한다. 실패한 테스트를 새 구조라는 이유로 삭제하지 않는다. 단순 숫자 일치에 더해 주요 사용자 흐름을 검증한다.
6. **문서/코드 불일치:** 검사기 자체는 금지 사례를 주입했을 때 fail, 되돌렸을 때 pass를 증명한다. 합성 테스트·모델 호출·실계정 검증을 각각 구분해 보고한다.

### 18.5 남은 선택과 조사

- **[PO]** 판매자 직접 LLM 계약/BYOK의 초기 UX·과금, 로컬 패키징 선택(spike 결과 §18.7), 라이선스 유예 기간, 리뷰 대행 처리회차·인력 비용(리뷰 교환 보유 기준은 §17.9에서 확정). 상세 인터뷰 재개 전 임의 숫자를 확정하지 않는다.
- **[EXT]** NAVER의 유료 설치형 자체 이용 분류와 외부 LLM/리뷰 대행 자료 조건, 적용 약관 전문, 채널별 설치형 등록/IP/OAuth 조건. 법률·플랫폼 허가와 기술 검증을 구분한다.
- **[REPO]** 모든 connector와 publish adapter의 실제 호출 주체, 숨어 있는 중앙 URL·관측 SDK·백업/relay·credential handoff, 현재 승인/발송/정책/지식 계약과의 차이, Windows 포트와 DB 배포 가능성.

미확인 항목은 제품 전체를 포기할 이유도, 허용됐다고 간주할 이유도 아니다. 기능별 경계와 검증 단위를 작게 두고 가능한 개발은 이어가되 외부 효과는 닫아 둔다.

`LOCAL_SINGLE_USER`는 DB의 모든 org를 대상으로 하고 loopback 검사는 datasource 호스트만 본다.
NAVER 문의·상품과 Cafe24 게시판은 backend가 공식 API를 직접 부른다. NAVER 리뷰만 collector 경유다.

**외부 통신 지도 — 로컬 모드에서 막을 것.**
- 바인드: backend는 `server.address`가 없어 모든 인터페이스, Vite dev `host: true`, agent-runtime `listen(port)`, 루트 `docker-compose.yml` 포트 공개.
- 인증: 기본 JWT secret을 거부하는 검사가 없다(`PilotConfigValidator`도 검사하지 않음). Host/Origin 검사·DNS rebinding 방어 없음(CSRF는 bearer header 방식이라 낮은 위험).
- 계측: backend Sentry(`SENTRY_DSN`), frontend Sentry · GTM · PostHog — 모두 env가 있을 때만 켜지지만 로컬 프로필에서 켜지지 못하게 해야 한다. SMTP · 소셜 로그인도 같다.
- 범위: `SELLEROPS_AGENT_ACCESS_SCOPE=ALL_ORGS`는 loopback 확인 없이 모든 org에 동작한다(`AgentCapabilityAccess`).
- agent-runtime: `langsmith`가 간접 의존성으로 설치돼 있고 `LANGCHAIN_TRACING_V2`를 명시적으로 끄는 코드가 없다.

**허용 목록 후보.** 채널 공식 API(NAVER `api.commerce.naver.com`, Coupang `api-gateway.coupang.com`, `{mall}.cafe24api.com`)와
LLM 제공자. LLM 엔드포인트는 약 9개 capability에 하드코딩돼 있어(`api.anthropic.com`, `api.openai.com`) 제공자 선택을 열려면 코드 변경이 필요하다.

**연결 튜토리얼.** 설치 없는 `NaverIssuanceTutorial` · `CoupangIssuanceTutorial`은 재사용한다. helper/bridge에 의존하는
`*IssuanceGuidedWalkthrough`는 v1.14 ⑦에 따라 로컬 설치본에서 뺀다. `AdvertisedCallIpPanel`은 공급자 고정 IP를
안내하므로 **판매자 자신의 현재 공인 IP**를 안내하도록 바꾸고, IP 변경으로 호출이 실패하면 재등록을 안내한다.
현재 IP 확인은 공급자 서버의 최소 응답으로 하고 제3자 서비스를 부르지 않는 쪽을 권고한다.

**기존 결함.** Cafe24 결과 리다이렉트 기본값이 `http://localhost:3000/connect/cafe24/result`인데 Vite는 5173이다(`application.yml`).

**L1 구체 범위(권고).** 기본 동작은 바꾸지 않고 새 `local-seller` 프로필에 가둔다.
1. backend: 프로필 전용 설정 + `PilotConfigValidator`와 같은 형태의 부팅 검사 — loopback 바인드, 기본 JWT secret · Sentry DSN · 메일 · 소셜 로그인 · `ALL_ORGS` · 비-loopback datasource면 부팅 거부. Host/Origin 검사 필터 신설.
2. agent-runtime: listen 호스트 설정화(기본 `127.0.0.1`), LangChain tracing 강제 OFF.
3. frontend: 로컬 빌드에 telemetry env가 있으면 빌드 실패.
4. 외부 통신 허용 목록: JDK `HttpClient` 생성 지점을 한 관문으로 모은다 — 범위가 커서 L1b로 분리.
5. 테스트: 잘못된 Host/Origin · 미인증 loopback 요청 거부와 정상 경로 성공을 같이 증명, 금지 목적지 주입 시 fail · 되돌리면 pass, 기준선 재측정.
6. 롤백: 프로필을 끄면 원상태. migration 추가 없음을 목표로 하고, 필요하면 새 버전만 추가한다(migration 계약 테스트의 글자 순 정렬 주의).

**L1 진행 (2026-10-16).** 1 · 2 · 3 · 5는 `local-seller` 모드로 구현했다(`LocalSellerConfigValidator`,
`LoopbackRequestGuard`, agent-runtime `AGENT_RUNTIME_HOST` · `disableVendorTracing`, frontend `localSellerBuild`).
4는 `OutboundGate`로 구현했다 — backend의 JDK `HttpClient` 10곳이 모두 `send` 직전에 목적지 분류와 함께 검사하고,
판매자 PC 모드에서는 채널 공식 호스트 · LLM 제공자 · 공개 상품 이미지(https) · loopback만 통과한다(ESM · 11번가 ·
SSG는 거부). `OutboundGateFenceTest`가 검사 누락을 막는다. 네이버 호출 IP는 판매자 PC 빌드에서 "이 PC의 공인 IP"를
안내하고(`AdvertisedCallIpPanel`), backend는 그 모드에서 공급자 고정 IP 설정을 요구하지 않는다. 남은 것: 패키징 spike.

**다음 작업 (2026-10-17 기준, 코드는 브랜치 `feat/local-seller-mode-l1`).**
1. **공급자 서버의 범위와 API 계약** — §17.9 표의 공급자 서버 책임(리뷰 교환 · 모바일 승인 상태 머신 · Cafe24 토큰
   중계와 응답 유실 복구 · 공인 IP 확인 · 라이선스)을 엔드포인트 · 저장 필드 · 보유 기준 단위로 정한다. 기존 AWS
   자산(`deploy/`)을 재사용한다.
2. **패키징 비교** — 판매자 PC 설치본(JRE · Postgres · Node · React 정적 자산)의 번들 방식을 작은 spike로 비교해 오너
   확인을 받는다.
3. **AI 전송 관문 [REPO]** — LLM 경로에 본문 검사 + 불확실 시 보류 단계 신설(§17.9). 사진 · 과거 답변 · 지식 포함.
4. 공인 IP 자동 감지는 1의 서버 엔드포인트가 생기면 연결 화면에 붙인다.

패키징(JRE · Postgres · Node 번들) spike는 L4가 아니라 L1과 병행한다. 판매자 PC에 Postgres를 넣는 방식이 가장 큰 미지수이고 L1의 설계에 영향을 준다.

**3의 결과 — AI 전송 관문 (2026-10-17).** `backend/.../outbound/LlmSendGate.java`. LLM으로 가는 길은 전송 클래스 두 곳
(`JdkAgentLlmTransport` · `JdkLlmHttpClient`)뿐이라 그 두 곳에서 조립이 끝난 JSON 전체를 검사한다 — 문의 · 리뷰 · 과거
답변 · 검색된 지식 · 사진이 모두 같은 검사를 지난다. 판매자 PC 모드(`OutboundGate`가 켜진 상태)에서만 동작하고, 그 밖에서는
본문을 바이트 그대로 둔다.
- **제거하고 보냄:** 휴대전화 · 지역번호 전화(대표번호 `1588-…`은 판매자 업무 번호라 남김), 이메일, 12자리 이상 연속 숫자와
  하이픈으로 묶인 10자리 이상 번호(주문 · 송장 · 계좌 · 카드 · 주민번호). 자리에 `[전화번호]` · `[이메일]` · `[번호]`를 넣고
  되돌리지 않는다(경계 4).
- **보류하고 안 보냄:** 도로명 · 지번 · 아파트 동호수 주소, 상품 이미지로 선언되지 않은 사진(리뷰 사진 포함), 읽을 수 없는
  본문. 보류는 `status 0` + `held:<종류>`로 돌아가 각 기능의 기존 fail-closed 경로("초안 없음")를 탄다. 상품 상세 이미지만
  `postProductImages`로 검사 없이 보낼 수 있고 그 호출자는 하나로 고정했다.
- **증명:** 단위 11 · fence 1 · 전송 3, 백엔드 전체 5412건 0 실패. 양방향: 원문 전송 · 비허용 호출자 · 관문 끄기 세 경우 모두
  빨강 → 되돌리면 초록. `AgentDraftBoundaryTest`의 전송 호출 검사가 `postProductImages`도 보도록 넓혔다.
- **남는 한계:** 자유문 속 이름, 시 · 구 없이 쓴 주소, 11자리 이하 송장번호는 모양으로 잡히지 않는다 — "검출 없음"은
  "깨끗함"이 아니다. 판매자 자신의 연락처가 지식에 있으면 그것도 지워진다. 보류 사유를 판매자 화면에 보여 주는 것과
  "로컬에서 고쳐 다시 보내기"는 FE delta로 남는다. 리뷰 사진 분석은 판매자 PC 모드에서 현재 늘 보류된다.

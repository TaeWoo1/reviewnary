## §0 이 문서가 소유하는 것

1. 네이버 톡톡 **챗봇 API**(커머스 API가 아니다) 레인의 행동 계약: 연결 · 수신 · 대화 · 답변 · 전송 · 인계.
2. **현재 개별 승인 계약에 대한 좁은 예외 하나**(§6). 다른 문의 · 리뷰의 승인 동작은 바뀌지 않는다.
3. 공식 문서에서 확인한 것 / 확인하지 못한 것(§1), 보관 기한과 모델 전송 최소 범위(§2, §8), 남은 경계(§9).
4. 판매자가 네이버 쪽에서 해야 하는 준비 — 챗봇 API 신청 순서와 조건(§3-1).

## §1 공식 계약 — 확인한 것과 확인하지 못한 것

출처: [navertalk/chatbot-api README](https://github.com/navertalk/chatbot-api) ·
[handover_v1.md](https://github.com/navertalk/chatbot-api/blob/master/handover_v1.md) (2026-11-16 Aside로 원문 열람, Codex 교차 확인).

| 항목 | 공식 문서 | 이 레인의 처리 |
|---|---|---|
| 수신 | 등록한 URL로 `POST` JSON. 연결 3초 · 읽기 5초. HTTP 200만 성공 | 저장 커밋 뒤에만 빈 200. 응답에 메시지를 싣지 않는다(동기 응답 0) |
| 수신 인증 | **서명 · 챌린지 · 공유 비밀 없음.** TLS와 ACL용 IP 4대역만 문서화 | 요청 인증을 지어내지 않는다. 신뢰 경계 = 추측 불가 경로 토큰 + 문서화된 출발 대역 + HTTPS. 확인 전 실연동 준비는 막힘(§3) |
| 이벤트 식별 | **이벤트 · 메시지 ID, 시각, 순서 번호 없음** | exactly-once를 주장하지 않는다. 같은 본문은 「중복 의심」으로 남기고 자동 안내를 다시 보내지 않는다(고객이 정말 반복했을 수 있으므로 지우지 않는다). 순서는 수신 순 |
| 재전송 | 200 외는 「실패 로깅」. 재전송 약속 없음 | 저장 실패 503. 놓친 이벤트가 다시 온다고 가정하지 않는다 |
| 사용자 식별 | `user` = 네이버 아이디에 대응하는 변하지 않는 값 | **주문 식별로 쓰지 않는다.** 봉인 저장 + `sha256(orgId:user)`로만 찾는다. 화면엔 해시 별칭만 |
| 상품 정보 | `options.product.name`은 `inputType=product`인 `send`에만 문서화 | 그 이름만 보관. 이름이 정확히 한 상품과 같을 때만 상품으로 묶는다(§5) |
| 보내기 API | `POST https://gw.talk.naver.com/chatbot/v1/event`, `Authorization: <키>` | 목적지는 **코드에 고정**(속성 없음): https · 기본 포트 · user-info/쿼리/조각 없음 · 리다이렉트 안 따름. 키는 org별 봉인 |
| 보내기 결과 | HTTP 200에도 `success=false`·`resultCode` 01/02/99 | JSON **불리언** `success:true` + 문자열 `"00"`만 「톡톡 접수」. `false`는 실패, 나머지(문자열 "true", 누락, 5xx, 시간 초과)는 결과 모름 |
| echo | 상담원 메시지와 **챗봇 자신의 메시지**가 온다 | echo로 답하지 않는다. `sourceId=1`이면 상담원 응대로 소유권 `PARTNER`, 대기 자동 안내 취소 |
| 인계 | `passThread`(targetId 1) · 상담 완료 시 챗봇으로 `passThread` · `takeThread` | 소유권을 DB에 저장. `standby`가 빠져도(챗봇 버튼 클릭) 저장된 소유권이 자동 안내를 막는다 |
| 과거 대화 조회 · 주문 연결 | 문서에서 확인 못 함 | 만들지 않는다. 불가능으로 단정하지도 않는다 |

## §2 데이터와 보관

`V191__talktalk_lane.sql`: `talktalk_connections`(org당 1, **generation**) · `talktalk_events` · `talktalk_conversations`
(파트너별) · `talktalk_messages` · `talktalk_drafts` · `talktalk_outbound`(outbox, generation) ·
`talktalk_shipping_guidance`(버전, 확정본 org당 1 — 부분 유일 색인) · `talktalk_delegations`(append-only).

- 원 본문은 SHA-256만. 정규화 필드(종류 · 본문 · 입력 종류 · standby · sourceId/threadOwnerId · handover control · 상품 이름)만 저장.
- 사용자 값은 `LocalSecretSealer`로 봉인. 봉인 키가 없으면 연결 · 수신을 거부(fail closed).
- **보관:** 메시지 · 초안 · 발신 · 이벤트의 텍스트는 `sellerops.talktalk.retention-days`(기본 90일) 뒤 지운다(`purged_at`).
  행 · 상태 · 지문은 감사 기록으로 남는다. 대화의 봉인 사용자 값은 대화가 이어지도록 남는다.

## §3 연결 · 세대 · 실연동 준비

- 연결(소유자만): 파트너 아이디 + 보내기 API 키. webhook 주소는 **한 번만** 보인다(토큰은 해시만). 키는 다시 보이지 않는다.
- **연결 세대(generation):** 재연결(다른 파트너·키 포함) · 주소 재발급 · 해제마다 오른다. 이벤트와 발신은 만들어진 세대에
  묶인다. 세대가 바뀌면 대기 발신을 모두 취소하고, 옛 세대 이벤트는 무시(`STALE_GENERATION`)하고, 첫 이벤트 확인을 지운다.
  디스패처는 세대가 다르면 `CONNECTION_CHANGED`, 대화의 파트너가 다르면 `PARTNER_CHANGED`로 막는다 — 옛 가게의 대화를 새 계정
  키로 보내지 않는다.
- **잠금 순서:** 연결 행 → 대화 행. 수신 · 처리 · 전송 요청 · 디스패치 · 기준 확정/내림 · 위임 · 재연결이 모두 이 순서로 잠근다.
  수신은 토큰으로 org id만 읽고 잠근 행을 처음 읽는다(캐시된 옛 엔터티 저장이 재발급을 되돌리던 결함, FINDINGS B196).
- **전송 방식은 연결 행에 기록:** `FAKE`(기본) 결과는 `FAKE_RECORDED`뿐 — 「톡톡 접수」로 세지 않는다. 화면 머리에 「모의 전송」.
- **실연동 준비(모두 충족해야 READY):** `CONNECTION_LIVE_MODE` · `LIVE_SEND_FLAG` · `HTTPS_PUBLIC_URL` · `SOURCE_ALLOWLIST` ·
  `SEND_KEY` · `INGRESS_OBSERVED`(이번 세대에서 허용 대역 + 토큰으로 들어온 첫 이벤트). LIVE 발신은 디스패치 직전에 이 목록
  전체를 다시 보고, 하나라도 빠지면 `BLOCKED(LIVE_NOT_READY)`. LIVE 연결에서 허용 대역 밖 이벤트는 자동 안내 대상이 아니다
  (`UNTRUSTED_SOURCE`). 서명이 없으므로 잔여 위험(대역 안 위조, 주소 유출)을 화면에 적는다.
- `X-Forwarded-For`는 설정된 신뢰 프록시에서 온 요청일 때만 읽는다. 본문은 64KB 상한을 **스트림에서** 지킨다(청크 포함).
- 서버 출구: `OutboundGate.Destination.TALKTALK` 검사를 지난다(판매자 PC 설치에서는 거부).

## §3-1 판매자 쪽 준비 — 챗봇 API 신청 순서와 조건 (2026-11-17 조사)

실연동의 앞단은 **가게가 네이버 톡톡 파트너센터에서 직접** 하는 일이다. 리뷰너리는 대신 신청하지 않고, 판매자가 받은 값만
연동 설정(`/settings/talktalk`)에 넣는다. 아래는 문서 조사 결과이고, **파트너센터 화면을 실제로 열어 확인한 것이 아니다.**

### 순서

| # | 누가 · 어디서 | 할 일 | 막는 것 |
|---|---|---|---|
| 1 | 판매자 · 파트너센터 | 지금 고객 상담을 받는 **스마트스토어 연결 톡톡 계정을 그대로** 쓴다. 새로 만들면 내계정관리 → 「새로운 톡톡 계정 만들기」 → 「서비스 연결 나중에 하기」 → 유형 「국내사업자」(「개인」은 테스트용) → 사용신청. 새 계정은 검수(안내상 1~2 또는 1~3영업일) 뒤 「사용중」 + SMS | 없음 |
| 2 | 판매자 · 스마트스토어센터 | **쇼핑챗봇 · AI FAQ를 끈다.** 켜져 있으면 챗봇 API가 동작하지 않는다는 연동 업체 안내가 있다(끈 뒤 재신청이 필요할 수 있음) | 없음 |
| 3 | 판매자 · 파트너센터 「챗봇API 설정」 | 신청서 작성 + 이용약관 동의 → **파트너 아이디**(예: `wc1234`)와 **보내기 API 인증 키**(「보내기 API → 생성」). 메뉴 위치는 공식 문서상 「개발자도구」 아래, 연동 업체 안내상 「연동 관리」 아래 — 화면이 바뀌었을 수 있다 | 없음 |
| 4 | 판매자 · 리뷰너리 `/settings/talktalk` | 파트너 아이디 + 보내기 키 입력 → 리뷰너리가 **받는 주소를 한 번만** 보여 준다 | **운영 HTTPS 서버**(배포) |
| 5 | 판매자 · 파트너센터 「챗봇API 설정」 | Webhook 「이벤트 받을 URL」에 4의 주소 등록 · 이벤트 선택에서 메시지(`send` · `open` · `leave`)와 **`echo`** 켜기 · **핸드오버 API ON** | 4 |
| 6 | 운영 · 리뷰너리 서버 | 출발 대역 허용(§1 · 아래), 서버 실제 전송 플래그 | 배포 · 운영 승인 |
| 7 | 판매자 + 리뷰너리 | `https://talk.naver.com/<파트너아이디>`에서 메시지 1건 → **첫 이벤트 확인**(§3 `INGRESS_OBSERVED`) → 전송 방식 실제로 전환 | 1~6 전부 · 실연동 승인 |

1~3은 배포와 무관하게 지금 할 수 있다. 4 이후는 운영 HTTPS 주소가 있어야 한다.

### 조건과 주의

- **받는 주소:** 정식 인증 기관 인증서의 HTTPS(문서상 TLS 1.0~1.2). 연결 3초 · 읽기 5초 안에 HTTP 200. 출발 IP
  `211.249.40.0/27` · `211.249.68.0/27` · `220.230.168.0/27` · `103.6.173.0/27`. 수신 서명 · 이벤트 ID는 없다(§1).
- **핸드오버 API를 꺼 두면** 상담원 넘기기(`passThread`)가 동작하지 않는다. 이 가게는 상담원이 파트너센터에서 직접 응대하므로
  켜는 것이 전제다(§4 · §5의 소유권 처리가 이것을 가정한다).
- **echo를 켜야** 상담원이 파트너센터에서 보낸 답을 리뷰너리가 보고 자동 안내를 멈춘다. echo에 다시 답하면 무한 반복이 된다는
  공식 경고가 있다 — 이 레인은 echo에 답하지 않는다(§4).
- **보내기 키가 새면** 파트너센터 「재설정」으로 바꾸고 리뷰너리에서 다시 연동한다. 재연동은 세대를 올려 옛 키로 대기하던 발신을
  모두 취소한다(§3).
- **신청 주체:** 그 톡톡 계정의 관리자. 키와 받는 주소는 가게마다 따로다(조직별 연결 1개, §3).
- **만 14세 미만:** 챗봇이 개인정보를 수집하면 법정대리인 동의가 필요하다(공식 문서, 개인정보보호법 제22조). 이 레인은
  개인정보를 묻지 않는다 — 묻는 기능을 넣을 때 다시 본다.
- **주문 정보는 오지 않는다.** 톡톡 이벤트에 주문이 없고, 외부 업체의 구매이력 연동 신청 경로도 공식적으로 불명확하다는 문의가
  있다(아래 출처). 그래서 주문 질문은 사람에게 간다(§6).
- **연동 업체 1:1 제약:** 한 톡톡 계정의 Webhook URL은 하나다. 다른 상담 도구(채널톡 · 해피톡 등)에 이미 연동돼 있으면 그쪽과
  동시에 쓸 수 없다 — 바꾸기 전에 지금 연동 상태를 판매자에게 묻는다(문서상 단일 URL에서 나온 추론, 화면 확인 필요).

### 확인하지 못한 것 (파트너센터 화면을 열면 바로 확인됨)

- 챗봇 API 신청 자체에 계정 검수 외의 심사 · 자격 조건이 있는지.
- 이용약관 세부 내용(재위탁 · 데이터 보관 · 광고성 메시지 제한 등).
- 신청할 때 받는 주소가 필수인지, 나중에 넣어도 되는지(필수라면 4 → 3 순서로 바뀐다).
- 쇼핑챗봇 · AI FAQ 충돌이 지금도 유효한지(연동 업체 안내만 있다).

## §4 대화 처리 (비동기)

이벤트는 조건부 갱신으로 하나씩 가져간다. `open` 대화 생성 · `send`(고객) 저장, `standby`면 소유권 `PARTNER`, 같은 본문 10분 안
재수신은 중복 의심(원래 건의 안내를 취소하지 않고 자기 안내도 없음), 새 메시지는 대기 자동 안내를 대체 · `echo` 우리 발신과
지문이 맞으면 「echo 확인」만, 상담원(`sourceId=1`)·모르는 발신이면 대기 자동 안내 취소 · `handover` 상담 완료 → `BOT` ·
`leave` 기록 · 그 외 무시. **사진 · 카드 메시지**(`imageContent` · `compositeContent`)는 내용을 저장하지 않고 종류만 남긴다 — 화면은 「사진을 보냈어요 — 파트너센터에서 확인」으로 보이고, 자동 안내 · 답변 준비 없이 사람(`NON_TEXT`)으로 간다. 첨부 저장 기능은 없다.

## §5 답변 준비와 직접 전송 (기존 개별 승인과 같은 규율)

- **준비:** ① 확정 배송 기준으로 코드가 쓴 문장(`GUIDANCE`) ② AI 답변 기능이 켜진 org만 `KnowledgeSpineService.retrieveForProduct`
  + `AgentDraftService.draft`(`MODEL`) ③ 판매자 편집(`SELLER_EDIT`).
- **모든 문장에 같은 검사**(`TalkTalkDraftService.textHolds`, 준비 · 편집 · 전송 요청 · 디스패치에서 같은 함수):
  `InquiryClaimGuard.unsupportedClaims`(약속 · 고객 행동 · 구제 · 조건 · 법 · 비용 부담 · 숫자) · `CostBearerCheck.judge`를 쓰는
  모든 자료 기준으로 반대면 `COST_CONFLICT` · `ClaimReader`+`KnowledgeState`로 자료와 다른 값 `POLICY_CONFLICT`, 정해지지 않은 값
  `UNSETTLED_VALUE` · `AnswerStyleInstruction.forbiddenPresentIn` 금지 표현 `FORBIDDEN_PHRASE`. 배송 기준 문장은 지금 다시 그린
  문장과 같아야 한다(`TEXT_CHANGED`)과 금지 표현 검사.
- **등급(ReplyHoldService와 같은 체계):** FIX_FIRST(`POLICY_CONFLICT` · `COST_CONFLICT` · `UNSETTLED_VALUE` · `KNOWLEDGE_CONFLICT` ·
  `FORBIDDEN_PHRASE` · 검사 불가 · 근거 기록 판독 불가)는 어떤 확인으로도 못 보낸다. 판매자 편집의 나머지 표시(`CLAIM_*`)는
  「이번 건만 예외」 확인(`confirmHolds`)과 함께만, 그 코드가 발신 행(`hold_confirmed`)에 남는다. 모델 · 기준 문장의 표시는 고쳐 써야 한다.
- **상품 범위:** 대화의 상품 이름이 이 org의 상품 **정확히 하나**의 이름이면 그 상품으로 검색 · 검사한다(`findIdsByOrgIdAndName`,
  좁은 조회). 아니면 회사 범위로만 쓰고 `PRODUCT_UNRESOLVED`를 단다 — 다른 상품의 자료를 이 상품 것으로 쓰지 않는다.
- **주문 사실은 만들지 않는다:** 모델에는 고정 문장 「확인된 주문 정보가 연결되어 있지 않다」만. 주문 · 도착 질문은 표시된다.
- **전송:** 같은 org 로그인 사용자. `commandId` + `draftVersion` + `expectedFingerprint`. 연결 → 대화 행을 잠그고 머리 버전 ·
  지문 · 표시 · 재검사 · 파트너 · 더 새 고객 메시지 · 이 대화의 보내는 중 · 같은 메시지에 같은 답 기보냄 · **미해결 결과 모름**
  (대화 단위 — 같은 문장의 새 버전도 확인 없이는 못 지나감)을 본다. 디스패치 직전에 **재검사 · 더 새 메시지 · 세대 · 준비**를
  다시 본다. 결과 기록은 같은 잠금 순서로, 전송 중 새 고객 메시지가 왔으면 「사람 확인」을 지우지 않는다.
- **결과 상태:** `QUEUED` · `SENDING` · `FAKE_RECORDED` · `API_ACCEPTED`(톡톡 접수) · `FAILED` · `UNKNOWN` · `CANCELLED` · `BLOCKED`.
  어느 것도 「고객이 받음 · 읽음」이 아니다. echo 확인도 수신 증거가 아니다.
- **재시도 0:** `FAILED`는 새 명령으로, `UNKNOWN`은 「톡톡에서 가지 않은 것을 확인함」(`acknowledgeUnknownOf`)과 함께만.
  2분 넘은 `SENDING`은 `UNKNOWN(INTERRUPTED)`.
- **인계:** 「상담원에게 넘기기」(`passThread` 1) · 「챗봇으로 가져오기」(`takeThread`). 같은 outbox · 같은 결과 판정.

## §6 좁은 예외 — 확정된 휴무 · 출고 마감 기준의 자동 안내 (오너 승인 2026-11-16)

**현재 계약:** 고객에게 나가는 답은 판매자가 그 문장을 승인한 뒤에만 나간다(scope v1.15, 서버 운영 경계 §3.2-2).
**예외:** 아래를 **모두** 만족하는 톡톡 고객 메시지 하나에, 오너가 확정 · 위임한 기준으로 코드가 만든 문장을 개별 승인 없이
보낸다. 「조건 자체를 판매자가 승인한 기록」은 `talktalk_delegations` 행이다.
**범위 밖(그대로):** 다른 문의 · 리뷰 · 채널의 자동 전송, 모델 문장의 자동 전송, 주문 · 재고 · 환불 판단. reply graph 초안 전용,
Operator 도구 읽기 전용 그대로 — 이 레인은 agent-runtime을 부르지 않는다.

1. **위임(기본 OFF, 소유자만).** 기준 버전 id + 기준 지문 + 미리보기 지문(렌더러 버전 포함). 새 버전 확정 · 기준 내림이면 꺼진 것과
   같다(`DELEGATION_STALE`). 끄기 · 다시 켜기도 행 하나이며 그 전 행으로 대기하던 안내는 취소된다.
2. **기준(`CONFIRMED`만).** 마감 시 · 분, 출고 요일, 휴무일(공휴일 포함 — 제품이 모름), 휴무일 확인 기한. 확정본은 불변.
   이 기준이 가게의 출고 마감 · 휴무일 **유일한 값**이다(오너 결정 2026-11-17). 기본 설정 질문지(`knowledge/defaults/`)는 이 값을
   읽기만 하고, 확정 · 내림 때 `TalkTalkGuidanceListener`로 같은 트랜잭션 안에서 「배송 안내 (기본 설정)」 문서를 다시 쓴다.
3. **메시지(결정론 · 닫힌 어휘).** `typing` · 120자 이하 · 이름 붙은 제외(주문 · 송장 · 결제 완료 · 「제 주문」 · 실제 출고/도착 ·
   도착일 · 재고 · 취소/환불/반품/교환 · 주소/옵션 변경 · 불량 · 가격/배송비) · **특정 날짜**(연 · 월/일 · `N/N` · `N일` · 다음
   주/달 · 모레 · 명절 · 공휴일 — 문장은 「지금 · 다음 출고일 · 다가오는 2주 휴무」만 말하므로) 가 없고, **모든 단어가** 출고 마감 ·
   출고 요일 · 휴무 · 요일/시각 · 인사 · 어미의 닫힌 목록 안이어야 한다. 「몇 시 마감인가요 그리고 설치도 해주시나요」는 사람.
4. **사실.** 문서의 출고 마감 값이 시 · **분**까지 기준과 다르면 사람(`KNOWLEDGE_CONFLICT`). 상품 문서의 출고 마감 · 제작 기간,
   회사 문서의 제작 기간, 상품 일정 줄이 있으면 「예외 상품 있음」 — 상품을 보고 온 대화는 사람(`PRODUCT_EXCEPTION_POSSIBLE`).
   기준 은퇴 · 마감 없음 · 다음 출고일이 확인 기한 밖 → 사람.
5. **대화.** 소유권 `BOT`(저장값) · `standby` 아님 · 해결 안 된 인계 요청(대기 · 전송 중 · 결과 모름 · 막힘) 없음 · 상담원 echo
   없음 · 나간 뒤 아님 · 중복 의심 아님 · 24시간 안 자동 안내 없음 · 진행 중 자동 안내 없음 · LIVE면 신뢰 경계로 들어옴.
6. **보내기 직전(연결 행 잠금 아래) 1~5 전부 다시**, 그리고 위임 행 · 기준 지문이 발신 행과 같음 · 더 새 고객 메시지 없음 ·
   10분 안에 만들어짐 · 세대 · 전송 방식 · 다시 그린 문장이 같음. 다르면 `CANCELLED` + 사유, 보내지 않는다.
7. **문장.** 기준 필드로 코드가 만든 고정 문장: 요일 · 마감 기준, 오늘 휴무, 오늘/다음 출고일, 2주 안 휴무일, 「재고 확인 ·
   주문 제작 · 예약 상품은 달라질 수 있어요」, 「이미 주문하신 건은 말씀해 주시면 담당자가 확인」. 모델 0.

판정 결과(자동 안내 예약 / 사람 확인 + 사유)는 대화에 남고 화면에 보인다. **자동으로 답하지 않는 것**(위임 화면에 그대로):
특정 주문의 실제 출고 · 도착 · 송장 · 도착일, 재고 · 주문 제작 · 예약 · 기준이 다른 상품, 취소 · 환불 · 교환 · 변경 · 불량 ·
가격, 기준 밖 요청이 섞인 메시지, 특정 날짜, 상담원 대화, 중복, 24시간 안 재문의, 기준 변경 · 충돌 · 기한 초과.

## §7 화면

- `/talktalk` 톡톡 상담(리뷰·문의 묶음, 리뷰/문의 전환에 「톡톡」): 목록 + 대화(PC 두 칸, 좁으면 `/talktalk/:id` 한 칸).
  보이는 동안 다시 읽는다(목록 10초, 대화 6초 · 보내는 중 2초). 고치던 문장은 덮지 않고 알린다. 확인(2단계 전송 · 결과 모름 확인 ·
  예외)은 그 기준이 바뀌면 풀린다. 늦은 응답 · 다른 대화의 응답은 표시하지 않는다(요청 순번). 거절(`NEWER_MESSAGE` ·
  `DRAFT_CHANGED` 등) 뒤 최신을 다시 읽는다. 보내는 동안 입력 잠금.
- `/settings/talktalk` 연동 · 실연동 준비 목록 · 배송 기준 버전 · 미리보기 · 자동 안내 위임(자동/사람 범위 목록).
- 홈: 「톡톡 상담 · 사람 확인 대기 대화 N개 · 결과 모르는 발신」 줄과 「홈의 문의·리뷰 숫자에는 톡톡이 들어가지 않아요」. 대화 단위로 센다.
  마켓 채널이 하나도 연결되지 않은 가게(톡톡만 쓰는 가게)의 첫 사용 홈에도 같은 줄이 제목 아래 나온다(FINDINGS B200).
- 열린 대화를 다시 읽다가 목록에 보이는 값(맡은 쪽 · 사람 확인 · 발신 상태)이 바뀌면 목록도 바로 다시 읽는다 — 보낸 뒤 목록이 10초 동안 옛 상태로 남지 않는다.
- 새 채널 코드 없음(NAVER 아래 표면). 디자인 계약 `docs/frontend/reviewnary_design.md`, 시각 울타리 목록에 추가.

## §8 모델 전송 최소 범위

`MODEL` 초안 1회: 고객의 **마지막 메시지 한 개**(전송기의 `LlmSendGate`가 전화 · 이메일 · 긴 숫자 제거), 같은 org 검색 근거 문단,
확정 기준 규칙 한 문장, 고정 주문 문장. 가지 않는 것: 사용자 값 · 파트너 아이디 · 이전 대화 · 상담원 이름 · 상품 URL · 키.
자동 안내는 모델을 부르지 않는다. AI 답변 기능이 꺼진 org는 모델을 부르지 않고 이유를 보인다.

- 서명이 없으므로 대역 안 위조 · 주소 유출은 막을 수 없다. 이벤트 ID가 없어 같은 본문의 재수신과 고객의 진짜 반복을 구별하지 못한다.
- 기존 문의 레인 재검사 중 이 레인에 **없는 것**: 판매자 확인 요청(seller-check) 흐름, 주문 사실 대조(주문이 연결되지 않으므로),
  `figuresToVerify`의 모델 숫자 재확인 단계(모델 초안은 숫자 위반이 있으면 보류로 끝난다), 문의 승인 원장(`InquiryApproval`) 사용 —
  이 레인의 원장은 `talktalk_outbound`(행위자 · 명령 · 지문 · 확인한 보류)와 `talktalk_delegations`다.
- 상품 결합은 이름 완전 일치 한 건만. 상품 번호(URL의 `p=`) 결합은 하지 않는다. 문서의 시각은 「N시 M분 / N:MM / N시 반」만 분을 읽는다.
- 자동 안내 문장은 「지금 · 다음 출고일 · 2주 안 휴무」만 말한다. 특정 날짜 질문은 모두 사람에게 간다(달력 기능 아님).
- 보내기가 전송기로 넘어간 뒤의 위임 끄기 · 재연결은 그 한 건을 되돌리지 못한다(잠금으로 「보내기 전 재검사」와 직렬화될 뿐).

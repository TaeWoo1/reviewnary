## 0. 용어

| 말 | 뜻 |
|---|---|
| 고객 · 조직 | 판매자 회사 하나 = backend `organizations`의 한 행. 모든 업무 자료는 조직에 속한다 |
| 사용자 | 조직에 속한 사람의 로그인 계정(backend `users`). 지금은 전원이 `OWNER`이다 |
| 담당자 | 공급자 쪽 사람(NAVER 리뷰 대행). vendor-server 계정이며 판매자 조직의 사용자가 아니다 |
| 운영자 | 공급자의 관리자. vendor-server 운영 명령을 쓴다 |
| 두 서버 | 업무 서버 = backend(문의 · 리뷰 · 지식 · 초안 · 승인 원장)와 교환 서버 = vendor-server(담당자 데스크 · 리뷰 반입 · 대행 작업 상태) |

## 1. 연결은 조직 단위다 — 단일 설치 가정 해소

**무엇이 문제였나 (2026-10-31 전).** backend의 공급자 서버 연결(`vendorlink/`)은 판매자 PC 하나를 전제로 만들어졌다.
- 연결 기록(`vendor_install_link`)이 backend 전체에 한 행뿐이었다.
- 설치 토큰을 꺼낼 때 조직을 묻지 않았다(`installToken()`).
- 대기 중인 연결 코드와 공인 IP 응답도 프로세스에 하나씩만 있었다.
- 예약 받기는 모든 조직의 스토어를 그 토큰 하나로 돌았다.

판매자 PC에서는 조직이 하나라 문제가 없었다. backend 하나에 조직이 여럿이면, 한 판매자의 공급자 계정이 모든 조직에 열린다.

**지금의 규칙 (구현됨, V161).**
1. 연결 기록은 **조직마다 많아야 한 행**이다(`org_id` NOT NULL + 유일 색인).
2. 모든 연결 동작은 **자기 조직을 인자로** 받는다: 상태 · 시작 · 확인 · 해제 · 공인 IP · 토큰. 화면 API는 로그인한 사용자의 조직만 넘긴다.
3. 대기 중인 코드와 IP 캐시는 조직별로 따로 둔다. 한 조직이 코드를 받아도 다른 조직의 코드나 연결이 바뀌지 않는다.
4. 예약 받기는 연결된 조직을 하나씩 돈다. 각 조직은 **자기 토큰으로 자기 스토어만** 읽는다. 한 조직의 실패(회수된 설치 · 거절)가 다른 조직을 막지 않는다.
5. 도착 대기(long-poll)도 조직마다 따로 묻는다. 묻는 범위는 그 조직의 스토어뿐이다.
6. 다른 조직에 묶인 스토어는 보여도 받지 않는다(`OTHER_ORGANISATION`). 연결이 없는 조직은 스토어 목록조차 받지 못한다.

**기존 판매자 PC 데이터.** 마이그레이션이 기존 한 행을 다음 순서로 조직에 붙인다.
- 리뷰 받기를 처음 시작한 조직에 붙인다.
- 받기를 시작한 적이 없으면 가장 먼저 만든 조직에 붙인다.
- 조직이 없는 행은 생길 수 없었으므로 지운다.

한 PC에서 두 조직이 서로 다른 스토어를 받던 드문 경우, 둘째 조직은 「이 PC 연결」을 다시 해야 한다.

**증거.** 아래를 통과했다.
- `VendorLinkServiceTest` 3건(두 조직 연결 · 동시 대기 · 재연결)
- `VendorReviewPullScenarios` 2건(H2 + Flyway로 V161까지 올린 PostgreSQL 15)
- `VendorReviewArrivalWatchTest` 2건
- V161 백필 네 경우(받기 조직 · 가장 먼저 만든 조직 · 조직 없음 · 빈 표)를 실제 PostgreSQL 15에서 확인

양방향 증명도 했다. 토큰 조회가 조직을 무시하게 바꾸면 컴파일은 되고 새 시험 4건이 실패한다. 되돌리면 통과한다.

**서버형에서 남는 것 [REPO].**
- 도착 대기는 연결된 조직마다 스레드 하나다. PC에서는 하나이고 파일럿 규모에서는 맞다. 조직이 수십 곳을 넘으면 두 서버 사이의 도착 알림 하나로 바꾼다(§5 규칙 3).
- 연결 기록을 만드는 방식(판매자의 기기 승인 코드)은 PC용이다. 서버형은 §5의 운영자 매핑을 쓴다.

상태: 구현됨 (2026-10-31, 커밋 전).

## 2. 고객별 권한

**사실 [REPO].**
- 로그인 주체는 `(userId, orgId, email)` 하나다.
- `users.role`은 모든 계정이 `OWNER`이다. 역할 모델은 설계된 적이 없다(`User.java` 주석).
- 업무 조회는 org 범위 저장소 메서드(`findByIdAndOrgId` 등)가 막는다.

### 2.1 격리 규칙

1. **모든 업무 자료는 조직 하나에 속한다.** 문의 · 리뷰 · 상품 · 지식 · 응대 기준 · 초안 · 승인 · 실행 기록 · 채널 자격 · AI 사용량이 그렇다. 조직을 건너는 조회 · 검색 · 집계 · 학습은 없다.
2. **ID 하나로 찾는 경로도 조직을 같이 확인한다.** 리뷰 ID처럼 전역 유일한 ID라도, 받은 ID가 요청자의 조직 것이 아니면 "없음"으로 답한다. "권한 없음"으로 답해 존재를 알리지 않는다.
3. **예약 작업 · 백그라운드 작업은 조직을 명시해서 돈다.** 한 번에 여러 조직을 다루는 반복은 각 단계가 그 조직의 자격 · 토큰 · 설정만 쓴다. §1의 예약 받기가 그 본보기다.
4. **검색 색인 · 임베딩 · 캐시 키에 조직이 들어간다.** 과거 답변 · 지식 검색이 다른 조직 문장을 근거로 가져오지 않는다.
5. **공급자 직원은 판매자 업무 화면에 들어가지 않는다.** 담당자는 vendor-server에서 배정받은 스토어의 리뷰와 승인된 답글만 본다. 운영자의 진단은 본문 없는 코드와 요청 ID로 한다. 원문을 봐야 하는 지원은 판매자가 그 건을 지정해 열어 줄 때만 한다(§19.2 관측 · 지원).

**검증 계획 [REPO]** — 서버형 첫 배포 전:
- org 범위가 아닌 저장소 호출(`findById` · `findAll` · 전역 ID 조회)을 전수 목록으로 만든다.
- 각 호출이 조직을 확인하는지 시험으로 고정한다.
- 숫자는 두 방법(정적 검색 · 런타임 호출 기록)으로 세어 맞춘다(`CLAUDE.md` 검사 도구 규칙 5).

### 2.2 조직 안의 역할

최소한으로 시작한다. 셋 다 같은 조직의 업무 화면을 쓰고, 차이는 할 수 있는 동작뿐이다.

| 역할 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|
| 소유자 | 아래 전부. 채널 연결 · 해제, 사용자 초대 · 회수, AI 사용 설정(§4.3), 승인 권한 부여, 보관 · 내보내기 · 해지 | — |
| 승인자 | 확인 · 수정 · **승인** · 승인 취소, 담당자에게 맡기기 | 채널 연결, 사용자 관리, AI 설정 |
| 작성자 | 확인 · 수정 · 초안 저장 · "확인 필요"로 넘기기 | 승인, 맡기기, 채널 · 설정 |

**정해진 것.**
- 지금 있는 계정은 전부 소유자로 남는다. 새 사용자는 소유자가 초대할 때 역할을 고른다.
- **채널 WRITE와 담당자 맡기기는 승인자 이상**이 한다. 승인 기록에 누가 승인했는지 남는다(§3).
- 역할은 서버에서 검사한다. 화면에서 버튼을 숨기는 것은 검사가 아니다.

**미룬 것.** 스토어별 · 채널별로 권한을 나누는 일은 첫 외부 판매자의 요구를 보고 정한다.

상태: 설계.

## 3. 승인 책임

### 3.1 누가 무엇을 책임지나

| 사건 | 책임 | 기록되는 곳 |
|---|---|---|
| 답변 문장의 내용 | 그 문장을 승인한 판매자(승인자) | backend 승인 원장 |
| 초안의 근거 · 금지 표현 · 약속 검사 | 서비스(재검사는 승인 직전과 등록 직전) | backend 초안 · 검사 기록 |
| 채널 API 등록 | 서비스가 **승인된 그 버전만** 보낸다. 결과는 공식 응답 · 재조회로 확인한다 | backend 실행 기록 |
| NAVER 리뷰 등록(사람 대행) | 담당자가 승인된 문장을 그대로 붙여 넣는다. 결과는 사람의 보고다 | vendor-server 작업 상태 → backend 사본(`OPERATOR_REPORTED_SUBMITTED` + `UNVERIFIED`) |
| 판매자 직접 등록(복사 길) | 판매자 | backend(판매자 보고) |
| 승인 이후 근거가 바뀜 | 서비스가 멈추고 다시 묻는다(재확인 필요). 판매자의 승인 문장을 대신 고치지 않는다 | backend |

### 3.2 규칙

1. **승인은 정확한 버전에 묶인다.** 하나의 승인은 다음 묶음에 걸린다.
   - 대상(조직 · 채널 · 건)
   - 원문 지문
   - 초안 버전 · 지문
   - 근거 지문(지식 · 정책 · 응대 기준)
   - 승인자 · 시각 · 명령 ID

   그사이 문장이 바뀌었으면 승인하지 않고 바뀐 문장을 보여 준다. 이 규칙은 지금의 D9 `baseVersion`과 같다.
2. **승인할 수 있는 것은 사람뿐이다.** AI · 예약 작업 · 담당자 · 운영자는 승인하지 않는다. 표준 승인(조건부 자동 승인)은 이 결정의 범위가 아니다. 그런 기능이 생기면 조건 자체를 판매자가 승인한 기록이 승인 원장에 남아야 한다.
3. **승인 원장의 정본은 업무 서버(backend) 하나다.**
   - 교환 서버(vendor-server)는 승인된 패키지를 받아 담당자 작업으로 바꾸고, **실행 상태**(배정 · 착수 · 보고 · 취소)의 정본이 된다.
   - 승인은 업무 서버 → 교환 서버로만, 실행 상태는 교환 서버 → 업무 서버로만 흐른다.

   지금 구조는 판매자가 휴대폰에서 교환 서버에 직접 승인한다. 그래서 교환 서버가 승인 상태의 정본이고 PC가 사본이다. §5의 단일 계정으로 옮기면서 이 방향을 바꾼다. 그 전환은 위험한 통합이어서 §19.4 T6과 같은 방식으로 단계를 나눈다: 먼저 양쪽 기록이 같은지 비교만 하는 단계를 두고, 그다음에 정본을 옮긴다.
4. **취소는 원자적이라고 약속하지 않는다.** 착수 전이면 끝내고, 착수 후면 담당자에게 멈춤을 요청한다. 결과가 불명확하면 다시 보내지 않고 확인을 기다린다(§17.6, 계약 §4 그대로).
5. **증거 등급을 섞지 않는다.** 화면 · 기록 · 보고서에서 셋은 같은 "완료"가 아니다.
   - 공식 API 확인
   - 채널 export 확인(답글여부)
   - 사람 보고
   - 판매자 보고

**승인한 사람 (구현됨, 외부 검토 2026-10-31).** 업무 서버 화면에서 누른 「답글 등록 요청」은 업무 서버의 대행 작업 사본에 다음을 남긴다.

| 칸 | 내용 |
|---|---|
| `approved_by_user_id` | 로그인한 사용자 |
| `org_id` | 조직 |
| `approved_draft_version` · `approved_fingerprint` | 승인한 문장의 버전과 지문 |
| `approved_locally_at` | 시각 |

V162로 추가했다. 공급자 서버에는 그 사용자를 가리키는 불투명 참조 `workspace-user:<사용자 ID>`만 간다(공급자 V15 `approved_by_ref`). 이름 · 이메일은 보내지 않는다. 매핑된 판매자 계정(`approved_by`)은 그대로 남는다. 휴대폰 페이지 · 공급자 서버 쪽에서 일어난 승인은 사용자 칸이 비어 있다.

상태: 일부 구현. 승인 묶음(규칙 1) · 증거 등급(규칙 5) · 승인자 기록은 코드에 있다. 원장 방향(규칙 3)은 §5와 같이 바꾼다.

## 4. AI 전송 보호

**사실 [REPO].**
- 모델로 가는 요청은 전부 backend의 두 전송기(`JdkAgentLlmTransport`, `JdkLlmHttpClient`)를 지난다.
- 기능마다 입력 하한(payload floor)이 있다.
- 전화 · 이메일 · 긴 숫자를 지우고 주소 · 불명 이미지 · 못 읽는 본문을 보류하는 `LlmSendGate`는 **판매자 PC 모드에서만** 켜진다(`OutboundGate`가 켜졌을 때). 지금 서버 배포에서는 꺼져 있다.

### 4.1 규칙

1. **서버에서도 같은 검사를 켠다.** `LlmSendGate`를 판매자 PC 여부와 떼어, 서버 배포에서 기본으로 켠다. 끄는 설정은 시험용 프로필에만 둔다. 입력 하한이 첫째 경계이고 이 검사가 둘째 경계다. 어느 쪽도 다른 쪽을 대신하지 않는다.
2. **조직 단위로 보낸다.** 한 요청에는 한 조직의 자료만 들어간다. 검색으로 가져온 근거도 같은 조직 것만 쓴다(§2.1-4).
3. **보류는 실패가 아니라 상태다.** 검사가 보류한 건은 "AI에 보내지 않음 — 사유"로 화면에 보인다. 원문으로 우회하지 않는다. 기본 문구나 판매자의 직접 작성으로 이어 간다. 'AI 처리 완료'로 위장하지 않는다.
4. **본문은 로그에 남지 않는다.** 남는 것은 조직 · 기능 · 모델 · 토큰 수 · 결과 코드 · 보류 사유 라벨뿐이다. 오류 추적 도구에도 본문을 싣지 않는다(§19.2 관측).
5. **목적지는 고정 목록이다.** 서버의 외부 출구(egress 검사)에서 허용하는 모델 제공사 주소는 계약한 곳뿐이다. 모델 출력이나 가져온 문서가 목적지를 정하지 못한다.
6. **사진 · 첨부는 전송용 사본만 보낸다.** 2026-10-17 방향(§18.7 리뷰 사진)을 서버에도 그대로 적용한다.

## 5. 하나의 계정, 하나의 업무 흐름 — 두 서버는 그대로

**목표 (2026-10-31 오너 지시).**
- 웹 판매자는 **Reviewnary 계정 하나**로 업무 화면과 휴대폰 승인을 쓴다.
- 공급자 서버(교환 서버) 계정으로 따로 로그인하지 않는다.
- PC 연결을 승인하지 않는다.
- 물리적인 서버 · DB 통합은 필수가 아니다. **서버 간 인증과 판매자 · 스토어 권한 매핑**으로 잇는다.

**구조 (구현됨).**

| 무엇 | 어떻게 |
|---|---|
| 서버 간 인증 | 업무 서버는 서비스 토큰(`rvw_…`) 하나로 교환 서버를 부른다. 교환 서버는 그 SHA-256만 설정으로 갖는다(`VENDOR_WORKSPACE_TOKEN_SHA256`). 토큰은 업무 서버 환경 변수(`SELLEROPS_VENDOR_SERVICE_TOKEN`)에만 있다 |
| 어느 판매자의 일인가 | 요청마다 조직 ID를 헤더(`X-Reviewnary-Org`)로 밝힌다. 토큰만 있고 조직이 없으면 "연결된 조직 목록"만 물을 수 있다 |
| 판매자 · 스토어 권한 매핑 | 운영자가 `link-workspace <판매자 이메일> <조직 ID> [create]`로 업무 서버 조직 하나를 교환 서버 판매자 계정 하나에 잇는다. **조직 하나 ↔ 계정 하나, 양쪽 모두 유일**하다. 계정의 스토어는 지금처럼 그 계정에 속하고, 담당자가 일하려면 지금처럼 `check-owner` · `check-assignment`가 필요하다 |
| 매핑의 저장 | `installs`의 한 종류(`WORKSPACE`, V13). 그래서 업무 서버의 호출은 그 계정의 PC가 하던 일과 정확히 같은 규칙을 따른다: 계정의 스토어만, 자기 저장 확인, 답글 작업. PC만의 일(공인 IP, 자기 연결 해제)과 판매자 세션만의 일(PC 승인, 설치 목록)은 못 한다 |
| 판매자 로그인 | 매핑용으로 만든 교환 서버 계정은 비밀번호가 없어 교환 서버에 로그인할 수 없다. 판매자 신원은 업무 서버 계정 하나다 |
| 휴대폰 승인 | 업무 서버 웹 화면(같은 계정)의 리뷰 답글 화면에서 「답글 등록 요청」. 화면 버전 그대로 승인되어 교환 서버의 담당자 작업이 된다 |
| 업무 서버 쪽 | `sellerops.vendor-link.mode=WORKSPACE`. 조직이 "연결됨"인 것은 교환 서버가 목록에 넣었을 때뿐이다(30초 재사용). 연결 시작 · 해제 · 공인 IP는 거절된다. 연결 화면은 「이 PC 연결」 · PC 문구 · 「이 Mac」 도우미 구역 · 도우미 안내 링크를 보이지 않는다 |
| 답할 계정 | NAVER 리뷰를 담당자에게서만 받는 조직은 NAVER 계정이 없다. 그러면 답글 화면이 열리지 않는다(실행에서 발견). 그래서 첫 「리뷰 받기 시작」이 연결된 파일 업로드 NAVER 계정 하나를 만든다(자격 · 예약 없음). 이미 NAVER 계정이 있으면 그대로 둔다 |

**한 스토어, 여러 경로 (구현됨, 외부 검토 2026-10-31).**
- 한 스토어(조직 × 채널)에는 반입 경로가 여럿 붙을 수 있다: 공식 API 연결, 판매자 파일 업로드, 담당자 반입.
- 답글의 기준이 되는 "답할 계정"은 그 스토어의 **자기 연결** 하나다. 담당자 반입용 계정(`review_route = DELEGATE_UPLOAD`, V163)은 그 스토어에 덧붙은 경로다. 자기 연결이 생기면 물러서고, 그것뿐일 때만 답할 계정이 된다(`SellerAccount.answering`).
- 리뷰가 어느 경로로 들어왔는지는 리뷰의 출처(`vendor_review_ref` 등)가 말한다. 등록 길(담당자 등록 / API / 판매자 직접)은 리뷰의 출처와 채널 능력이 정한다.
- 자기 연결이 둘이면 지금처럼 고르지 않는다.
- 두 계정 행을 하나로 합치는 데이터 통합은 공식 연동(T4) 때 따로 한다.

**여러 스토어는 아직 지원하지 않는다 (외부 검토 2026-10-31).** 위 규칙은 "한 스토어의 여러 경로"다. "한 조직, 같은 채널의 여러 스토어"와 다르다.
- 리뷰 행은 조직과 채널만 안다. 어느 스토어의 리뷰인지는 적혀 있지 않다(`Review`에 스토어 · 계정 열이 없다). 답할 계정도 조직 × 채널로 고른다.
- 그래서 같은 채널에 스토어가 둘이면 다음과 같다.
  - 자기 연결이 둘이면 답할 계정을 고르지 않는다. 답글 화면이 열리지 않는다.
  - 스토어 A의 자기 연결과 스토어 B의 담당자 반입이 같이 있으면, B의 리뷰에도 A의 연결이 답할 계정으로 보인다. **틀린 짝이다.**
- 지원하는 모양은 조직마다 채널당 스토어 하나다. 운영자는 `link-workspace` · `add-store` 때 이 모양을 지킨다.
- 여러 스토어를 지원하려면 리뷰에 스토어를 적고, 답할 계정을 그 스토어로 골라야 한다. 공식 연동(T4) 전에 따로 설계한다.

**조직 ↔ 계정 1:1을 DB가 지킨다 (구현됨).** 조직 쪽은 `installs.workspace_org_id`, 계정 쪽은 `installs.workspace_account_id`(V14)에 유일 색인을 둔다. 조회 뒤 생성만으로는 동시에 연결할 때 사전 검사를 둘 다 통과할 수 있다. 실제로 계정 쪽 색인을 빼면 동시 연결 시험이 실패한다.

**서비스 종류를 모르는 동안은 로컬 도우미를 찾지 않는다 (구현됨).**
- 화면은 서비스 종류를 `install` · `web` · `unknown` · `error`로 안다(`lib/serviceMode.ts`).
- 이 PC의 도우미(`127.0.0.1:47615`)를 찾는 모든 길은 `install`로 확인됐을 때만 연다. 그 길은 `useBridge` · 화면 투영 · 대화 도우미 확인 · 연결 화면 도우미 구역 · 도우미 안내 링크다.
- 모르는 동안은 「불러오는 중…」, 읽기 실패는 「다시 확인」만 보인다.
- "공급자 서버로 보낸 요청 0건"과 "이 PC의 도우미를 찾지 않음"은 서로 다른 검증이다(FINDINGS B51). 둘 다 서버 간 흐름에서 0건으로 확인했다.

**지켜야 할 규칙.**
1. **판매자가 직접 쓰는 화면은 업무 서버의 웹 화면뿐이다.** 교환 서버의 판매자 화면(`/replies` · `/link` · 판매자 가입)은 PC 설치형 전용으로 보존한다.

## 6. 공식 연동 인증 — 별도 개발 단계

최종 목표는 **법인 · 공식 연결 기반 웹 운영**이다. 개인사업자 단계의 제약은 임시 상태다. 그래서 화면과 흐름은 최종 형태로 만들고, 아직 승인받지 못한 채널은 그 형태 안에서 "공식 연동 준비 중" 상태로 둔다. 임시 경로를 위한 별도 화면이나 흐름은 만들지 않는다.

이 단계에서 할 일은 채널마다 둘이다.
- 상용 연결 방식에 맞는 인증 흐름을 개발한다.
- 플랫폼 심사에 낼 자료를 만든다.

| 채널 | 개발할 것 | 준비할 자료 | 켜지는 조건 |
|---|---|---|---|
| NAVER | 솔루션(또는 대행) 방식의 판매자 연결 · 토큰 흐름, 판매자가 솔루션을 고르고 끊는 흐름 | 법인 · 서비스 설명 · 자료 흐름 · 보안 설명(§17.8 자료 재사용) | 입점(또는 대행) 승인 |
| Coupang | 연동업체로서의 키 연결 흐름(판매자가 WING에서 업체를 지정), 업체 IP 고정 | 업체 · IP · 사용 API 제출, 연동협약 | 등록 검토 · 협약 |
| Cafe24 | 공급자 앱 하나의 설치 · 동의 · 재동의 흐름(기존 중앙 OAuth 재사용), 필요한 scope 정리 | 앱 심사 자료(개인정보 처리방침 주소 등) | 상용 심사 통과 |

**규칙.**
- 승인 전 채널은 연결 · 호출 · 예약이 서버 설정에서 꺼져 있다(§19.4 T1).
- 화면은 최종 연결 흐름을 그리되, 그 채널을 "준비 중"으로 표시한다. 연결 버튼이 실제로 동작하는 것은 승인 뒤다.
- 테스트 설치 · 오너 본인 스토어 연결은 승인을 대신하지 않는다. 그 결과를 "운영 지원"으로 표기하지 않는다(§4.1 capability 규율).

**채널 활성화 게이트 (구현됨, §19.4 T1).**
- `ChannelActivation`이 채널마다 `OFF` · `SELF`(운영자 본인 조직만, `self-org-ids`) · `ALL` 중 하나를 둔다.
- 세 곳에서 막는다.
  - 자격 증명 금고(`CredentialVault`)의 저장 · 회전 · 열기. 공식 API로 가는 모든 호출이 이 금고를 거치므로 연결 · 수집 · 등록이 모두 여기서 멈춘다.
  - 공식 API 계정 만들기(`registerApiChannel`).
  - Cafe24 동의 화면으로 보내기 전(`Cafe24OnboardingService.start`).
- 파일 업로드와 담당자 반입은 공식 연결이 아니라서 막지 않는다.
- `sellerops.channel-activation.enforced`가 false(기본)면 지금과 같다. 서버 배포는 true로 두고, 그러면 이름이 없는 채널은 `OFF`다.
- **업무 서버는 이 설정이 빠지면 시작하지 않는다 (구현됨, 외부 검토 2026-10-31).**
  - 업무 서버 = `sellerops.vendor-link.mode=WORKSPACE`인 백엔드다(`WorkspaceServerConfigValidator`).
  - 시작을 거부하는 경우: 채널 게이트가 꺼짐, 모델 전송 전 검사가 꺼짐, 서비스 토큰 없음, 리뷰 받기 꺼짐.
  - 메시지는 설정 이름만 말하고 값은 말하지 않는다.
  - 근거: `WorkspaceServerConfigValidatorTest` 6건. 실제 설정 키로 문맥을 띄워 게이트가 꺼지면 시작에 실패함을 본다. 게이트 검사를 빼면 4건이 실패한다.
  - 한계: 업무 서버 모드 자체를 빼먹은 배포는 잡지 못한다. 그 배포에서는 웹 판매자가 리뷰를 받지 못하므로 첫 점검에서 드러난다. 배포 점검표(T6)에 이 모드를 첫 줄로 둔다.
- 근거:
  - `ChannelActivationTest` 3건. 금고 열기의 검사를 빼면 실패한다.
  - 서버 간 전체 흐름이 모든 채널 `OFF`로 강제한 채 돌았다. 담당자 리뷰 흐름은 그대로 돌았고, NAVER 공식 연결 만들기는 409로 거절됐다.
- 남은 것: 연결 화면의 "공식 연동 준비 중" 표시(시안 먼저), 채널 안에서 업무별(읽기/쓰기) 수준 나누기.

상태: 게이트 구현, 채널별 인증 흐름과 심사 자료는 설계. 단계 위치는 §19.4.

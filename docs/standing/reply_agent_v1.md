# Reply Agent v1 — 답글 에이전트 (LangGraph · 1회용 실행 토큰)

> **상태:** 설계 계약. 사장님 결정 2026-10-28 — 「제안한 구조대 진행하자」, 위치는 「agent-runtime(LangGraph) + 1회용 토큰」.
> 이 문서는 `docs/standing/responsibility_runtime_v1.md` **PD-5를 다시 연다**(§6). 기준은 `contracts/reply-standard/v1`.

## 0. 무엇이 바뀌나

리뷰·문의 답글을 모델 한 번으로 쓰던 것을 **단계형 에이전트**로 바꾼다. 판단 → 사실 모으기 → 초안 → 검토 → (한 번)
고치기 → 저장, 또는 사람에게 넘김. 그래프는 agent-runtime의 LangGraph로 두고, 판매자가 없을 때(연동 직후 · 자동 확인)는
백엔드가 그 한 번의 실행에만 쓰는 토큰을 만들어 runtime을 부른다. **모델 출구는 여전히 백엔드 하나다** — 각 모델 단계는
자기 지시문과 payload 하한을 가진 백엔드 엔드포인트이고, runtime은 순서만 정한다.

## 1. 그래프 (`agent-runtime/src/reply/`)

| 노드 | 하는 일 | 부르는 백엔드 |
|---|---|---|
| judge | 범주(S·L·R·Q·D·M·V·X·P) 판정 | `POST /api/agent/reply/classify` (모델) |
| handoff? | S·L·X면 초안을 쓰지 않고 사람에게 넘긴다 — 실행은 `HANDOFF`로 끝나고 이유가 남는다 | — |
| draft | 사실(상품 지식 · 운영 정책 · 과거 답변 · 판매자 말투 · 금지 표현)을 백엔드가 모아 그 범주의 뼈대 · 금지 · 규칙으로 초안 | `POST /api/agent/reply/run/draft` (모델) |
| critique | 규칙 번호별 채점 + 코드 검사(근거 없는 약속 N9 · 금지 표현) | `POST /api/agent/reply/run/critique` (모델 + 결정론) |
| revise | 걸린 규칙과 지적을 넣어 **한 번만** 다시 쓴다 | `POST /api/agent/reply/run/draft {revise:true}` |
| save / handoff | 통과하면 초안 저장(저장 직전 게이트를 다시 확인), 그래도 걸리면 사람에게 | `POST /api/agent/reply/run/save` · `/finish` |

- **구현(2026-10-28):** 판단 경로는 `/api/agent/reply/run/classify`. 단계 사이의 상태(범주 · 작업 중 초안 · 걸린 규칙)는
  `reply_agent_run`에 있고, runtime 상태에는 닫힌 단어와 숫자만 있다. runtime 그래프는 `agent-runtime/src/reply/`,
  입구는 `POST /api/reply-runs {runId, token}`. v1은 리뷰만 — 문의 실행은 백엔드가 거절한다.

- runtime이 부를 수 있는 것은 `ReplySpringClient`의 다섯 경로(판단 · 초안 · 검토 · 저장 · 종료)뿐이다 — Operator 도구 등록부(100%
  READ)를 쓰지 않고 `src/conversation/` 밖에 둔다. 쓰기는 초안 저장 하나뿐이고, 경로 목록 · 토큰 비저장 · 체크포인터 없음을
  `agent-runtime/test/reply/`가 고정한다.
- 승인은 언제나 판매자다. 그래프는 승인 · 등록 · 전송을 하지 않는다.
- `ReviewDraftComposer`의 「repair pass 없음 · 두 번째 호출 없음」 원칙은 이 그래프에서 「검토를 거친 고치기 한 번」으로 바뀐다
  — 같은 근거로 같은 질문을 다시 하는 것이 아니라, 규칙 번호로 지목된 결함을 고치는 호출이다.

## 2. 실행 토큰 (`backend/.../auth/runtoken/`)

- 백엔드가 판매자 없는 실행 하나마다 만든다: 접두어가 따로 있고(`rvr_`), **그 org 하나 · 그 실행 하나**, 몇 분 뒤 만료, 한 번
  쓰고 나면 끝(`jti` 해시 저장). 장치 토큰(`HelperDeviceAuthFilter`)처럼 **허용된 경로만** 통과하고 JWT 필터로 넘어가지 않는다.
- 허용 경로: §1의 모델 단계 · 그 실행의 대상 리뷰/문의 READ · 초안 저장. 승인 · 등록 · 전송 · 설정 · 다른 org는 없다.
- 사용자가 없으므로 작성자는 미리 쓴 초안의 작성자(`ReviewReplyService.PREPARED_AHEAD_ACTOR` = `SYSTEM:RESPONSIBILITY`)로 남는다. 판매자가 그 초안을 고치거나 승인하면 그것이 판매자의 「대응
  필요」다(`ReviewReplyService` — 2026-10-28에 만든 규칙 그대로).
- runtime은 토큰을 **저장하지 않는다**: 체크포인트 · 실행 저장소 · 로그 어디에도 남기지 않고 그 실행의 요청에만 실어 보낸다.
  사람에게 넘긴 실행을 이어 가는 것은 나중에 판매자의 로그인(bearer)으로 한다 — 실행 토큰은 그때 이미 만료돼 있다.
- **판매자가 누른 실행도 백엔드가 시작한다**(`POST /api/agent/reply/start`, 판매자 로그인). 그 실행 역시 실행 토큰으로 돌고, runtime은
  판매자 로그인을 받지 않는다 — 경로가 하나라 「runtime은 토큰을 저장하지 않는다」를 한 곳에서 지킨다. 저장되는 초안의 작성자는 누른
  판매자다.
- 스위치는 `sellerops.reply-agent.*`(기본 꺼짐, 공급자 · 모델 · 키 · org 목록은 초안 기능 값으로 기본값), runtime 주소는
  `sellerops.agent-runtime.base-url`. 둘 중 하나라도 없으면 미리 쓰기는 이전의 한 번 호출 방식으로 쓴다.

## 3. 사용량 기록 (데모로 가늠, 사장님 2026-10-28: 「모니터링 잘 할 수 있도록만」)

- `agent_llm_usage`에 실행 id(필수) · 단계(`CLASSIFY · DRAFT · CRITIQUE · REVISE`) · 계기(`SELLER · INGEST · SCHEDULED`) ·
  걸린 시간 · 입력/출력 토큰 수를 남긴다. 실행 토큰의 호출은 actor `RUN`.
- 하루 단위로 단계별 · 계기별 · 실행당 평균 호출 수와 토큰을 보여 주는 화면(설정 → AI 사용량)과 그 읽기 엔드포인트.
- 지금의 하루 한도(미리 쓰기는 절반, ★4~5 감사는 4분의 1)는 그대로 두고, 데모 수치를 보고 다시 정한다.

## 4. 기준표 주입

모델 단계 지시문은 `contracts/reply-standard/v1/standard.json`(백엔드 사본 `resources/reply-standard/v1/`)을 읽어 그 범주의
뼈대 · 금지 · 규칙을 넣는다. 검토 결과는 규칙 번호로 돌아오고, 화면은 「지킨 기준 / 걸린 기준」을 그 번호로 보여 준다. 평가
채점도 같은 번호다.

## 3-1. 검토(2026-10-28) 뒤에 더한 것 — 모델 혼자 지키지 않는다

독립 검토가 짚은 「사고가 나는 규칙을 모델 혼자 지킨다」 · 「넘김이 아무에게도 가지 않는다」를 고쳤다.

- **안전 · 분쟁은 모델보다 먼저(§3-4에서 바뀜 — 이제 모델이 항상 읽고, 낱말은 사람 확인을 요구하는 보조 신호):** 리뷰에 위해나 법적 단어가 있으면(`ReviewSafetySignal`) 판단 단계가 모델을 부르지 않고 S · L로
  정하고 사람에게 넘긴다.
- **넘긴 리뷰는 다시 돌리지 않고, 보인다:** 한 번 `HANDOFF`로 끝난 리뷰는 미리 쓰기가 다시 실행하지 않는다(판매자가 누르면 돈다).
  홈의 「AI가 사람에게 넘긴 리뷰」가 답할 때까지 보여 준다(`GET /api/agent/reply/handoffs`, 목록이라 가린 미리보기만). 안전 관련은
  법정 보고 의무 검토가 필요할 수 있다고 말한다. 즉시 알림(메일)은 아직 없다.
- **코드가 보는 규칙:** 초안에 개인정보 정제기를 다시 돌려 바뀌면 N2, 리뷰 대가 · 수정 요청 N3, 삭제 · 신고 · 비난 N7, 「개봉하면
  반품 불가」 · 7일 미만 기한 N8(판매자 정책 문구가 있어도), 근거 없는 약속 N9, 채널 길이(NAVER 200자) F1, 금지 표현 — 걸리면
  고칠 점 한 문장과 함께 고치기에 넘긴다(`ReviewDraftComposer#agentFindings`).
- **검토는 통과 쪽으로 기울지 않는다:** N 규칙은 애매하면 어긴 것으로 고른다(지시문 v2). 검토가 돌지 못하면 고치기 없이 사람에게.
- **판정 기록:** 첫 검토가 건 규칙과 코드 검사가 건 규칙이 실행이 끝난 뒤에도 남는다(V155) — 평가가 규칙별로 다시 읽는다.
- **쿠팡:** 판매자 누름 경로도 답글을 달 수 없는 채널을 거절한다.
- **시간:** runtime 단계당 60초 · 백엔드 330초 · 토큰 10분.

## 3-2. 2차 검토(2026-10-28) 뒤에 고친 것 — 검사가 통과로 새지 않는다

- **문의 숫자는 값만이 아니라 단위 · 대상 · 조건까지 맞춘다(`InquiryClaimGuard`, 보조 검사):** 근거 · 주문 문장의 같은 값이
  **양쪽 다 적은 같은 단위**로 있고, 답글에서 그 숫자가 무엇에 대한 것인지(구절의 주제어 · 바로 앞뒤 낱말)가 근거 구절에 있어야
  한다. 숫자 옆 낱말을 근거의 다른 구절이 다른 값에 쓰면(「평일 배송 2일, 제주 배송 7일」의 평일) 막는다. 단위나 대상을 읽지
  못하면 일치로 보지 않는다(「폭: 10」은 「10cm」를 허용하지 않는다). 고객 질문의 숫자는 「문의 주신 20가닥은」처럼 주제로 되짚을
  때만 쓰고, 「문의하신 20가닥까지 가능합니다」는 막는다. 막히면 판매자에게 어느 숫자인지 말한다. 단위 환산 · 동의어는 하지
  않는다 — 「너비 10mm」는 「폭 10mm」로 허용되지 않고 판매자 확인으로 간다. 실측 뒤에 정한다.
- **읽지 못한 검토는 통과가 아니다(`ReplyAgentService#critique`):** 모르는 규칙 번호 · 번호 없는 항목 · 객체가 아닌 항목이 하나라도
  있으면 검토 실패로 본다. 전에는 그 항목만 버려 「문제가 있습니다」가 「위반 없음」이 될 수 있었다.
- **검토한 그 초안, 그 근거만 저장(V156):** 초안을 쓸 때 본 리뷰 · 근거 · 회사 문구의 지문(`inputs_hash`)을 남기고, 검토를 통과하면
  초안과 그 근거의 지문(`passed_hash`)을 남긴다. 검토 때 근거가 바뀌었으면 `EVIDENCE_CHANGED`로 실패시켜 고치기로 보내고, 저장
  때 지문이 다르면 저장하지 않는다(`NOT_REVIEWED` · `EVIDENCE_CHANGED`) — 저장된 인용 근거가 쓴 쪽과 검토한 쪽이 본 근거와 같다.
  그래프 순서와 별개로 백엔드가 지킨다. 저장을 거절한 실행은 `SKIPPED`로 끝나고 다음 동기화 때 다시 돈다.
- **모델 응답은 문서 하나로만 읽는다:** 뒤에 붙은 두 번째 JSON, 같은 필드를 두 번 쓴 응답은 판단 · 초안 · 검토 모두 실패다.
- **넘길 범주는 백엔드가 막는다:** S · L · X는 단계를 어떤 순서로 불러도 초안 · 검토가 거절되고 저장은 `HANDOFF_CATEGORY`다. 다시
  판단하면 지난 통과 기록이 지워지고, 통과 지문에 범주와 기준표 버전이 묶인다. 판단한 뒤 리뷰 본문이 바뀌면 초안을 쓰지 않는다.
- **넘긴 리뷰는 사람이 처리할 때까지 남는다:** 전에는 초안이 하나라도 있으면 목록에서 빠졌다. 이제 넘긴 뒤에 채널 답변 · 승인 ·
  사람이 쓰거나 고친 초안 · 담당자 맡김 · 업무 닫기 · 「답글 불필요」 판단 중 하나가 있어야 빠진다. 넘기기 전 초안이 있으면
  홈에 「그대로 쓰기 전에 다시 확인」이라고 같이 보인다.
- **F2를 좁혔다:** 여닫는 말은 판매자가 정한 기본 문구를 따라도 된다(사장님: 판매자가 답변 템플릿과 말투를 지정). 대신 본문이 이
  리뷰의 상황을 읽었는지를 본다. 지시문 v3.

**당시 남아 있던 것 (2026-10-28 2차 검토 시점의 기록).** 아래는 현재 미구현 목록이 아니다. 판단 분리 · 판단 불가 ·
여러 문제 처리 · 화면 버튼 연결의 후속 구현은 §3-3~§3-6을 따른다. 화면 전체를 공통 판단으로 바꾸는 일과 실제 품질 평가는
여전히 남아 있으며, 재개할 작업은 §8에서 고른다.

- **판단을 셋으로 나누기:** 고객이 말한 것(접착 실패 · 교환 질문 · 이미 해 본 방법) / 판매자가 할 일(답변 · 주문 확인 · 안전
  검토 · 불필요) / 처리 상태(준비 중 · 근거 부족 · 승인 대기 · 등록 대기 · 완료). 지금은 목록 분류 · 미리 쓸지 판단 · 에이전트
  범주가 서로 다른 경로이고, 범주 판단은 별점 없이 본문만 본다.
- **한 리뷰의 여러 문제:** 범주는 답글 순서를 고를 뿐 초안은 리뷰 전문을 보지만, 「부품 누락 + 교환 질문」에서 하나를 빠뜨렸는지는
  아직 아무도 세지 않는다. 평가표와 채점자 질문(5-1)에 「빠뜨림」을 넣어 먼저 잰다.
- **판단 불가 ≠ 문제없음:** 범주를 억지로 고르지 않고 판매자 확인으로 보내는 길이 아직 없다.
- **안전 단어는 보조 장치다:** 걸리지 않았다고 안전한 것이 아니다. 명확한 부상 표현 일부가 목록에 없다 — 모델 판단(S)이 뒤를 받친다.
- **화면 버튼:** 리뷰 화면의 「초안 생성 · 다시 쓰기」는 아직 이전 방식이다. 그 결과로 에이전트를 평가하지 않는다.

## 3-3. 미뤄 둔 것 처리 (사장님 2026-10-28: 「아직 안 한 것 처리도 가고」)

- **문의 숫자의 뜻은 모델이 읽는다(사장님: 주변 낱말 비교는 맞는 초안을 막고 틀린 초안을 통과시킨다).** 코드는 확실한 반쪽만
  본다 — 근거 · 주문 문장 · 질문 어디에도 없는 값, 다른 단위로만 있는 값은 모델 없이 막는다(`InquiryClaimGuard`). 근거에 적힌
  값이면 그 숫자가 같은 대상 · 같은 조건인지를 **초안과 같은 문의 초안 경로**(같은 스위치 · 키 · 모델로 나가는 내용)의 숫자 확인
  호출이 숫자마다 SUPPORTED · SAID_BACK · NOT_SUPPORTED로 답한다(`AgentDraftService#checkFigures`, 지시문
  `inquiry-figure-check/v1`). 확인되지 않거나 답이 없으면 저장하지 않고 판매자에게 어느 숫자인지 말한다. 답은 숫자마다 정확히
  하나여야 하고(중복 · 누락 · 뒤에 붙은 문서 거절), 나가는 내용은 초안 호출과 같다(`AgentFigureCheckPayloadFloorTest`).
- **사용량(사장님: 숫자가 든 초안은 하루 사용량을 두 배로 쓴다):** 숫자 확인은 그 초안의 일부로 본다 — 한도에서 따로 빠지지
  않고, 사용량 기록에는 `FIGURE_CHECK` 줄로 시간 · 토큰이 남는다. 확인 호출만 더 작은 모델 · 짧은 출력 한도를 쓸 수 있다
  (`sellerops.agent.draft.check-model` · `check-max-output-tokens` · `check-reasoning-effort`, 비우면 초안과 같음). 숫자가
  없거나 코드가 이미 막은 초안은 확인을 부르지 않는다.
- **판단 단계가 버리지 않는다(G8):** 첫 범주와 함께 있는 범주(`also`)와 답할 점(`points`, 최대 5개)을 남긴다. 함께 있는
  범주 중 하나라도 S · L · X면 사람에게. 판단 불가(`UNSURE`)는 문제없음이 아니라 사람에게(`UNSURE`). 답할 점은 초안과 검토에 같이
  들어가고, 기준표에 G8(여러 문제 · 질문을 빠뜨리지 않는다)을 더했다.
- **답할 사실이 없는 질문(G2):** 질문 범주가 있고 등록된 현재 근거가 하나도 없으면 사람에게(`QUESTION_NO_FACTS`). 넘긴 판단은
  백엔드도 지켜, 단계를 직접 불러도 초안 · 저장이 거절된다.
- **안전 단어 보강:** (§3-4에서 낱말은 보조 신호로 바뀌었다.) 「베었 · 데었 · 찔렸 · 피났 · 진물 · 합선」 같은 분명한 사고 표현을 더했다. 앞 두 글자가 흔한 낱말(피부 · 손가
  · 목에)이나 과장(기절 · 쇼크)은 넣지 않았다 — 그 두 글자가 별점 3 리뷰의 「참고」를 막는 표시로도 쓰이기 때문이다.
- **리뷰 화면 버튼:** 에이전트가 켜진 판매자는 「초안 생성 · 다시 쓰기」가 에이전트를 돌린다. 저장한 버전을 보이거나, 넘긴
  이유 · 못 만든 이유를 말한다. 이전 방식으로 몰래 넘어가지 않는다. 에이전트가 꺼져 있으면 이전 방식이다.
- **순서:** 미리 쓰기는 같은 순위 · 같은 별점 안에서 오래 기다린 리뷰부터(15일 안).
- **예전 지시문의 교훈:** 판매자가 정하지 않은 「확인 후 연락드리겠습니다」는 약속(N9)으로 코드가 잡는다.
- **판단 셋 나누기:** 홈의 「AI가 사람에게 넘긴 리뷰」가 이유 · AI가 읽은 점 · 넘기기 전 초안 여부를 보인다. 목록 분류 · 미리 쓸지
  판단 · 에이전트 범주를 하나로 합치는 일은 「무엇이 필요한가」를 읽는 다섯 곳을 하나로 모으는 리팩터라 기준선 측정과 사장님
  승인 뒤에 따로 한다.

## 3-4. 공통 판단 구조 (두 번째 외부 의견 2026-10-28: 「구조는 지금 정하고, 교체는 검증하며」)

리뷰 하나에 대한 판단을 세 가지로 나누고, 누가 정하는지를 고정한다. 셋을 한 범주로 뭉치지 않는다.

| 구분 | 무엇 | 누가 정하나 | 어디에 |
|---|---|---|---|
| 고객이 말한 것 | 범주(첫 범주 + 함께 있는 범주) · 답할 점(빠짐없이, 12개 넘으면 사람에게) | AI(답글 에이전트 판단 단계) | `review_judgement`(리뷰마다 최신 한 줄, V157) |
| 판매자가 할 일 | 제안: 공개 답글 · 주문 확인 · 더 듣기 · 직접 검토 · 대응 불필요. 판매자 응대 기준(별점대마다 미리 쓰기/필요할 때만/누를 때)은 프로그램이 적용 | AI 제안 + 판매자 기준 | `review_judgement.action` + `review_response_rule` |
| 실제 처리 상태 | 근거 찾는 중 · 승인 대기 · 담당자 등록 대기 · 등록 확인 · 넘김 | 프로그램의 기록만 | 초안 · 승인 · 맡김 · 채널 답글 상태 |

- **판단 불가는 이유를 구분한다:** 표현이 모호함(`UNSURE_AMBIGUOUS`) · 상품 연결이 불확실함(`UNSURE_PRODUCT`) · 답할 근거가 부족함(`KNOWLEDGE_MISSING`, 초안 단계가 근거를 읽고 판단) · 근거끼리 충돌(`POLICY_CONFLICT`) · 모델 호출 실패(실행 `FAILED`, 판단 기록 `MODEL_FAILED`). 판매자에게 보이는 문장이 이유마다 다르다.
- **모든 리뷰를 AI가 읽는다:** 별점과 낱말에 상관없이 판단 단계가 돈다. 안전 낱말은 범주를 정하지 않고, 걸리면 사람 확인을 요구하는 보조 신호다(`SAFETY_SIGNAL` — 읽은 결과가 안전과 다르거나 모델이 답하지 못해도). 판단은 리뷰마다 한 번, 초안 · 검토 · 한 번 고치기는 응대가 필요한 리뷰에만 돈다.
- **분석할 대상과 초안을 쓸 대상을 나눈다(세 번째 외부 의견):** 리뷰가 들어오면(동기화 직후, 최근 15일, 한 번에 50건까지 —
  자동 확인이 나머지를 잇는다) 채널 · 별점 · 판매자 응대 기준과 상관없이 먼저 판단해 저장한다(`ReviewJudgeService#judgeAll`).
  답글을 달 수 없는 채널(쿠팡)도 판단한다. 그다음 미리 쓰기가 그 판단을 읽는다 — 판단이 아직 없는 리뷰만 기존 리뷰 분류 AI로
  대신한다. 답글 에이전트는 리뷰 문장과 판단 버전이 같으면 저장된 판단을 다시 쓰고 모델을 다시 부르지 않는다. 판단 규칙은
  이 서비스 한 곳에만 있다.
- **할 일 제안 + 판매자 기준 → 실행:** 판단은 할 일을 여러 개 낼 수 있다(주문 확인 + 공개 답글). 「대응 불필요」는 다른 것과
  함께 쓸 수 없다. 자동 실행에서 그 별점대가 「필요할 때만」이고 판단이 「판매자가 할 일 없음」이면 초안 없이 끝난다
  (`SKIPPED` · `NO_RESPONSE_NEEDED`). 판매자가 직접 누르면 늘 쓴다. 초안 단계가 찾은 근거 부족 · 충돌은 같은 판단 줄에도 남는다.
  「주문 확인」을 따로 보이는 업무로 만드는 것은 화면을 바꿀 때 한다.
- **비교는 차이를 찾는 도구이고 정확도가 아니다:** `GET /api/review-judgement/compare`는 이미 저장된 값만 읽는다 — 기존 분류 AI의
  판정이 없으면 「미평가」이고 모델을 부르지 않는다. 일치는 판단끼리 같다는 뜻일 뿐 둘 다 틀릴 수 있다. **정확도는 판매자가 정답을
  붙인 사례(평가의 사람 정답)로만 잰다.** 홈 분류의 기존 기준(RUBRIC §5)도 사람 정답으로 확인한 뒤에야 바꾼다.
- **옮기는 순서:** 지금 홈 · 목록은 기존 판단을 그대로 쓴다. 비교로 차이를 보고, 사람 정답으로 정확도를 잰 뒤, 읽는 곳을 하나씩
  바꾼다. 저장소 전체를 한 번에 고치지 않는다.
- **필수 항목:** 판단의 범주 · 함께 있는 범주 · 답할 점 · 할 일 · 판단 불가 이유, 초안의 본문 · 답 못 한 점 · 충돌, 사실 확인의
  숫자 판정 · 사실 목록은 모두 있어야 한다. 빠진 항목은 빈 목록이 아니라 실패다. 다만 항목이 있다고 AI가 모든 사실을 찾았다는
  보장은 아니다 — 그건 평가가 잰다.
- **문의도 같은 계약을 쓴다:** 근거의 권한(현재 · 후보 · 과거 답변), 사실 대조, 판단 불가의 이유, 실행 기록은 문의에도 같은 뜻이다. 지금 문의 경로는 그대로 두고, 빠져 있던 사실 대조를 붙였다(아래). 문의를 에이전트 실행으로 옮길지는 문의 사례로 따로 비교한 뒤 정한다.

**이번에 고친 것.**
- **사실 대조(문의):** 확인 호출이 숫자만이 아니라 초안의 사실 · 조건 · 약속을 근거와 대조한다(「식기세척기 사용 가능」처럼 숫자 없는 것도). 숫자 없는 초안도 대조한다. 판정은 뒷받침됨 · 되짚기만 · 안 됨 · 근거 충돌.
- **코드와 지시문의 충돌:** 정확히 정의된 환산(mm · cm · m, ml · L, g · kg)은 코드가 계산한다 — 근거 10mm · 초안 1cm는 모델까지 간다. 「문의 주신 20가닥은 한 번에 넣기 어렵습니다」는 되짚기가 아니라 판단이므로 근거가 필요하다고 지시문 예시를 고쳤다.
- **답할 점:** 다섯 개 제한을 없앴다(12개 넘으면 사람에게, 버리지 않는다). 검토는 목록만 믿지 않고 원문과 초안을 직접 비교한다(G8).
- **후보 근거와 마무리:** 「후보」 근거는 상품 · 옵션 · 조건이 맞을 때만 팁으로 쓰고 약속 · 상품 사실의 근거로 쓰지 않는다(검토는 N9로 잡는다). 불만 · 피해 리뷰는 판매자 기본 문구에 밝은 인사가 있어도 차분하게 맺는다(F6, 코드도 검사).
- **PC 알림:** 앱이 열려 있는 동안 2분마다 확인해 브라우저 시스템 알림을 띄운다. 안전 관련 리뷰는 하나씩, 나머지 리뷰 · 문의(새
  문의 · 답변 승인 대기)는 30분에 한 번 묶어서. 같은 일이 여러 목록에 있어도 한 번, 가장 중요한 이유로. **실제로 표시된 알림만
  「알림 보냄」으로 기록**해 실패한 알림은 다음에 다시 시도한다. 누르면 그 일로, 미리보기 숨기기(`/settings/notifications`).
  창이 닫혔거나 PC가 꺼지면 수집도 알림도 없다는 것을 설정 화면이 말한다. 창이 닫힌 뒤에도 오는 알림(Web Push)은 아직이다.
- **지표:** 사용량과 별도로 실행 결과 · 넘긴 이유, 그리고 리뷰마다 마지막으로 저장한 실행 하나를 기준으로(한 승인이 두 실행에
  잡히지 않게) AI 문장 그대로 승인 · 판매자가 고쳐서 승인 · AI가 다시 쓴 문장 승인 · 대기, 초안부터 승인까지 걸린 시간
  (`GET /api/agent/reply/outcomes`, 「AI 사용량」 화면 아래). 판매자 입력 · 수정에 든 시간 자체는 아직 재지 않는다.
- **작은 모델은 가설이다:** 확인용 모델 설정은 기본으로 비어 있다(초안과 같은 모델). 품질을 먼저 확인하고, 작은 모델로 바꿔도 유지되는지 비교한 뒤 바꾼다.

## 3-5. 사용량 상한 · 검토 대기 · 가짜 모델 점검 (사장님 2026-10-29)

- **두 숫자를 나눈다.** 실제 AI 호출 상한(`daily-llm-calls-per-org`)은 판매자와 자동 실행의 모든 호출을 센다 — 판단 · 초안 ·
  검토 · 고치기 · 재시도 · 사실 확인 · 기존 리뷰 분류 AI. 닿으면 자동이든 아니든 어떤 호출도 나가지 않는다. 판매자용 처리
  건수(`daily-items-per-org`)는 판매자가 맡긴 일 한 건(실행 하나 · 초안 요청 하나 · 대화 한 번)을 하나로 세고, 판매자의 새 일만
  막는다. 미리 쓰기의 「절반」은 실제 상한의 절반이다. 「AI 사용량」 화면이 두 숫자를 따로 보인다.
- **동시 요청에도 상한이 지켜진다(외부 검토 2026-10-29):** 호출을 기록하기 전에 조직 · 날짜의 예산 행(`agent_daily_budget`,
  V160)을 잠근다. 사용량 확인 → 상한 비교 → 기록이 같은 조직 · 같은 날에 한 번에 하나씩만 일어나, 남은 한 자리를 두 요청이 같이
  가져가지 못한다. 판매자용 처리 건수와 실행 한도도 같은 잠금 안에서 비교한다(`AgentQuotaConcurrencyTest` — 잠금이 없으면 같은
  끼어듦에서 둘 다 통과하는 것도 같이 보인다). Postgres에서 동시 요청 4건으로 확인했다.
- **검토 대기:** 상한 때문에 검토(답글 에이전트의 검토 · 문의 사실 확인)를 못 한 초안은 버리지도, 검토 없이 보이지도 않는다.
  답글은 실행에 `PENDING`으로 남고 홈 「AI가 사람에게 넘긴 리뷰」에 「검토 대기」로 보인다. 문의는 `draft_review_pending`(V159)에
  남는다. 같은 입력으로 다음 실행 · 다음 생성이 오면 새로 쓰지 않고 그 본문을 검토부터 잇는다. 「같은 입력」은 초안 호출에 들어간
  것 전부다 — 문의 · 근거 · 주문 문장 · 모델에 더해 규격 안내 · 회사 답변 스타일 · 회사 소개 · 답변 범위(답글은 리뷰 · 근거 · 회사
  문구 · 말투 · 금지 표현 · 범주). 하나라도 바뀌면 새로 쓴다.
- **판단의 최신성 · 대응 필요는 한 군데:** 저장된 판단은 리뷰 문장의 지문과 판단 버전이 지금과 같을 때만 쓴다 — 다시 쓰기도,
  미리 쓰기도 같은 규칙. 「대응 필요」는 판단 때 계산한 값을 저장해 그대로 읽고(`needs_response`), 다른 곳에서 다시 계산하지
  않는다. 초안 단계가 넘기면 그 줄도 「대응 필요」가 된다. 상한에 닿은 판단은 실패로 남기지 않고 멈춘다.
- **가짜 모델 점검:** `sellerops.dev.fake-llm=true`(개발 전용, prod 프로필이면 시작을 거부, 연결을 열지 않음. 리뷰 분류 AI는
  자기 연결을 따로 만들므로 가짜 모드와 함께 켜져 있으면 그쪽이 시작을 거부한다)로 규칙대로 답하는
  모델을 붙인다. `FakeModelFullFlowTest`가 한 Spring 맥락에서 수집 → 판단 저장 → 판매자 기준 → 미리 쓰기 → 승인 대기 · 사람에게
  넘김 · 대응 불필요 · 검토 대기 → 이어서 검토를 확인한다. 실제 runtime(Node)과 Postgres로는 `holds/eval/start-fake.sh`로
  평가용 복사본에서 돌려, 실행 토큰 · HTTP · 그래프 · 마이그레이션 V156–V159를 확인했다(2026-10-29, 20건 + 합성 2건, 끝나고
  합성 리뷰 · 가짜 초안 · 실행 기록을 지움).

## 3-6. 판매자 몫을 남긴다 · Claude로 말하기 (여섯 번째 외부 검토 2026-10-29, 사장님 「진행할 시 claude로 진행하자」)

- **자동 작업은 판매자 몫 앞에서 멈춘다.** 실제 AI 상한은 그대로 하나다. 그중 `daily-seller-reserve-calls`(기본 300 — 임시값,
  실제 모델 평가에서 일 하나에 드는 호출을 잰 뒤 정한다)는 판매자가 직접 누른 일만 쓴다. 판단 · 미리 쓰기 · 백그라운드 문의 초안
  (Proactive · 책임 조사) · 그 사실 확인은 `상한 − 판매자 몫`에서 멈추고(`QuotaDecision.Reason.AUTOMATIC_SHARE`), 판매자의 누름은
  상한까지 쓴다. 「AI 사용량」 화면이 자동 작업 몫을 따로 보인다.
- **누가 시작했는지 끝까지 들고 간다.** 백그라운드 문의 초안은 예전엔 판매자 사용량(`USER`)으로 적혔다. 이제 초안과 그 사실 확인이
  작성자(`SELLER:…`만 판매자, 나머지는 자동)대로 적힌다. 이전 방식 리뷰 초안도 같다.
- **끝낼 수 있을 때만 시작한다.** 새 일은 남은 호출까지 들어갈 때만 연다 — 답글 실행은 판단부터면 5번, 저장된 판단을 쓰면 4번,
  문의 초안은 초안과 사실 확인 2번. 이미 시작한 실행의 다음 단계는 그 한 번만 확인한다. 그래서 검토 대기(`PENDING`)는 이제 주로
  동시에 들어온 다른 요청이 남은 몫을 가져간 경우다(`SellerReserveTest`, `FakeModelFullFlowTest`).
- **Claude 응답 읽기.** 지금 Claude 모델은 답하기 전에 생각하므로 답은 첫 블록이 아니다 — 응답의 `text` 블록을 읽는다(예전엔
  `content[0].text`만 읽어 모든 호출이 「답 없음」이 될 자리였다). 설정의 effort는 `output_config.effort`로 보낸다(예전엔 OpenAI
  에만 갔다). 안전 거절(`stop_reason=refusal`)은 「답 없음」이 아니라 `refusal`로 적는다(`AnthropicWireFormatTest`).
- **공통 모델 연결(사장님 2026-10-29: 「백엔드의 공통 모델 연결 구조를 완성한다」).** 업체별 요청 · 응답은
  `agent/llm/provider`에만 있다 — `LlmWire`(OpenAI Chat · Anthropic Messages)와 `EmbeddingWire`(OpenAI). 각 기능은 자기
  플래그 · 키 · 프롬프트 · 스키마 · 해석기 · 문을 그대로 갖고, 바이트와 읽기만 wire에 묻는다(생성기가 여전히 전송을 쥔다).
  `*_VENDOR`로 바꿀 수 있는 기능: 답글 에이전트 · 문의 초안 · 사실 확인 · Operator 계획/판정/대화 · 목표 해석 · 책임 조사 ·
  이미지 지식 · 문의 판단 · 질문 의도 · 근거 적격성 · 리뷰 사진 판독. 임베딩은 자기 설정(`SELLEROPS_KNOWLEDGE_EMBEDDING_VENDOR`)
  으로 채팅 업체와 따로 바뀌고, Anthropic은 임베딩 API가 없어 시작을 거부한다. OpenAI 아닌 업체의 벡터는 `업체:모델` 이름으로
  저장돼 OpenAI 벡터와 섞이지 않는다. 모르는 업체 이름은 OpenAI로 바뀌지 않고 시작을 거부한다(업스테이지는 국내 리전 조건 ·
  지원 기능 확인 뒤 wire 하나로 붙인다). 예외: 예전 리뷰 분류 AI(`ApiTriageClassifier`)는 요청 바이트가 봉인된 측정 기록이라
  그대로 둔다(`VendorWireFenceTest`가 예외를 이름으로 적는다).
- **Claude에 보내는 스키마.** Claude의 구조화 출력은 개수 · 길이 · 범위 제약(`minItems`>1 · `maxItems` · `maxLength` …)을
  받지 않아, 보내는 사본에서 뺀다(`AnthropicMessagesWire#forClaude`). 같은 제약은 각 기능의 해석기가 그대로 검사한다 — 문의 판단은
  필요 항목마다 판정 하나가 아니면 `VERDICT_SET`로 실패한다(`CrossVendorDecisionContractTest`). 그래서 Claude에선 이 실패가 늘 수
  있다.
- **판정 v3(사장님 2026-10-29: 「v3 구조로 만들고 v2와 비교해 줘」).** `coverage-judge/v3`는 v2 규칙을 글자 그대로 두고 답의 모양만
  바꾼다 — 판정을 목록이 아니라 need id를 키로 하는 객체로, 각 id는 필수 칸, 다른 칸은 금지. 개수가 구조 자체라 두 업체 모두
  강제한다. 해석기는 v2 목록으로 바꿔 같은 엄격 검사를 거치고, 같은 칸이 두 번 오면 `VERDICT_SET`(`CoverageJudgeV3Test`). 기본은
  v2 그대로다(`SELLEROPS_INQUIRY_DECISION_JUDGE_PROMPT=coverage-judge/v3`로 고른다).
- **v2 · v3 비교(2026-10-29, Claude Opus 5.5, effort low, 평가용 복사본).** 실제 문의 19건(네이버 상품 Q&A 8 · 네이버 고객 문의 6 ·
  쿠팡 2 · 카페24 답변된 글 3)을 운영 평가 경로(`InquiryKnowledgeAssessor#assess`, 저장된 주문 사실만, 쓰기 없음)로 돌리고, 같은
  need · 근거로 두 판정을 각각 2번(`JudgeArmComparisonIT`, 결과는 id와 닫힌 단어만 저장소 밖에). 검색 보조(임베딩 · 의도 ·
  적격성)는 꺼 두었다. 결과: 두 판정 모두 38번 중 실패 0. 같은 문의 · 같은 회차에서 판정이 같은 것 44/48 — 각 판정 안에서
  1회차와 2회차가 같은 것도 22/24로, 차이는 반복 흔들림 수준이다. 토큰은 비슷(입력 v3 +4%). 한계: need가 하나뿐인 문의가 14건이라
  개수 제한이 실제로 시험된 것은 need 2개짜리 5건뿐이고, FULL 판정이 한 번도 없어(근거 후보 2–8개, 지난 답변 0) 「답할 수 있다」
  쪽은 비교되지 않았다. 처음 무작위로 뽑은 20건은 전부 답변 안 된 카페24 게시판 글이었고 플래너가 20건 모두 「요청 없음」으로
  봤다 — 이 조직 문의 3,443건 중 3,267건이 그런 글이다.
  **결과의 범위(2026-10-29 검토 반영):** 이 비교는 답의 형식과 판정 일치도를 확인한 기록이며, 실제 응대 품질이나 v3의 우위를
  증명하지 않는다. FULL 0건의 원인을 검색 보조가 꺼져 있었기 때문이라고 단정하지 않는다 — 자료 · 상품 연결 · 검색 · 판정을
  구분해 본다. 카페24 자료 확인 건은 같은 날 오너가 이미 확인했다고 알려 후속 작업에서 제외했다(§8).
- **증명.** 같은 답을 두 업체 봉투로 넣으면 같은 결과 · 같은 실패 단어(`CrossVendorDecisionContractTest`, `LlmWireTest`).
  OpenAI 요청 바이트는 그대로(기존 payload floor 테스트 통과). 개인정보 관문(`LlmSendGate`)은 전송 계층에 있어 업체와 무관하다.
- **알려진 빈틈(이번에 바꾸지 않음).** 문의 판단 · 질문 의도 · 근거 적격성 · 임베딩 · 리뷰 사진 판독 · 이미지 지식 호출은 하루
  AI 상한(`agent_llm_usage`)에 세지 않는다 — 공통 연결 이전부터 그랬다.

## 4-1. 평가는 쓰는 쪽과 떼어 놓는다 (사장님 2026-10-28: 「같은 기준표로 채점하면 실제 품질이 그대로여도 점수는 좋게 나올 수 있으니 유의」)

- **사람 정답이 먼저:** 사장님이 일부 사례에 직접 좋다 · 나쁘다를 매기고, 자동 채점은 그 판단과 맞는지로 검증한다.
- **블라인드 비교:** 예전 답글과 새 답글을 가린 채 나란히 보인다.
- **채점자 분리:** 채점은 에이전트의 검토 단계와 다른 지시문 · 다른 모델로 하고, 기준표 문구를 그대로 쓰지 않고 결과를 묻는다
  (「이 고객이 읽고 해결됐다고 느끼는가」).
- **사실 대조:** 이미 해 본 방법을 다시 권했는지 · 약속을 지어냈는지 · 개인정보가 들어갔는지는 사람이 단 정답과 코드로 본다.
- **보류 사례:** 규칙을 다듬을 때 본 사례와 평가 사례를 나눈다.
- **도구:** `tools/eval/reply-agent/` — 같은 리뷰를 이전 방식과 에이전트가 각각 쓰고(`run_eval.sh`), 가린 A/B 비교표 · 정답 열쇠 ·
  별도 채점자 입력 · 코드 사실 검사를 만든다(`build_sheet.py`, 결과는 저장소 밖으로만). 채점자 지시문은 `judge_prompt.md` — 기준표
  문구 없이 결과를 묻는다.
- **이번 실행에 묶는다(2차 검토):** 비교표는 이번 실행이 만든 버전만 읽는다(이전 방식 = generate가 돌려준 버전, 에이전트 = 그
  실행 ID가 저장한 버전). 초안이 없으면 이유(사람에게 넘김 · 저장 안 함 · 생성 실패)를 열쇠에 남긴다. 버전마다 인용 근거 원문을
  붙여, 사람과 채점자가 약속 · 숫자를 정책과 대조한다. 채점자는 A/B를 바꿔 두 번 채점한다(위치 편향).
- **채점 모델에는 정제본만(2차 검토):** 외부 채점자 입력의 리뷰 · 답글 · 근거는 백엔드의 모델 전송 전 정제기를 그대로 거친다.
  사장님 비교표만 원문이다.
- **지식 고정:** 실행 시작 · 끝의 지식 지문이 지금과 같고 인용 원문을 다 되살린 답글만 사실 정확성을 채점한다.
- **고르는 판단은 따로:** 이 도구는 모든 사례를 먼저 「대응 필요」로 정하므로 답글 품질만 잰다. (리뷰 화면 버튼은 2026-10-28부터 에이전트를 돌린다 — 도구 README가 한동안 「아직 이전 방식」이라 적고 있었다.) 어떤 리뷰에 답할지 고른 판단은
  미리 쓰기가 실제로 고른 것과 사장님 판단을 따로 맞춘다.
- **시작 규모:** 리뷰 30 · 문의 20 정도의 실제 사례 + 위험 · 단위 바뀜 · 정책 충돌 · 복합 질문 합성 사례. 결함을 찾는 규모이지
  정확도를 보증하는 표본이 아니다.

## 6. PD-5를 다시 연다

PD-5(2026-09-16)는 판매자 없는 조사를 백엔드 안에 두었다 — runtime이 그렇게 돌려면 system principal이 필요하고 그것이
보안 경계 변경이라서. 이번 결정은 그 경계를 **좁게** 바꾼다: system principal이 아니라 **실행 하나 · org 하나 · 허용 경로만 ·
몇 분 · 1회용**인 토큰이고, runtime은 그것을 저장하지 않는다. PD-5의 다른 조건(고객 전송 금지, run이 확정한 org가 경계,
org 범위의 도구만)은 그대로다. 기존 백엔드 Investigator는 이 그래프가 대신할 때까지 남는다.

## 7. 순서

**2026-10-29 기준.** 기준표 계약 · 실행 토큰 · 사용량 기록 · 리뷰 모델 단계 · runtime 그래프 · 미리 쓰기 · 판매자 누름 화면 연결은
구현했다. 공통 판단은 §3-4처럼 답글 에이전트가 먼저 읽어 저장하고 이후 단계가 재사용한다 — 예전 분류 AI가 먼저 범주를 내도록
바꾸는 것이 다음 순서는 아니다. 예전 분류 AI는 남은 사용처를 대체한 뒤 은퇴하며, 화면 전체의 전환은 사람 정답으로 잰 뒤 한다.

**현재 진행은 판매자용 설치 제품 개발이다.** 이를 유지하고, 답글 에이전트 작업을 다시 시작할 때는 §8의 순서를 따른다.
문의에는 기존 초안 · 사실 확인 · 지식 판정 경로가 있지만, 이 문서의 리뷰용 LangGraph를 문의 실행으로 확장하는 일은 아직 남아 있다.

## 8. 아직 하지 않은 일 (사장님 2026-10-29: 「아직 하지 못한 작업은 기록해두고, 나중에 하자」)

다시 시작할 때 이 목록에서 고른다. 「필요한 것」은 해당 실행의 조건이며, 아직 채워지지 않았다고 평가표 빈 양식 작성이나
설정 · 근거 목록 정리까지 막는 것은 아니다. 아래는 후속 작업 기록이며, 완료 표시가 없는 작업을 구현 완료로 읽지 않는다.

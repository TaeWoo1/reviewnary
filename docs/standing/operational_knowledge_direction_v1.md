> **아이템 정의의 단일 원본:** [제품 기준 문서의 「현재 아이템 기준」](../sellerops_canonical_reference.md). 이 문서의 §0은 운영 기록 연결·권한·기술 경계의 상세 근거이며, 전체 아이템이나 시뮬레이션의 별도 최신본이 아니다. 아래 개발 순서 제안은 이번 문서 정리의 실행 목록이 아니다.

> **이 문서는 아무것도 구현하지 않는다.** 장기 방향을 기록해서, 오늘의 좁은 선택이 내일의 넓은
> 구조를 **막지 않게** 하는 것이 전부다. 작성 당시 phase의 범위는 **상품 상세페이지 grounding까지**였다. 현재 시점의 설명은 아래 §0을 먼저 읽는다.
> 작성 2026-08-26 (product-owner decision).

## 0. 중기 목표와 현재 구현의 경계 (2026-11-12 정리)

이 절은 2026-10-13 오너 인터뷰 질문 76-80과 2026-11-12의 「가게 운영 기록을 연결하는 제품」 방향을 연결한 설명이다.
새 구현·일정·임계값·외부 권한을 승인하지 않는다. 아래 §1-§5는 2026-08-26 당시 설계 근거이며, 당시의 「현재 phase」를 지금 범위로 읽지 않는다.
현재 운영 계약은 `docs/product-scope-v1.md` v1.15와 `docs/reviewnary_product_architecture_proposal_v1.md` §19다.

### 0.1 목표: 답변 작성 위에 놓일 가게의 운영 맥락

여러 채널의 상품·옵션, 주문·배송, 문의·리뷰, 가게 기준, 판매자 처리 기록과 고객에게 안내한 내용을 **해당 가게의 업무 단위로 연결**한다.
사람과 허용된 AI가 「무슨 사실을 아는가 / 어디서 언제 확인했는가 / 지금 이 주문에 적용되는가 / 누구의 결정이 필요한가」를 같은 기록에서 판단하게 하는 방향이다.
고객 응대는 그 기반을 쓰는 첫 업무다. 이를 「운영 장부」 또는 온톨로지에 가까운 구조라고 설명할 수 있지만,
새 그래프 DB·범용 엔진을 도입하기로 결정한 것은 아니다. 기존 관계형 DB의 식별자·근거·상태 연결부터 검증한다.

판매자에게는 구조보다 결과를 설명한다: **가게 기준과 처리 기록을 다시 찾아보는 일을 줄이고, 답변 뒤 남은 일도 놓치지 않게 한다.**
「다시는 묻지 않음」「모든 사실을 실시간으로 앎」처럼 보장하지 않는다.

### 0.2 현재 출발점과 아직 채워야 하는 연결

| 영역 | 현재 조사에서 확인한 출발점 | 중기 보완·미확인 |
|---|---|---|
| 근거·기억 | 상품/정책 검색, 적용 가능성, 과거 답변·판매자 기록을 쓰는 경로 | 가게 설정 부담·반복 질문이 실제로 줄어드는지 측정 |
| 주문 맥락 | 조직·계정·정확한 주문 참조·신선도 조건을 거치는 주문 사실 경로 | 모든 채널·교환 건의 출고 상태를 아는 것은 아님 |
| 남은 질문 | 부족한 사실과 별도 질문을 보존하고 판매자가 보완하는 경로 | 매번 정확히 하나만 묻거나 모든 누락을 잡는다는 보장은 없음 |
| 처리 추적 | 판매자 진행 기록·다음 확인일, 등록과 실제 처리 완료를 분리 | 채널의 실제 교환/환불 완료를 독립 확인하는 범위는 별도 검증 |
| 약속 | 근거 없는 일부 조치·숫자·비용 조건을 검사하는 경로 | 「오늘 출고」 안내와 실제 출고의 자동 대조·위반 탐지는 확인되지 않음 |
| 실행 권한 | 현재 개별 승인, 허용 API/담당자 수행, 읽기 도구와 초안 저장의 경계 | 유형별 자동 발송, 외부 AI의 장부 쓰기는 현재 제공 권한이 아님 |

실제 코드 대조: `InquiryDraftComposer`와 `OpenQuestionService`, `InquiryFollowUpService`,
`InquiryApprovalWithdrawalService.toldBehind`, `InquiryOrderFactReader`, `OperationsPolicyFence`.
소스 확인은 새 실행 검증을 대신하지 않는다. `operationscase`는 환불을 실행하는 API라는 뜻이 아니다.

### 0.3 자동화 방향은 이미 합의했고, 수치는 아직 정하지 않았다

근거: `docs/reviewnary_implementation_goals_draft_v1.md` 질문 78-80(2026-10-13).

1. 판매자가 **명시적으로 맡긴 업무 유형**만 자동 발송 후보로 삼는다. 개별 승인율 하나로 자동 전환하지 않는다.
2. **유형 수준:** 실제 사실·정책 오류, 의미 있는 수정, 충분한 표본·기간 등을 평가한다. 말투 수정은 사실 오류와 구분한다.
3. **개별 건 수준:** 근거·최신성·적용 범위·채널 권한을 충족하고 정책 충돌·특별한 약속 등의 예외가 없어야 한다. 예외는 승인으로 돌아간다.
4. 오류 확인 시 영향 유형을 멈추고, 수정·재검증 후 **판매자가 재개**한다. 자동 복구 완료가 자동 재개 권한은 아니다.

필요 표본·허용 오류·기간·유형 분류·중단/정정 UX는 앞으로 설계할 항목이다. 현재 데모는 개별 승인을 유지한다.
환불·보상 등의 금전 실행까지 한꺼번에 위임한다고 해석하지 않는다.

### 0.4 개발·검증 순서 제안 - 확정 일정 아님

| 단계 | 증명할 것 | 넘어갈 때 볼 근거 |
|---|---|---|
| 지금: 좁은 판매자 데모 | 실제 담당자가 과업을 이해하고 같은 품질로 끝내는가 | 직접 작업시간, 필수 질문 해소, 수정·오류, 반복 사용 의향 |
| 다음: 반복 사용·기록 연결 | 한 번 확인한 기준이 다음 유사 업무의 확인을 줄이는가 | 초기 설정시간, 반복 질문·재입력, 과거 기록 오적용, 최신성 누락 |
| 이후: 허용 범위 결과 관측 | 답변 확정·등록·조치 완료를 혼동하지 않는가 | 관측 가능한 결과 / 모름 / 재문의·정정, 대행 포함 총 노동 |
| 조건 충족 뒤: 유형별 위임 | 위임해도 품질·권한·복구가 유지되는가 | 유형·개별 건의 이중 기준, 판매자 위임/중단/재개 기록 |
| 별도 검토: 외부 AI 연동 | 다른 도구가 가게 맥락을 안전하게 활용하는가 | 조직·자료·동작별 권한, 최신성, 감사, 멱등성; 쓰기 범위는 미정 |

### 0.5 사업 효과와 해자는 실측 가설이다

- **판매자 효율:** 같은 난도·같은 품질의 수작업 대비 직접 작업시간과 찾기 시간을 비교한다. AI 대기·고객/정보 대기는 별도다.
- **서비스 전체 효율:** 대표/담당자의 초기 설정·수집 대행·등록·예외 복구 노동과 모델·인프라 비용을 포함한다. 판매자 노동을 우리 쪽으로 옮긴 것만으로 자동화라 하지 않는다.
- **누적 자산의 효과:** 새 가게 준비시간, 같은 문제의 재확인 횟수, 잘못된 기억 사용, 반복 사용·유료 유지가 개선되는지 본다. 데이터 양이나 옮기기 어려움 자체를 해자로 단정하지 않는다.
- **증거 구분:** 가상 패널 반응은 피치·가설 점검용이다. 실제 구매율·수요·효율 KPI가 아니다. 관찰표는 `docs/pilot/pilot_usage_loop_v1.md` §9.5를 쓴다.

멘토링 PDF는 이 방향을 설명하는 날짜별 산출물이다. 제품 계약이나 실행 승인을 대신하지 않는다.


## 1. 왜 이걸 적어 두는가

지금 reviewnary가 답변의 근거로 검색하는 것은 사실상 **상품 지식**과 **org 운영 정책**, 그리고
판매자의 **과거 답변**이다. 그것으로 답할 수 있는 질문은 실제 백로그의 일부일 뿐이다. 판매자에게
오는 질문은 이런 것들이다 — 「이거 오늘 보내주시나요」 「재고 있나요」 「사은품 아직 주나요」
「이 옵션은 언제 들어와요」 「반품비 얼마예요」.

이 답들은 상품 상세페이지에 없다. **여러 시스템과 문서와 판매자의 머릿속에 흩어져 있다.**

위험한 것은 그 사실 자체가 아니라, 그 사실을 모른 채 오늘의 구조를 굳히는 것이다. 「knowledge란
곧 Product FAQ다」라고 가정한 스키마·검색·프롬프트를 만들면, 나중에 배송 일정을 넣으려 할 때
그것을 **가짜 상품 FAQ로 위장**해서 넣게 된다. 그러면 근거의 출처가 무의미해지고, 틀렸을 때 어디를
고쳐야 하는지 아무도 모르게 된다.

## 2. 언젠가 근거가 될 수 있는 것들

Product / Variant · Shipping schedule / shipping rule · Inventory / availability · Promotion ·
Gift(사은품) · Return / exchange policy · Channel-specific rule · Order context ·
Organization CS policy · Seller-authored operational note · 그 밖의 운영 사실.

## 3. 장기적으로 지향하는 모양

```
Entity  ─ 무엇에 대한 사실인가        (상품 · 옵션 · 주문 · 채널 · 조직)
Fact    ─ 그 사실 자체
Relation─ 무엇이 무엇에 매이는가
Provenance ─ 누가 언제 어디서 말했나  (판매자 입력 · 판매자 상세페이지 · 채널 API · AI 추출)
Applicability ─ 이 질문·이 고객·지금에 적용되는가
```

이 다섯은 **새 개념이 아니라 이미 저장소에 흩어져 있는 것들의 이름**이다:

| 장기 개념 | 오늘 이미 있는 것 |
|---|---|
| Provenance | `KnowledgeAuthorship`(V77) · `DataOrigin` · `AnswerMemoryStrength` · `FactConfidence` |
| Applicability | `SpecApplicability` · `OrderFact` freshness · `ChannelDataState` |
| Entity/Fact 분리 | `KnowledgeScope`(5종) · `product_facts` vs `product_knowledge_sources` |
| Relation | `InquiryOrderBinding` · `product_binding` · `thread_parent_external_id` |

즉 **ontology를 새로 만들어야 하는 상태가 아니라, 이미 그 방향으로 갈라져 있다.**

## 4. 이번 phase에서 **금지**

- ontology / knowledge graph 구현
- generic operational fact engine
- 배송 · 사은품 · 프로모션 · 재고의 **신규 ingestion**
- 새 connector 확장

## 5. 대신 지키는 것 — 「knowledge는 항상 Product FAQ다」가 되지 않게

이미 지켜지고 있고, 계속 지켜야 하는 성질들:

1. **`KnowledgeScope`는 상품에 매이지 않는다.** `ORG_OPERATIONS`·`ORDER_STATE`·`CHANNEL_FACT`가
   이미 상품 없이 존재하고, 상품이 없는 문의도 정책만으로 `GROUNDED`가 된다.
2. **검색 코퍼스를 갖지 않는 scope가 이미 둘 있다.** `ORDER_STATE`와 `CHANNEL_FACT`는 결정론적
   출처에서 그때 읽는다 — 「모든 지식은 문서로 색인된다」는 가정이 이미 깨져 있다. 재고·배송 일정처럼
   **변하는** 사실이 들어올 자리는 문서가 아니라 이 자리다.
3. **작성자 축과 문서 종류 축은 직교한다.** `KnowledgeAuthorship` × `KnowledgeSourceType`.
   새 출처가 생겨도 「누가 썼나」를 다시 설계하지 않는다.
4. **현재 사실과 과거 발언은 구조적으로 갈라져 있다**(`KnowledgeScope.current()`).
   새 운영 사실은 전부 CURRENT 쪽에 들어오면 되고, 우선순위 규칙을 다시 쓸 필요가 없다.
5. **적용 가능성은 근거와 별개의 주장이다**(`SpecApplicability`). 「근거가 검색됐다」와 「이 고객의
   이 질문에 그대로 쓸 수 있다」는 다르고, 그 구분은 배송·재고·프로모션에서 **더** 필요해진다
   (오늘의 배송 일정은 내일 틀리다).

**한 문장으로:** 새 종류의 운영 사실을 추가할 때 손대야 할 것은 **출처와 적용 가능성**이지,
검색·프롬프트·근거 표시의 **구조**가 아니어야 한다. 그렇지 않게 되는 변경이 나오면 그때 멈추고
이 문서를 다시 연다.

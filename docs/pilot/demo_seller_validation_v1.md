# Demo Seller Validation v1 — 외부 판매자 검증 준비 (2026-09-22)

> **2026-11-09 재검토:** §1–§6의 커밋·건수·시연 제약은 당시의 기록이며 현재 준비에 그대로 적용하지 않는다. 현재 목표인 **판매자 데모 → 사용 관찰 → 사업계획서의 실측 근거**는 §7을 먼저 읽는다. 서버형 기본 배치와 제공 범위는 [제품 구조 §19](../reviewnary_product_architecture_proposal_v1.md#19-서버-중심-웹-서비스로-전환-2026-10-31-오너-결정)가 우선한다. §7은 운영 활성화·외부 실데이터 처리 승인이 아니다.

**대상 커밋: `68bd10fc` (Demo Core FEATURE FREEZE).** 이 문서는 **새 기능을 정의하지 않는다** — 얼린 것을
외부 판매자 앞에서 어떤 순서로 보이고, 무엇을 말하고, **무엇을 관찰할 것인가**만 적는다. 제품 정의는
`docs/demo_core_experience_v1.md` §12가, 기동·환경·증명 수준은 `docs/demo_runbook_v1.md`가 계속 소유한다.

이 검증의 가설은 하나다:

> **판매자가 다른 채널을 직접 돌아다니지 않고 Reviewnary만 보고 오늘 고객운영 상황과 할 일을 이해할 수 있는가.**

그러므로 이 세션의 성공은 「판매자가 감탄했다」가 아니라 **그 가설이 참인지 거짓인지 말할 수 있는 관찰을
가지고 나오는 것**이다. §4가 그 관찰 목록이고, 시나리오(§2)는 관찰을 얻기 위한 최소 경로다.

> **문서 소유권 충돌을 보고한다.** `demo_runbook_v1.md` §3의 7화면 표(홈 → 리뷰 → 문의 → 연결 → 주문)는
> **A7(2026-08-18) 제품 조립의 walkthrough**이고, 이 문서의 §2는 **Demo Core freeze(2026-09-22)의
> walkthrough**다. 둘은 다른 화면 집합이며 아직 통합되지 않았다. 어느 쪽을 데모의 정본으로 할지는
> **product-owner 결정**이고, 이 문서는 그것을 대신 정하지 않는다 — Demo Core를 보이기로 한 세션에서는
> §2를 따르고, 런북 §3은 그대로 남는다.

## 1. Preflight — 데모 시작 20분 전

체크리스트의 모든 기대값은 **`68bd10fc` 기준 로컬 PG에서 실측된 값**이다. 다르면 데이터가 달라진
것이고, 그 자체는 결함이 아니다 — **다른 것은 기록하고 시나리오의 숫자를 그 자리에서 고친다.**

### 1-A. 기동 (5분)

```bash
tools/dev/local-stack.sh up      # backend :8080 + agent-runtime :8787 + frontend :5173
```

- **`bootRun`은 버전 핀이다.** 커밋을 옮겼으면 반드시 재기동한다 — 살아 있는 프로세스는 자기가 시작할 때의
  클래스를 계속 서빙한다.
- **agent-runtime(8787)은 Demo Core 7화면에 필요하지 않다.** 다만 띄우지 않으면 **모든 화면에서 콘솔 오류
  2건**이 나고 `/agent`가 실패한다. 판매자에게 콘솔을 보일 일은 없지만, 데모 중 개발자 도구를 열 계획이면
  띄운다.

### 1-B. 이것 하나가 없으면 데모의 첫 화면이 통째로 사라진다

```bash
# backend/.env.local — 이름과 데모 org 자신의 uuid; 편집 후 backend 재기동
RESPONSIBILITY_RUNTIME_ORG_IDS=7146c50f-ff6d-4c83-ae96-18c930e6d8e0   # 데모 제조사
```

비어 있으면 `available:false`가 되어 홈이 **레거시 네 영역**으로 떨어지고 확인 필요 · 실행 대기 · Case
화면이 **전부 없어진다**. 그리고 **아무것도 항의하지 않는다** — 아무도 지명하지 않은 조직을 거절하는 것이
그 코드의 옳은 동작이기 때문이다. 조건은 **둘**이다: 여기 이름이 있을 것, 그리고 responsibility 행이
`ACTIVE`일 것. 상세와 스케줄러 스위치는 `demo_runbook_v1.md` §1.

### 1-C. 화면으로 확인 (5분) — 판매자가 보게 될 그대로

| # | 확인 | 기대값 (`68bd10fc` 실측) | 어긋나면 |
|---|---|---|---|
| 1 | `/login?demo=1` → 로그인 | 폼이 데모 계정으로 채워져 있다 | seed off → §5-A |
| 2 | 홈 `/` | **「자동 확인」 카드**가 서고 네 영역 레이아웃이 **아니다** | §1-B |
| 3 | 홈 내 확인 필요 | **27건**, 첫 5줄 = 확인 필요 리뷰 3 + 9월 네이버 문의 2 | §5-C |
| 4 | 확인할 일 `/customer-operations/cases` | **홈과 같은 27건** | §5-C |
| 5 | 홈 실행 대기 | 승인된 리뷰 답변 **4건**, 전부 링크 | §5-D |
| 6 | 홈 반복 문제 | 「판단이 필요한 반복 문제가 1건… 1건은 지켜보고 있습니다」 | §5-D |
| 7 | Memory `/memory` | 이슈 **17건** (판단 1 · 관찰 1 · 잠잠 15) | §5-D |
| 8 | 케이스 하나 열기 | 본문이 깨끗하다(HTML 태그·엔티티 노출 0) | §5-E |
| 9 | 리뷰 하나 열기 `/reviews/reply/{id}` | 자동 분류와 반복 신호가 **서로 다른 사실**로 읽힌다 | §5-E |

### 1-D. 말하지 않기로 미리 정해 둘 것

데모에서 **누르지 않는다**: `/agent`(별도 기동 필요), `/connect`의 리뷰 수집 실행(로컬 도우미 필요),
`[쿠팡에서 보기]`(페어링된 도우미 필요). 판매자가 물으면 **「지금 이 자리에서는 안 보여 드립니다」**라고
말하고 넘어간다 — 준비되지 않은 것을 즉석에서 시도하는 것이 데모가 무너지는 가장 흔한 방식이다.

**라이브 마켓플레이스 실행은 이 세션의 범위가 아니다.** 하려면 그 turn 안에서 단일 사용 승인이 새로
있어야 한다(`docs/standing/sellerops_live_approval_contract.md`).

## 2. 시나리오 — 10~15분

원칙 셋. **(1) 설명하지 말고 먼저 보여준다** — 화면을 열고 3초 기다린 뒤 「여기서 뭐가 보이세요?」를
먼저 묻는다. **(2) 숫자는 화면이 말하게 둔다** — 우리가 읽어 주면 판매자가 그 숫자를 읽었는지 알 수 없다.
**(3) 구조지 못했으면 그대로 둔다** — 막히는 지점이 이 검증의 데이터다.

| # | 장면 | 경로 | 시간 | 보이는 것 | **핵심 가치 한 줄** (판매자에게 그대로 말한다) |
|---|---|---|---|---|---|
| 1 | 홈 | `/` | 2분 | 자동 확인(마지막 확인 시각 · 채널별 수집) → 내 확인 필요 27건의 첫 5줄 → 실행 대기 → 반복 문제 | **「아침에 채널 세 곳을 돌지 않고 이 한 화면에서 오늘 무엇이 기다리는지 보십니다.」** |
| 2 | 확인할 일 | `/customer-operations/cases` | 1.5분 | 같은 27건 전부, 기다린 순서 | **「홈이 줄여 보여 준 그 목록의 전부입니다 — 문의와 리뷰를 가르지 않고, 오래 기다린 순서 하나로 섭니다.」** |
| 3 | Inquiry Case | 2행의 케이스 행 → `/customer-operations/cases/{id}` | 3분 | 고객 문장 → 확인한 것 → 근거(운영 정책) → 준비된 초안 | **「고객 질문을 대신 읽고, 회사 기준에서 근거를 찾아, 보낼 문장까지 준비해 둡니다. 보내는 것은 대표님이 결정하십니다.」** |
| 4 | Review Case | 확인 필요 리뷰 행 → `/reviews/reply/{id}` | 3분 | 별점·고객 문장 → 자동 분류 → **반복 신호** → 답변 초안 → 판단 컨트롤 | **「한 건을 처리하면서 '이게 이번 한 번인지, 계속 생기는 일인지'를 같이 보십니다.」** |
| 5 | 실행 대기 | 홈으로 복귀 | 1.5분 | 승인된 리뷰 답변 4건, 각 행이 그 리뷰로 가는 링크 | **「승인은 문장을 확정하는 것이고, 등록은 판매자센터에서 대표님이 하십니다 — 저희가 몰래 올리지 않습니다.」** |
| 6 | 반복 문제 | 홈 → `/memory/{id}` | 2분 | 「접착 부족」 · 근거 18건 · 별점 분포 · 판단 기록 | **「한 건씩 보면 안 보이던 것이, 쌓이면 상품을 고칠 근거가 됩니다.」** |
| 7 | Memory | `/memory` | 1분 | 이슈 17건과 그 상태(판단 필요 · 관찰 · 잠잠) | **「고객이 반복해서 말한 것을 회사의 기억으로 남깁니다 — 담당자가 바뀌어도 남습니다.」** |

**닫는 질문(꼭 한다, 2분).** 「내일 아침에 이 화면을 먼저 열고, 네이버·쿠팡·카페24를 안 열어도 될 것
같으세요? 안 된다면 **무엇 때문에** 여십니까?」 — 이 세션에서 가장 값진 한 문장은 대개 여기서 나온다.

**시간이 부족하면 6·7을 줄인다.** 1~5가 가설의 본체이고 6~7은 그 위의 약속이다.

## 3. 데모 중에 하지 않는 말

- 「AI가 알아서 답변을 보냅니다」 — **거짓이다.** 이 제품에 dispatcher는 없다(freeze 계약).
- 「반복 문제를 자동으로 해결합니다」 — 반복 문제는 **일이 아니고** 동사도 버튼도 갖지 않는다.
- 「모든 채널에서 바로 답변이 나갑니다」 — 채널별 전송 준비 상태는 다르다
  (`docs/pilot/pilot_runtime_foundation_v1.md` §0-A).
- 숫자를 지어내지 않는다. 화면이 「확인할 수 없습니다」라고 말하면 **그대로 읽는다.**

## 4. 검증에서 관찰할 것

각 항목은 **행동으로 관찰 가능한 신호**와, 그 신호가 가설을 지지하는지 **반증**하는지를 함께 적는다.
판매자가 한 말을 그대로 적고, 우리 해석은 괄호로 분리한다.

### 4-1. Queue부터 보려 하는가

- **관찰**: 홈을 열었을 때 첫 클릭이 어디인가. 「전체 보기」/「확인할 일」로 바로 가는가, 아니면 홈의
  브리핑 5줄을 읽고 그 안에서 고르는가.
- **지지**: 홈에서 바로 한 건을 골라 연다 → 브리핑이 우선순위 역할을 하고 있다.
- **반증**: 홈을 훑고 곧장 전체 목록으로 간다 → **브리핑이 신뢰받지 못하거나 5줄 컷이 잘못됐다.**
  (freeze가 이미 올려 둔 항목: 간밤에 조사된 케이스가 5줄 컷에 안 보인다 — 이것 때문인지 확인한다.)
- **묻지 않는다**: 「목록으로 가실래요?」 — 유도하면 이 관찰은 무효다.

### 4-2. AI가 올린 Case가 볼 가치가 있는가

- **관찰**: Inquiry Case에서 판매자가 **어디를 먼저 읽는가**(고객 문장 / 확인한 것 / 초안), 그리고
  「이건 내가 안 봐도 되겠네」와 「이건 내가 봐야겠네」 중 어느 쪽을 말하는가.
- **지지**: 「이 정도면 그냥 보내도 되겠다」 또는 「여기만 고치면 되겠다」.
- **반증**: 케이스를 열고 **원래 채널을 확인하겠다고 말한다**(→ 4-5와 같은 신호), 또는 「왜 이게 올라왔는지
  모르겠다」.
- **함께 적을 것**: 케이스가 **왜** 올라왔는지(사유 태그)를 판매자가 소리 내어 읽는가. 못 읽으면 사유 문구가
  일하지 않는 것이다.

### 4-3. 근거와 초안을 신뢰하는가

- **관찰**: 초안을 **읽는가, 고치는가, 무시하는가**. 근거 카드를 펼쳐 보는가. 「이 문장 어디서 나온
  거예요?」를 묻는가 — 묻는다면 **화면이 그 답을 이미 말하고 있었는지** 확인한다.
- **지지**: 근거를 한 번 확인한 뒤 초안을 그대로/조금 고쳐 쓰겠다고 말한다.
- **반증**: 초안을 처음부터 다시 쓰겠다고 하거나, 근거를 보고도 **자기 회사 기준과 다르다**고 말한다
  (→ 지식이 비었거나 틀렸다는 뜻이고, 그것은 제품 결함이 아니라 **온보딩 과제**다. 구분해서 적는다).
- **함께 적을 것**: 「보내기」를 누를 수 있다고 **오해하는가**. 오해한다면 승인/등록 분리 문구가 약한 것이다.

### 4-4. 반복 문제 신호가 새 정보인가

- **관찰**: 「접착 부족 18건」을 보고 **이미 알고 있었다**고 하는가, **몰랐다**고 하는가. 안다면 **어떻게
  알고 있었는지**(감·CS 통화·반품률) 묻는다.
- **지지**: 「이 정도 건수인 줄은 몰랐다」 또는 근거 리뷰를 한 건씩 눌러 본다.
- **반증**: 「그건 원래 그래요」로 끝난다 → 신호는 참이지만 **행동을 바꾸지 못한다**(= 가치가 아직 없다).
- **주의**: 이 org의 반복 문제는 규칙 추출기의 것이고 **부정문 오탐이 남아 있다**. 판매자가 근거 하나를
  「이건 좋다는 얘긴데요?」라고 지적하면 **변명하지 말고 그대로 기록한다** — 이미 알려진 결함이다.

### 4-5. 기존 채널을 다시 직접 확인하려 하는가 — **이 검증의 핵심 지표**

- **관찰**: 세션 중 판매자가 **네이버/쿠팡/카페24를 열겠다고 말하거나 실제로 여는 횟수와 그 이유**.
- **분류해서 적는다**:
  - (a) **제품이 아직 못 하는 일** — 등록/전송처럼 설계상 판매자센터에서 하는 것 → 정상.
  - (b) **제품이 말했는데 못 믿어서** → 신뢰 결함. **가장 중요하게 기록한다.**
  - (c) **제품이 말하지 않은 정보를 찾아서**(주문 상태·정산·재고 등) → 범위 결함. 무엇을 찾았는지
    낱말 그대로 적는다.
- **지지**: 세션 내내 (b)가 0이다.
- **반증**: (b)가 한 번이라도 있다 → 「Reviewnary만 보고 이해할 수 있다」는 아직 거짓이다.

### 4-6. 기록 양식

세션당 한 장. **숫자보다 인용이 값지다.**

```
일시 / 판매자 / 채널 구성 / 커밋 68bd10fc
1. 첫 클릭:              (화면·요소)
2. 스스로 연 화면 순서:   (실제 순서, 우리가 안내한 것은 (안내) 표시)
3. 판매자 원문 인용 5개:  (그대로, 요약하지 않는다)
4. 채널을 직접 열려 한 순간: 몇 번 / 각각 (a)(b)(c) 분류와 이유
5. 막힌 지점:             (어디서 멈췄고 무엇을 찾고 있었는가)
6. 판매자가 물었는데 화면이 답하지 못한 질문: (전부)
7. 닫는 질문의 답:        (그대로)
```

## 5. 데모 중 장애 — 증상에서 문서로

## 7. 사용 관찰과 사업계획서 근거를 위한 데모 준비 (2026-11-09)

### 7.1 목표와 근거의 범위

**오너 목표:** 데모를 판매자에게 요청하고, 사용하면서 얻은 KPI와 피드백으로 사업계획서를 강화한다. 기능 안정성과 디자인 때문에 요청을 미뤘던 문제를 푼다.

**설계 제안:** 현재 구현된 고객 운영 흐름 중 설명·측정 가능한 범위를 골라 먼저 관찰한다. 아래 표본·기간·판정 기준은 제안이며 확보된 고객 수나 성과가 아니다. 제품 범위·승인·외부 데이터 처리 조건은 유지한다.

이번 확인은 문서와 현재 소스의 읽기다. 앱·DB·실제 채널·모델·핵클에 연결하지 않았다. 개별 검증 보고를 현재 배포 전체의 통과로 바꾸지 않는다. `구현됨`과 `외부 실사용 준비 완료`는 구분한다.

### 7.3 증거를 얻는 세 단계

| 단계 | 방식 제안 | 얻는 근거 | 주장할 수 없는 것 |
|---|---|---|---|
| A. 설명·체험 | 실제 응대 담당자 또는 대표 3~5명, 각 20~30분. 합성 사례·전용 조직, 실제 발송 없음 | 이해도, 무도움 과업 수행, 막힘, 초안 사용 의향, 후속 체험 약속 | 실제 시간 절감·유지율·업무 처리량·매출 효과 |
| B. 오너 내부 운영 | 기존 방향대로 본인 스토어 1주일·3일차 점검. 실제 경로 확인·라이브 승인 별도 | 일상 안정성, 새 업무 발견부터 결과 확인, 장애 복구·AI 비용 | 외부 판매자 수요·일반화된 품질 |

A의 모집·일정 조율은 준비와 병행할 수 있다. A의 참여가 B·C의 자격을 대신하지 않는다. 이전 Mac→Windows 검증 합의를 조용히 폐기하지 않는다. 웹은 실제 참여자의 OS·브라우저에서 확인하고, 도우미를 사용하는 체험은 해당 OS 설치·실행 검증이 필요하다.

### 7.4 체험 동선과 디자인 범위

핵심 설명: **“고객 문의와 리뷰를 먼저 정리하고, 근거를 찾아 답변을 준비합니다. 사장님은 필요한 정보와 보낼 내용을 결정합니다.”** 매출 대시보드·범용 채팅·전체 설정 탐색은 첫 체험의 중심에 놓지 않는다.

| 과업 | 판매자가 해볼 일 | 관찰 |
|---|---|---|
| 정상 답변 | 홈에서 선택 → 고객 질문·초안 확인 → 근거 → 승인 | 일 찾기, 근거 신뢰, 승인과 등록 구분 |
| 사실 하나 보완 | 조치 확인 안내 → 결과·한 줄 입력 → 답변 확인 | 제공할 정보가 분명한가, 기록 저장과 생성 실패 구분 |
| 별도 질문 유지 | 교환 완료 + 배송비 질문 → 남은 배송비 답 보완·처리 | 막힌 이유·해결 방법·중복 확인 |
| 진행 중 후속 확인 | 진행 중 기록 → 다음 확인 날짜 → 등록·조치 상태 구분 | 누구를 기다리는가, 언제 다시 보는가 |
| 복구 | 기록 변경 또는 생성 실패 → 새로고침 → 이어가기 | 기록·초안 보존, 복구 경로 발견 |

5분 설명·10~15분 직접 과업·5~10분 인터뷰를 제안한다. 앞의 세 과업은 직접 수행하고 뒤의 둘은 시간에 따라 확인 장면으로 진행한다. 도움 수준을 기록한다. 합성 체험의 승인은 실제 발송이 아니라고 명시한다.

디자인은 기존 계약의 글꼴·색·컴포넌트를 유지하며 홈·문의/리뷰 상세·결과 입력·승인/등록·첫 시작에서 막히는 곳만 고친다. `무슨 일 / 준비한 답 / 내가 할 일 / 현재 상태`를 구별하고 답변·주 행동을 먼저, 근거·이력은 펼쳐 보기로 둔다. 긴 설명·겹친 경고·중복 버튼은 관찰된 막힘 순서대로 정리한다. **전면 리디자인을 모집의 선행 조건으로 두지 않는다.** 새 화면·상태는 기존 시안 확인 규칙을 따른다.

### 7.5 요청을 시작하는 기준

**A 체험 준비 제안:** 같은 고정 후보로 앞의 세 과업을 실제 API 경로에서 두 번 연속 수행하고, 기록·수정 보존·새로고침 복구·실패 안내를 확인한다. 잘못된 대상·옛 기록의 승인·미승인 발송·다른 판매자 정보 노출은 남겨 두지 않는다. PC·휴대폰의 주 행동과 참여자 환경의 진입을 확인한다. 안전하지만 헤매는 부분은 체험에서 관찰할 대상이며, 모든 사용성 문제를 없애야만 요청할 수 있다고 보지 않는다.

전용 합성 조직·사례를 사용하고 실제 운영 데이터를 초기화하지 않는다. 장애 시 저장된 사례로 이어가되 출처를 밝힌다. 코드·프롬프트·설정·스키마·리허설을 한 후보로 고정한다. 미커밋 작업 전체를 배포 완료로 보지 않는다. 커밋·배포는 별도 실행 범위다.

**B·C 실사용:** 실제 수집 경로·업무 권한·결과 확인 수준·배포/지원/데이터 처리 조건을 더 확인한다. Cafe24 재확인은 필요한 실제 경로에 연결한다. `READ_ONLY`여도 기존 실행기는 내부 DB 상태·할 일·예산을 바꾼다. 관찰만 할지 실제 업무에 반영할지 실행 범위에 적고 [라이브 승인 계약](../standing/sellerops_live_approval_contract.md)을 따른다.

### 7.6 KPI·관찰·모집

지표 정의·출처 감사는 [파일럿 사용 지표 §9](pilot_usage_loop_v1.md#9-사업계획서-근거를-위한-최소-측정안-2026-11-09)가 소유한다. 핵클·GA4를 기다리지 않고 **기존 원장 집계 + 세션 관찰표 + 모집·후속 약속 기록**으로 시작한다. 새 대형 KPI 화면은 선행 조건이 아니다.

세션 기록 한 장: 세션 코드·일시·후보 버전·OS/브라우저 / 대표 또는 실제 담당자 / 평소 채널·업무량(자기 보고) / 합성·내부·외부 실사용 구분 / 과업별 성공·실패·중단과 무도움·힌트·대신 수행, 시간 / 초안 그대로·수정·미사용과 이유 / 막힌 문구·판매자센터 재확인 이유 / 다음 사용 의사·구체적인 후속 약속과 실제 이행. 발언·관찰 사실과 조사자 해석을 분리한다. 연락처는 별도 동의된 모집 명단에서 관리한다.

**모집 문안 초안(발송하지 않음):**
> 온라인 판매 문의·리뷰를 정리하고, 가게 기준을 참고해 답변을 준비하는 서비스를 만들고 있습니다. 실제 응대하시는 분께 20~30분 정도 직접 사용해 보시고 어려운 점을 듣고 싶습니다. 첫 체험은 준비된 예시로 진행하며, 실제 판매 계정 연결이나 고객 답변 발송은 하지 않습니다. 도움이 될 만하면 이후 실제 업무에 적용하는 제한된 체험을 별도로 상의드리겠습니다.

### 7.7 다음 작업 순서와 멈출 지점

1. **현재 후보 리허설:** 다섯 과업의 막힘·개입·복구 목록. 합성·가짜 모델부터 확인. 이번 설계만으로 유료 호출·DB 적용·배포·마켓 접근을 실행하지 않는다.
2. **핵심 UX·결함 수정:** 기록 보존·다음 행동·복구 우선. 새 채널·전체 디자인 개편·AI 솔루션 탐색은 하지 않는다. 기존 시안 계약 준수.
3. **최소 KPI 집계:** §9 원장 대조·코호트 분리·중복 처리. 리뷰 전용 결과를 전체 성과로 표현하지 않는다. 먼저 운영자 집계표를 만든다.
4. **A 체험:** 3~5명 제안, 관찰과 후속 약속 기록. 직접 사용에서 막힌 곳으로 두 번째 수정 우선순위를 정한다.
5. **B → C:** 실제 조건 충족 업무만 운영, 3일차 점검·1주 내부 운영 후 외부 범위 결정. 주 단위로 KPI·사례·비용 정리.

개발을 계속할 기준은 **이번 체험을 막는가 / 다음 행동을 이해하지 못하게 하는가 / 지표를 틀리게 만드는가**다. 해당하지 않는 기능은 이번 모집을 지연시키지 않는다.

사업계획서에는 대상·기간·표본·버전·업무 범위·측정 방법·확인 수준을 숫자와 함께 쓴다. 체험 참석은 사용 고객, 승인은 등록 완료, 사용 의향은 유료 매출, 경과시간 감소는 직접 작업시간 절감으로 바꾸지 않는다. 소수 사례의 재현 가능한 관찰을 시장 전체 효과로 일반화하지 않는다.

### 7.8 초안 품질과 서버 통신의 준비 판정 (2026-11-09 추가 확인)

**판정: 구현·개별 검증은 있지만 최신 후보의 전체 데모 준비 완료는 미확인이다.** 비용 없는 현재 확인은 문서·소스·기존 결과 파일·로컬 리슨 포트 확인이다. 실제 앱 로그인·서버 기능 호출·모델 호출·공개 배포 접속은 하지 않았다.

| 확인 대상 | 확보된 증거 | 아직 확인해야 할 것 |
|---|---|---|
| 실제 모델 초안 | 합성 18회 평가에서 수정 없이 사용 가능 7/18. 이후 개선과 R1·R2 각 1회 성공 기록 | 7/18은 이전 버전 결과이고 최신 품질 비율이 아님. 기본 지시 `coverage-judge/v6`, `agent-draft-prompt/v25`, `inquiry-claim-check/v13`의 반복 안정성은 미검증으로 기록돼 있음 |

로컬에서는 확인 순간 표준 개발 포트 5173·8080·8787의 리슨이 없었다. 이는 점검용 서버를 내려 둔 보고와 일치하며 통신 결함의 증거는 아니다. 외부 배포 서버의 가동 상태는 이 관찰로 알 수 없다.

**다음 확인 순서 제안:**
1. 배포할 코드·프롬프트·설정·스키마 후보를 고정한다. 데모 URL과 합성 테스트 조직, 실제/가짜 모델 구성을 명시한다.
2. 비용 없는 가짜 모델을 서버 뒤에 두고 정상 답변·결과 보완·별도 질문·진행 중·실패 복구를 실제 API로 확인한다. 두 번 연속 실행과 새로고침·다른 기기의 옛 화면 요청도 확인한다. 프런트 mock만으로 대체하지 않는다.
3. 같은 배포 모양에서 웹→업무 서버→agent-runtime→업무 서버 저장, 필요한 담당자 서버 왕복을 실제로 확인한다. 외부 브라우저가 판매자 PC의 localhost를 찾지 않는지, 실패 시 기록과 복구가 남는지 본다. health 200만으로 기능 통과를 선언하지 않는다.
4. 그 뒤 최신 지시의 실제 모델 확인을 최소 사례로 설계한다. 정상 답변·판매자 완료 기록·명시적 미정·불필요 요청 억제·별도 질문 유지가 포함돼야 한다. 한 번씩은 동작 확인이며 안정성 비율로 쓰지 않는다. 기존 자료를 재사용하고 추가 반복은 발견된 문제에 한정한다. 모델·호출 수·예상액·상한을 정한 별도 승인 전에는 실행하지 않는다.
5. 실채널이 포함된 체험은 채널별 제한된 승인 범위로 확인한다. 설명·합성 체험과 실제 실데이터 파일럿의 준비 판정은 분리한다.

효율 측정은 [사용 지표 §9.4](pilot_usage_loop_v1.md#94-업무-효율화-ai의-효과를-직접-측정한다-2026-11-09-오너-추가-요구)를 적용한다. 판매자가 줄인 시간, 전체 사람의 시간, 품질·재처리를 함께 본다. 이 절의 확인 계획은 아직 실행 완료가 아니며 유료 모델·배포·마켓 실행 승인을 대신하지 않는다.

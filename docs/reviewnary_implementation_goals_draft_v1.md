## 1. 기준과 해석

- 최신 방향 기준: 제품 오너가 공유한 GPT 대화(링크는 저장소 밖에 보관), 마지막으로 확인한 대화는 2026-09-21.
- 현재 우선순위 기준: 이번 대화의 실제 쿠팡·네이버·자사몰 계정 검증, 오래된 작업 노출, 폴더 기반 지식, 초기 연결 가이드, FE 및 SaaS 완성도 요구.
- 기존 기준: `docs/standing/responsibility_runtime_v1.md` §26의 Customer Operations Manager Demo v1, `docs/demo_core_experience_v1.md`의 이전 데모 정의.
- 이 초안은 최신 대화와 현재 요구를 종합한 **확인용 해석**이다. 공유 대화 속 GPT의 제안 전부를 제품 오너의 확정 결정으로 취급하지 않는다.
- 공유 페이지에서 보이지 않는 첨부 파일의 원문은 분석하지 않았다. 인터뷰 사례는 그 페이지에 표시된 분석 내용에 근거하며 독립적으로 검증한 원문 사실이 아니다.
- 기존 정본은 이번 초안으로 변경하지 않는다. 기능별 현재 구현 상태도 이 문서에서는 재판정하지 않는다.

## 2. 제품 정의

**Reviewnary는 판매자의 여러 채널을 대신 확인하고, 회사·상품 지식과 실제 운영 맥락을 이용해 고객 업무를 판단·준비·처리하며, 필요한 결정만 판매자에게 가져오는 고객 운영 제품이다.**

처음부터 전체 판매를 자동화하는 것이 아니라, 문의·리뷰 중심의 고객 운영을 실제로 맡길 수 있게 만든다. 대시보드, 채팅, 브라우저 조작, 답변 생성은 이를 위한 수단이다.

고객에게 먼저 증명할 가치:

제품 오너가 명시한 최우선 목표는 **사용자가 판매 후 운영에 들이는 시간 자체를 줄이는 것**이다. 업무 선별·판단·학습·보고는 이 목표를 위한 수단이다. 시간 절감의 측정 방식과 데모 통과 기준은 추가 합의한다.

- 여러 판매자센터를 반복해서 순회하고 로그인하는 수고를 줄인다.
- 새 문의·문제를 늦게 발견하거나 놓치는 일을 줄인다.
- 자료와 과거 대응을 매번 찾아 설명하는 수고를 줄인다.
- 확인해야 할 건에는 판단 근거와 필요한 대응을 함께 준비한다.

## 3. 당장의 구현 목표선

**외부 데모 전에 제품 오너의 실제 네이버·쿠팡·자사몰 계정으로 모든 대상 채널을 확인하고, 중요한 업무를 선별해 대응을 준비하며, 사용자가 수정·컨펌한 뒤 실제 답변을 발송할 수 있는 상태. 데모에서는 사용자 확인 없는 발송을 금지한다.**

단발성 기술 시연, 테스트 통과, 일부 채널의 과거 라이브 증명만으로 이 목표를 달성했다고 보지 않는다. 사용자 화면에서 실제 관찰·판단·대응 준비·수정 및 컨펌·승인 후 발송까지 이어져야 한다. 수정 저장과 발송 승인 UX의 구체적 관계는 추가 확인한다.

### 3.1 처음 연결하기

- 비개발자가 API 키 발급·권한 설정·인증·연결 확인을 제품의 안내로 진행할 수 있다.
- 필요한 단계와 현재 위치가 명확하고, 실패하면 원인과 다음 행동이 드러난다.
- 기존에 만든 상세 튜토리얼이 현재 채널 화면에서도 유효해야 한다.
- 연결됨은 실제 읽기 가능 여부와 구분해 검증한다. 인증 만료와 재연결 경로도 필요하다.

### 3.2 대신 확인하기

- 연결한 채널의 지원 대상 문의·리뷰를 정기적으로 확인하고 새 항목 및 변화를 반영한다.
- 채널별 마지막 확인 시각, 확인 성공 여부, 로그인 필요 및 확인 중단을 알 수 있다.
- 확인하지 못한 상태를 '새 업무 없음'으로 표현하지 않는다.
- 최초 연동으로 가져온 과거 기록과 지금 대응해야 하는 업무를 구분한다.
- 최초 연동 시 발견한 과거 미처리 업무는 별도 확인 대상으로 모아 보여준다. 이를 최근 업무의 일반 승인 대기에 자동으로 섞지 않는다. 선택한 과거 건의 대응 준비 흐름, 과거·최근의 경계 및 연동 후 누적되는 미처리의 처리는 추가 확인한다.
- 최근 업무 및 실제 확인·처리 활동이 보이지 않고 과거 업무만 노출되는 현상은 제품 오너가 현재 겪는 문제다. UI 정렬만의 문제로 단정하지 않는다. 수집·저장·업무 생성·홈 노출의 어느 단계에서 최근 건이 빠지는지 저장소·실행 검증 대상으로 남긴다.
- '오늘 먼저 볼 일'과 '확인할 일'에는 지금 확인할 이유가 있는 항목이 나와야 한다. 오래됐다는 이유만으로 숨겨서도 안 된다.

### 3.3 판매자의 지식을 이해하기

- 사용자가 지정한 **폴더를 지식 원천으로 연결**하는 경험이 목표다. 파일 한 건 업로드만으로 이를 대신했다고 보지 않는다.
- 폴더에 자료를 추가하거나 수정하면 자동으로 감지·읽기·지식 갱신하는 경험을 데모에서도 원한다. 별도 수동 갱신을 기본 사용 절차로 요구하지 않는다. 제품 오너는 UX를 최대한 개선하는 것을 이유로 명시했다. 반영 지연, 실패 표시·복구, 삭제 처리와 지식 충돌 정책은 후속 확인한다.
- 매뉴얼, 상세페이지 자료, 회사 CS 정책, 과거 문의·답변 및 대응 기록을 활용할 수 있어야 한다.
- 온라인 자료도 이 지식 체계에 담을 수 있어야 한다. 사용자가 저장하는 방식과 제품이 가져오는 방식의 범위는 인터뷰에서 정한다.
- 데모의 자료 범위는 지정 폴더와 연결 채널의 자료다. 응대 매뉴얼·재고 현황·상세페이지·과거 대응 기록 등을 대상으로 한다. 채널별 실제 접근 가능 범위는 구현 검증이 필요하며 이 범위 결정만으로 지원을 선언하지 않는다.
- 재고 현황은 지속적으로 바뀌는 운영 상태로, 매뉴얼 등 비교적 안정적인 지식과 구분한다. 조회 시점·신선도·획득 방법 및 답변 시 재확인 기준은 추가 확인한다.
- 새 자료와 기존 기준이 충돌하면 해당 부분만 채팅으로 확인하는 것이 기본이다. 다만 시간 흐름에 따라 달라지는 성질의 자료는 최신 정보를 우선 적용한다. 이 예외의 대상과 최신성을 판단할 관측·적용 시점, 원천 신뢰 기준은 후속 합의한다. 파일 등록 시각만으로 최신 정책이라고 판정하는 것은 아직 채택하지 않았다.
- 무엇이 등록됐고 어떤 회사·상품에 적용되는지, 어떤 자료를 근거로 판단했는지 사용자가 이해할 수 있어야 한다.
- 지식은 답변 작성뿐 아니라 사용 안내·상품 문제·사람 확인 필요 여부의 판단에도 연결돼야 한다.
- 없는 사실을 만들어 답하지 않고, 필요한 지식이 없으면 판매자에게 묻는다.
- 판매자가 알려준 내용이나 수정한 대응은 다음 유사 업무에 재사용할 수 있어야 한다.
- 판매자의 암묵지를 얻는 경험은 chat 기반이다. 한켠의 채팅창에 입력한 내용을 바탕으로 대응을 작성하고, 내용을 기록해 이후에 활용한다. 해당 UX의 중요성이 명시됐다. 현재 업무 맥락 연결, 지식 적용 범위·유효기간, 확인·수정 경험은 후속 인터뷰에서 구체화한다.
- 채팅에서 기억할 적용 범위가 명확하면 자동 추론해 기억하고, 기억한 범위를 짧게 표시하며, 애매하면 되묻는 방식에 제품 오너가 동의했다. 모든 재사용 지식에 별도의 확인을 매번 요구하는 방식은 기본으로 채택하지 않는다. 단기 답변 발송의 사용자 승인 경계와는 별개다.
- 채팅 외에 판매자가 초안을 직접 수정한 행동도 학습 신호로 사용한다. 일회성인지 공통 기준인지 불분명하면 짧게 확인하고, 일회성이 아닌 수정은 이후 대응 기준을 장기적으로 갱신한다. 원본 문서 변경 권한과 충돌 처리 방식은 아직 정하지 않았다.
- 학습으로 바뀐 기준을 원본 매뉴얼에도 반영하는 것을 선호한다. 다만 구현·운영 부담이 크면 일목요연한 정리·관리 방식으로 대신할 수 있다. 원본 수정 지원의 형식·승인·변경 이력·복구 및 데모 필수 범위는 아직 확정하지 않았다. 이번 방향 결정은 실제 원본 파일을 수정할 실행 승인이 아니다.

### 3.4 판단하고 대응 준비하기

- 단순 별점·키워드 분류를 넘어 고객의 상황과 회사·상품 지식을 함께 고려한다.
- 리뷰 대응 여부는 판매자별 기준을 반영한다. 모든 리뷰에 템플릿으로 감사 답변을 하는 판매자와 부정 리뷰에만 대응하는 판매자가 모두 있을 수 있다.
- 처음에는 기존 대응 기록에서 판매자 기준을 추론하는 것을 우선한다. 기간 제한·미대응 등으로 기록을 활용하기 어려우면 Reviewnary가 적절하다고 판단하는 기본 기준을 사용한다. 추론 또는 기본 기준을 판매자에게 제안하고 확인·수정받는 흐름이다. 기본 기준의 내용과 기록 충분성 판단은 추가 합의한다.
- 문제없는 긍정 리뷰에 대한 기본 기준은 리뷰 모수가 적으면 대응하고, 규모가 크면 대응하지 않는 방향이다. 모수의 집계 단위와 임계값은 미확정이다. 문제·불만·질문 리뷰까지 이 생략 기준을 확대하지 않는다.
- 기본 기준에서 문제없는 긍정 리뷰는 리뷰 모수가 적으면 감사 대응하고 규모가 크면 대응하지 않는다. 모수의 집계 대상·기간·단위와 전환 임계값은 아직 미정이다. 문제·불만·질문에 대한 대응 판단과는 구분한다.
- 판매자 고유의 말투·템플릿을 유지하되, 저평점 고객과 싸우는 등 공격적인 대응을 하지 않도록 돕는다. 과거 대응을 그대로 모방하는 것과 구분한다. 구체적인 경고·수정·차단 경계는 미확정이다.
- 일상적인 항목, 지켜볼 항목, 답변이 필요한 항목, 판매자 판단이 필요한 항목을 구분한다. 최종 분류 체계는 미확정이다.
- 필요한 경우 지원되는 주문·배송 맥락과 리뷰 사진도 판단 근거로 사용한다. 구체적 필수 범위는 인터뷰에서 정한다.
- 중요한 건에는 원문, 관련 근거, 권고 이유, 준비된 답변 또는 다음 행동이 함께 있어야 한다.
- 질문은 책임질 수 없는 결정이나 필요한 정보에 집중한다. 전체 조사·작업을 판매자에게 다시 떠넘기지 않는다.

### 3.5 실행하고 결과 확인하기

- 자동 확인·조사·분류·준비와 외부 자동 발송은 서로 다른 권한이다.
- **단기 데모에서는 사용자 확인 없는 발송을 금지한다. 사용자가 대응을 수정하거나 컨펌한 뒤에는 실제 발송하는 것이 목표다.** 발송 자체를 금지하는 것으로 해석하지 않는다.
- 수정만 저장하는 행동과 최종 발송 승인, 발송 후 확인·실패 처리의 세부 UX는 추가 확인한다.
- 동일한 확인 사항을 묶어 질문하고 결과를 보고하더라도, 답변 발송 전 승인은 개별 건별로 받는다. 데모의 일괄 발송 승인은 채택하지 않는다.
- 장기 목표는 지식을 근거로 문의에 답변하고 결과를 보고하며, 리뷰는 대응 필요 여부를 판단한 뒤 필요한 대응을 수행하는 운영 담당이다.
- 장기 외부 실행의 업무별 권한 및 고위험 예외 경계는 별도 확인한다. 장기 방향에 대한 동의는 지금의 라이브 실행 승인이 아니다.
- 채널에서 사용자가 별도로 답변한 결과를 단기 데모가 어떻게 반영할지는 인터뷰에서 확인한다.
- 미지원·미확인·실패·성공을 구분한다. 초안 생성이나 버튼 클릭만으로 완료라고 표시하지 않는다.
- 라이브 검증 및 외부 실행은 `docs/standing/sellerops_live_approval_contract.md`를 따른다.

### 3.6 제품으로 사용하기

- 사용자는 한 화면 흐름에서 현재 상태, 필요한 결정, 진행 중 업무, 완료 결과를 이해할 수 있어야 한다.
- 홈에서는 모든 승인 대기를 볼 수 있는 방향이다. 중요한 승인만 남기고 일반 승인 대기를 별도로 분리하는 것을 기본으로 채택하지 않는다. 중요도 등 정렬 기준은 사용자가 바꿀 수 있어야 한다. 기본 순서, 필터·페이지 처리와 승인 외 확인 업무의 배치는 추가 확인한다.
- 홈 승인 대기의 기본 정렬은 중요도순이다. 같은 중요도 내 순서와 중요도 산정 기준은 미확정이다.
- 우선순위의 기본 방향은 문의 우선, 리뷰 다음이다. 중요도 판단에서는 응답 기한 등 시간 긴급성을 중시하는 방향을 제품 오너가 제시했다. 심각한 리뷰의 예외, 기한을 알 수 없는 문의, 정확한 정렬 조합은 아직 확정하지 않았다.
- 매우 심각한 리뷰는 문의 우선순위의 예외로 먼저 보여줄 수 있다. 구체적인 판정 기준과 표시 방식은 아직 합의하지 않았다.
- 내부 실행 용어와 기술 진단을 사용자 경험의 중심으로 두지 않는다.
- FE, 초기 연결, 지식 설정, 오류·빈 상태·재연결은 이번 목표의 일부다. 기능 구현 뒤의 선택적 미화로 보지 않는다.
- 개발자의 DB 수정이나 숨은 플래그 조작 없이 일반 제품 경로로 주요 업무를 수행할 수 있어야 한다.
- SaaS 완성도를 외형만으로 판단하지 않는다. 가입·접속·설정·권한·연결·복구를 포함한 필수 범위는 인터뷰에서 구체화한다.

## 4. 처음부터 남겨야 할 학습 자산

최신 대화에서 강조된 구조는 **Context → Decision → Action → Outcome**이다.

- 그때 어떤 고객 신호와 회사·상품 자료를 보고 판단했는가.
- Reviewnary는 무엇을 추천했고 판매자는 승인·수정·거절 중 무엇을 선택했는가.
- 무엇을 수정했고 이유는 무엇이었는가. 이유 수집이 불필요한 사용자 부담을 만들지 않는 방식은 미정이다.
- 실제로 어떤 행동을 했으며 결과를 어디까지 확인했는가.
- 그 기록이 다음 판단에 어떻게 사용되는가.

대화 로그나 API 실행 로그를 많이 저장하는 것만으로 이 목표를 달성했다고 보지 않는다. 결과를 관찰할 수 없을 때는 미확인으로 남긴다. 승인 자체를 성공 결과로 간주하지 않는다.

제품 오너는 **모든 학습에서 기록이 중요하다**고 명시했다. 기록해야 할 항목·열람 및 수정 UX·보존 범위는 추가 정의한다. 학습 과정의 추적 필요성과 모든 원문·개인정보를 무제한 보존하는 것은 동일한 요구가 아니다.

## 5. 중장기 방향

- **중기:** 주문·배송·문의·리뷰를 가능한 근거에 따라 고객·상품 맥락으로 연결한다. 반복 문제와 구매 후 필요한 행동을 먼저 발견한다.
- **중기 후보:** 상품별 리뷰 요청 시점, 선제 안내, 재구매 안내, 반복 문제 개선 등 판매자별 운영 playbook을 축적한다.
- **장기:** 판매자는 상품과 운영 의도를 제공하고 Reviewnary가 허용된 범위의 판매 운영을 수행한다.
- 모델과 브라우저 실행 도구는 교체 가능하게 두고, 회사 지식·운영 상태·판단과 결과 기록은 Reviewnary의 자산으로 남긴다.
- 외부 도구를 단순한 대체 위협으로 보지 않는다. 성능 발전을 제품에 적극 활용하면서 Reviewnary가 소유할 지식·상태·판단·결과와 실행 도구의 역할을 구분한다.
- 장기 확장과 해자는 부차적인 후속 과제가 아니라 현재 기능을 설계하는 기준이다. 다만 실제 재사용·성과 개선이 입증되기 전에는 기록 축적만으로 해자를 확보했다고 주장하지 않는다.
- 다판매자 benchmark, 거대한 digital twin, 전체 판매 자동화는 현재 데모의 완료 조건이 아니다. 데이터 규모·권한·효과 검증이 필요한 미래 가설이다.

## 6. 구조 및 범위의 미확정 항목

공유 대화에는 Thin Bridge와 Aside를 사용한 Mac 전환 후 Windows 지원이 제안돼 있다. 이를 전체 고객 운영 목표와 구분한다.

- Windows가 첫 외부 데모의 필수 조건인지, 자기 계정 검증 후의 배포 조건인지.
- Aside 의존 및 설치·실행·비용·지원 범위를 사용자에게 어떻게 제공할지.
- 자사몰의 실제 플랫폼 및 채널별 반드시 지원할 데이터·행동.
- 정기 확인 주기와 중단 시 알림 방식.
- 폴더 동기화, 수정·삭제 반영, 온라인 수집, 자료 충돌·최신성·확인 절차.
- 업무별 자동 처리와 외부 실행의 권한 경계.
- 판매자에게 올리는 조건, 우선순위, 과거 backlog 처리 기준.
- 답변 말투, 이미지 판단, 주문·배송 맥락의 초기 필수 범위.
- 필요한 SaaS 운영 기능과 FE의 기준 화면.
- 검증 기간·표본·허용 실패 및 외부 데모 통과 기준.

이 항목들은 구현 편의에 따라 임의로 정하지 않고 제품 오너 인터뷰로 확정한다.

## 7. 완료 판정 제안

제품 오너가 자기 계정에서 아래 흐름을 일반 사용자 경로로 재현하고, 반복 사용에서도 맡길 수 있다고 판단하는 것이 첫 목표선이다.

**연결 → 지식 연결 → 새 업무 확인 → 근거 있는 판단·대응 준비 → 사용자 수정·컨펌 → 승인 후 실제 발송**

수정·컨펌 기록을 다음 판단·대응에 활용하는 것이 목표다. 데모에서 재사용 및 발송 결과 확인까지 검증할 필수 시나리오는 추가 확인한다. 사용자 승인 없이 대응하고 결과를 보고하는 것은 장기 운영 흐름이다.

동시에 확인해야 할 것:

- 중요한 항목을 놓치거나 과거 기록만 반복해서 보여주지 않는가.
- 지식 부족·확인 중단·실행 실패가 숨겨지지 않는가.
- 사람이 직접 채널을 확인하고 자료를 찾아 답하는 일이 실제로 줄었는가.
- 개발자가 옆에서 계속 수리하거나 대신 설정하지 않아도 유지되는가.

구체적인 수치와 기간은 아직 합의하지 않았다. 과거 공유 대화의 개발 진행률, 예시 자동 처리 비율, 데모 일정은 현재 완료 판정에 사용하지 않는다.

## 8. 인터뷰 기록

### 질문 1: 하루 동안 사용자가 열지 않았을 때 맡길 책임

제품 오너 답변, 2026-10-11:

- 장기적으로는 운영 담당이다. 문의는 product knowledge 등 knowledge base를 근거로 답변하고 결과를 보고한다.
- 리뷰는 단순 별점 기준이 아니라 대응 필요 여부를 판단하고 필요한 대응을 한다.
- 상품·배송 정보와 사용자의 과거 답변을 활용해 기존 대응 기준 및 템플릿과 이질감이 없게 한다.
- 당장 데모는 모든 대상 채널을 확인해 중요한 업무를 골라둔다. 대응 준비 및 사용자 수정·컨펌이 가능해야 한다.
- **단기는 사용자가 대응을 수정하거나 컨펌한 뒤 실제 발송한다. 장기는 문의에 대응하고 결과를 보고하며, 리뷰는 대응 필요 여부를 판단한 뒤 대응한다.** 단기 제한은 발송 자체가 아니라 사용자 확인 없는 발송이다.

추가 확인: 중요한 업무 및 대응 필요의 기준, 근거 부족 처리, 과거 대응에서 사실·판단 기준·문체를 구분하는 방식, 컨펌 이후 상태와 재사용.

### 질문 2: 리뷰의 대응 필요 기준

제품 오너 답변, 2026-10-11:

- 예시 2(5점이지만 설치 후 떨어지는 문제)와 3(2점 배송 지연)은 제품 오너의 기준에서 대응 대상이다. 별점만으로 판단하지 않는다.
- 예시 1(5점 칭찬)의 대응 여부는 이번 답변에서 확정하지 않았다.
- 판매자마다 기준이 다르다. 모든 리뷰에 특정 템플릿을 지켜 감사 답변을 하는 경우와 부정 리뷰에만 답변하는 경우가 있다.
- 이 문제에 관해 이미 라벨링하여 학습시켰던 이력이 있다는 제품 오너의 설명이 있다. 학습의 종류, 자료 위치, 현재 판단 경로에 적용되는지는 저장소 검증 대상으로 남긴다.
- 저평점 리뷰와 싸우는 행위 등을 하지 않도록 돕는 방향이 좋다.

추가 확인: 처음 연결한 판매자의 기준을 얻는 방식, 명시적 설정과 과거 관행이 충돌할 때의 우선순위, 부적절한 대응에 대한 개입 수준.

### 질문 3: 판매자별 기준의 초기 설정

제품 오너 답변, 2026-10-11:

- 기존 기록에서 추론하는 것이 첫 번째 선택이다.

- 기존 기록에서 추론한 기준을 제안하고 판매자가 확인·수정하는 방식(질문 3의 선택지 3)이 가장 좋다.

추가 확인: 기본 대응 기준의 내용, 과거 기록이 충분한지 판단하는 방법, 일부 기준만 추론 가능한 경우의 처리, 무응답이 의도적 판단인지 미처리인지 구분하는 방법.

### 질문 4: 기본 기준에서 문제없는 긍정 리뷰의 대응

제품 오너 답변, 2026-10-11:

- 기본 기준에서는 리뷰 모수가 적은 경우 대응하고, 규모가 큰 경우에는 대응하지 않는 것이 좋다.
- 모수 기준은 아직 정하지 못했다.
- 리뷰가 구매행동에 영향을 미치므로 리뷰의 절대적인 수가 중요할 것 같다는 제품 오너의 판단이다. 누적 리뷰 수, 감사 답변과 구매행동의 실제 관계는 검증된 효과로 간주하지 않는다.

추가 확인: 상품별 누적 리뷰 수와 유입량의 우선순위·조합, 채널별 계산 여부, 전환 임계값 및 판매자 조정 방식. 질문 5에서 집계 기준의 최종 결정은 보류했다.

### 질문 5: 긍정 리뷰 대응 기준의 집계 단위

제품 오너 답변, 2026-10-11:

- 이치상 상품별로 보는 것이 맞을 것 같다.
- 다만 운영자는 신규 리뷰 유입량을 기준으로 잡고 싶어 할 것 같다.
- 더 고민할 필요가 있으며 이번 답변에서 최종 기준을 확정하지 않았다.

열린 결정: 상품별 누적 리뷰 수(구매자 관점)와 신규 리뷰 유입량(운영 부담 관점)을 구분해 검토한다. 어느 한쪽이나 두 기준의 조합, 임계값, 판매자 설정 방식은 아직 채택하지 않는다.

### 질문 6: 초기 지식 획득 범위

제품 오너 답변, 2026-10-11:

- 전체 방향으로는 지정 폴더, 연결 채널 자료, 외부 리소스를 포함하는 1~3의 범위를 생각한다.

- 고객 운영 관리: 운영 중, 2시간마다를 표시하지만 마지막 확인과 다음 확인이 모두 9월 27일로 표시되고 최근 24시간 자동 확인은 0건이다. 실제 스케줄러 정지·지연·자료 고정 여부 등 원인은 진단하지 않았다.
- 확인할 일: 문의·리뷰·승인·초안 필요 필터는 있다. 1년 넘은 업무는 별도 목록 제목으로 나누지만 같은 페이지와 전체 집계에 포함된다. 1년 미만의 오래된 업무도 현재 업무 목록에 남아 있어, 최초 연동 과거 미처리를 별도 확인한다는 목표와 같지 않다.

평가: 현재 홈은 운영 대시보드의 일부 요소를 가진 업무 요약 화면이다. 최신성·확인 범위·실제 활동·전체 승인 대기를 함께 이해하는 목표는 아직 충족하지 못한다. 화면 재배치와 실제 자동 확인의 정상 동작 검증은 별개의 작업으로 다룬다.

#### 에이전트 범위 검토: 제안 당시의 기록, 합의는 질문 32 참조

현재 코드 재확인: `agent-runtime/src/operator/graph/operatorGraph.ts`는 LangGraph StateGraph를 사용하고 LLM 계획·specialist 조사·근거 검증·제한된 재계획을 수행한다. `agent-runtime/src/operator/tools/OperatorToolRegistry.ts`는 WRITE 도구 등록을 거부한다. 이는 구조가 있다는 확인이며 현재 데모의 모든 기능이 정상 동작한다는 검증은 아니다.

제안: 범용 실행 에이전트를 별도로 제품 전체에 붙이기보다 기존 LangGraph를 업무 상태·중단·재개·승인 대기의 실행 구조로 사용하고, 그 안에서 판매운영에 필요한 자료 선택·추가 조사·분류·초안 준비를 제한된 도구와 예산 안에서 agentic하게 수행한다. 승인된 실제 발송은 기존 안전 계약을 지키는 별도 실행 경로로 다룬다. 자유문장 목표의 LLM planning 계약을 키워드 분기나 결정론 fallback으로 바꾸자는 제안이 아니다.

오너는 규정·상용 구조 검토를 위해 상세 인터뷰를 일시 중단한 뒤, 'AI 준비 -> 판매자 개별 승인 -> 허용된 공식 API 또는 권한 있는 담당자의 직접 등록 -> 결과 확인'의 하이브리드 구조를 확정했다. 확정 범위와 기존 합의 변경은 [제품 구조 v1 §12](reviewnary_product_architecture_proposal_v1.md#12-오너-확정-api와-사람-수행을-결합한-운영-ai)가 소유한다. 특히 네이버 리뷰의 기본 등록은 판매자가 아닌 담당자의 직접 수행이며, Aside 필수 설치는 초기 기본 의존성에서 제외한다. 기존 Q1~Q94는 인터뷰 당시 이력으로 보존하되 충돌하는 수단은 새 결정을 우선한다. 외부 허가·실제 구현·라이브 실행을 승인한 것은 아니다.

오너는 초보자도 API 연결·부매니저 등록을 수행할 수 있는 튜토리얼을 추가 요구했다. 자체 화면 안내와 외부 페이지 주입은 구분하며 구체적 구현 방식은 미확정이다. 개인사업자로 검증한 뒤 법인화하고 싶다는 선호를 밝혔으며, 공식 연결 자격과 단계별 제공 범위는 제품 구조 문서 §13에서 검토한다. 인터뷰 재개나 추가 번호 질문의 답변으로 간주하지 않는다.

## 후속 요청 — 데모 마무리와 회원가입 절차 (2026-11-14)

오너는 현재 구현 조사 후, 우선 백엔드 테스트 실패 2건의 정확한 원인·조치와 데모 실행본의 재현 조건 보존을 Claude에게 맡기기로 했다. 기존 미커밋 변경을 임의로 묶어 커밋하거나 실모델·실채널 실행을 시작하는 승인은 아니다. 이후 지식 자료·초안 품질, 카톡 알림, 분석 고도화는 각각 범위를 구체화하여 진행한다.

**회원가입 절차 개선은 후속 과제로 기록한다.** 지금은 개발하지 않고, 착수 시 현재 가입·첫 사용 흐름과 관련 서비스 사례·사용자 불편을 리서치한 뒤 설계·개발한다. 가입 항목·인증 방식·팀 초대·채널 연결의 배치는 아직 정하지 않았다. 기존 가입·인증·온보딩 결정을 이번 요청만으로 변경하지 않는다.
